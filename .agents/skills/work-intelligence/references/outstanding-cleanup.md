# Review outstanding items through proposals

Read this guide with the core [Work Intelligence skill](../SKILL.md) when the user asks to 整理未結項. The operation contracts of `work_request_outstanding_cleanup`, `work_get_outstanding_cleanup_context` and `work_submit_outstanding_cleanup_proposals` hold the outstanding cleanup contract.

When the user asks to 整理未結項, find the applicable Web-created pending request from `pendingRequests.outstandingCleanup` or paged `work_list_outstanding_cleanup_requests`. If no request exists, create one with `work_request_outstanding_cleanup` (`projectRoot`, a fresh `idempotencyKey`) instead of sending the user to Web, then continue with the flow below. It returns the project's open request when one exists (use it) and a `not_needed` outcome when no item is pending (tell the user there is nothing to clean up). Call it only because the user asked, never on your own initiative; it creates a request only. Do not ask for IDs.

Read `work_get_outstanding_cleanup_context` with `requestId`, or with `projectRoot` for the project's latest open request (exactly one of the two; `no_open_request` means nothing is open), reading independent item and Session pages (maximum 5 items and 10 Sessions, 24,000 serialized characters). Changing the item page changes its source time floor; a Session newer than one item can be older than another. Read every page needed and full source Sessions using `work_get_session`; inspect outcomes, verification, later contradictory work and PR evidence. Context truncation or a passed verification status alone does not establish completion. Eligible evidence is same-project, nonvoided, finalized, strictly later than that item's source and completed/created no later than requestedAt. Stale snapshot items must not receive new proposals.

Use `work_submit_outstanding_cleanup_proposals` for evidence-supported verdicts, each with a concise reason. `completed` and `not_needed` also need 1–10 `evidenceSessionIds`. `acknowledged` (記錄為已知限制) needs a reason and no evidence Session: use it for an item that is no task, such as a scope exclusion, a known limitation, an unverified-platform caveat or a decision left to the user. It is stored as not_needed and shown as a known limitation; never use it for work that may still be wanted. Supply distinct `examinedItemIds` and a subset of verdicts; an empty list correctly withholds unsupported inspected items. An item examined without a verdict can still get one in a later submission of the same request (it is rechecked like a first verdict); an item that already has a verdict, or an examined item resubmitted without one, is rejected as `already_examined`. Once every item is examined the request completes and accepts nothing more; then open a new request with work_request_outstanding_cleanup (still-pending items are included again). Paginate until the fixed snapshot is fully examined. Reuse a key only with the same normalized payload; never overwrite another examination or silently retry a conflicting payload.

Verdicts apply directly, like Agent review: each one changes the item status at submission and writes an Agent-sourced audit event linked to the request and proposal. Eligibility of every item, source and evidence version is rechecked in one transaction; one stale or ineligible verdict rejects the whole submission without writes, so re-read the context and resubmit. Do not bypass the request with finalize resolved/superseded IDs. Active-request snapshot items are protected from Agent finalization and nextSteps removal until the request is cancelled or completed. Tell the user how many items you closed and how many stayed pending, and that they can review every verdict in Web (工作歷程 → 未結項 → 整理未結項, "Agent 已結案") and reopen any item there individually or in a batch. There is no accept or reject step.
