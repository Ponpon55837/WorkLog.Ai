# Reading records, context, and recall

Read this guide with the core [Work Intelligence skill](../SKILL.md) when you read Sessions in part, page through context omissions, or rely on the details of recall and Knowledge search. The core's privacy rules and its rule to read the full source before relying on a pointer apply throughout.

## Optional Session field reads

Read a Session with `work_get_session` and `view: "handoff"` by default: summary, the five workSummary sections, verification, decisions, links, and `session.files`, which lists each changed path once with its status, sources and references. Use `view: "completion"` to check whether recorded work finished, fixed `select` groups from its operation contract for single families, and the full read (no view/select) only when you need raw `changedFilesProvenance`/`changedFileChanges`, events, evidence, Knowledge or diagrams. Projection includedFields/unavailableFields distinguish unread, historical unknown and selected empty data. Partial reads never satisfy full-source requirements: obtain all relevant evidence and inspect review, correction, void/trust and truncation state before relying on it. Projected raw content requires selecting rawSnapshots and includeRawSnapshots=true. Reconnect for updated contracts; schema is unchanged.

When re-reading a Session whose body is still in your current context, pass the `session.revision` you hold as `knownRevision`; on `session_unchanged` reuse what you hold. Never pass it for content you no longer hold (new conversation, after compaction, or a subagent).

`work_list_sessions` returns compact digests by default: summaries are truncated and changed-file paths, events, Evidence, and full `workSummary` are omitted. Use `work_get_session` with the returned `id` when you need the complete record. To find the Session behind a commit (from `git blame` or `git log`), pass `commitSha` (the full sha or an unambiguous prefix of at least 7 hex characters); the recorded sha is the HEAD seen at finalize, so it can be the commit before the work was committed. This compact behavior applies to MCP only; the Web REST Session list keeps its existing full list items.

## File history

A focused context sets `relevant.fileHistoryReadWith` when a path has more Sessions than it shows. Only recorded `changedFiles` relate a Session to a path. `work_get_file_history` returns whole-history totals (Sessions, dates, verification counts, Sessions with decisions, pending items), the newest Session digests, older failed or `not_run` Sessions under `attention`, and active Knowledge whose `appliesTo` covers the path, within 4,000 characters for one path. Page older Sessions by passing `nextCursor` back as `cursor` with that one path; read the Session with `work_get_session` (`view: "handoff"`; `readArguments` carries it) before relying on it.

## Context omissions and supplements

- Tool results are compact JSON. The complete context response is capped at 10,000 characters with a task or paths, and 16,000 without. Session and Knowledge records that also match another section appear once as full content; the other section only counts them.
- Focused `work_get_context` may include optional `relevant.supplements`: compact pointers from at most the three highest-ranked Sessions that remain after normal context budget trimming. They cover one-hop parent/related Sessions and active Knowledge those Sessions applied, with at most two pointers per source and four total. The existing `relevant.sessions` and `relevant.knowledge` lists keep their original contents, order, limits, and budget behavior. Each pointer's `includedBecause` names the source Session and relationship; treat it as possibly related context, never as a literal match or evidence. Knowledge pointers retain `possiblyStale` and `needsReview` flags. Pointers contain no excerpt or score; read the Session with `work_get_session` or search the Knowledge with `work_search_knowledge` before relying on it. Supplements are removed before existing context when the response budget is tight, and their omissions appear under `relevant.supplements`. Without task or paths, no supplements are returned.
- Read `omitted` before proceeding. It is a small pointer per section: `count`, `duplicates` (already shown elsewhere in this response), up to 3 budget-omitted `ids` with `reasons` plus `moreIds`, `entries` with only the id and flag of anything flagged `possiblyStale` or `needsReview`, and `readWith`, the full-read tool. Page review sections and citation ids are not repeated there; read them with `work_get_knowledge_page_context`. A `projectRoot` context names its project once in `project`; its items carry no `projectId`/`projectName`. Knowledge-page citation ids are capped at 8 per context; `sourceSessionIdsOmittedCount` gives the omitted count. Preserve `possiblyStale` and `needsReview` as review signals. Pending requests remain available in the context.
- Read full source records with the tool named by `omitted` (`work_get_session`, `work_search_knowledge`, or `work_get_knowledge_page_context`); read Sessions with `view: "handoff"` unless you need raw provenance, events or evidence. Use `work_preview_metadata_backfill` for metadata follow-up counts.

## Recall and search results

- `work_recall` and `work_search` both return compact hits rather than complete records. Excerpts are limited to 110 characters; `truncated: true` means the excerpt is partial. For `work_search`, a title-only strongest match may use the Session summary as the excerpt when that summary also matches the query. Words are matched independently, so natural-language and Chinese questions work.
- Search ranking gives more weight to structured Session fields (title, summary, workSummary) than raw handoff text. Identical raw sections are normalized and hashed within a project; the earliest Session reference keeps full raw weight and later duplicates are downweighted, so completed structured work can rank ahead of repeated old plans while raw-only answers remain searchable. A Session that continues an earlier hit (a `continues` link) and scores at least 30% of it is placed directly above that hit, so a chain shows its latest state first; the earlier record stays right after it. For ranking, query words found only in raw handoff text count half, so a long imported handoff that mentions many words in passing does not outrank a record that answers in structured fields; raw-only answers are still returned, just lower.
- Both tools report `confidence`: `none` means no hit reached 10% IDF-weighted query coverage and no path matched, so the hit list is empty and must not be used as evidence; `low` means only weak partial matches reached that floor, or the query was found only in raw handoff text (for example quoted in an old plan); `high` means at least one hit matched half the query in its title, summary, workSummary, or Knowledge, or matched a path. A question that no record answers can still come back `high`, and a correct answer often comes back `low`. `work_search` returns `{ outcome: "search", confidence, hits, termHits? }`.
- `work_recall` keeps only the strongest `matchedIn` field and linked Session ids/relations, without repeating linked titles; raw section headings are shortened. When `projectRoot` is supplied, it also omits the top-level project object. Scoped `work_search` omits repeated project identifiers.
- Treat compact hits as pointers and evidence for ranking: use `work_get_session` for Session hits and `work_search_knowledge` for Knowledge hits, and cite the returned Session or Knowledge id in the answer. A Session hit may list related Sessions (the plan it implements, or its follow-up); check them when the hit alone does not explain the decision.
- `work_search_knowledge` is a strict list: every word must appear in a title, body, tag, reference, or `appliesTo` path. With `q`, check `match`. `strict` means `items` answer the query. When nothing matches every word, `items` is empty and `match` is `relaxed` with up to 3 `relaxedMatches` or `none`. Relaxed matches are digests of ranked records of the same scope and status that share only their `matchedTerms` (plus `matchedPaths` for a file path matched by `appliesTo` or references), with a body `excerpt` of up to 400 characters. Treat them as leads: read one in full with `work_get_knowledge_history` (`projectRoot`, `knowledgeId`) and cite it only when it answers the question. An empty or relaxed answer may carry `otherStatusMatches` (for example `{ "archived": 2 }`): the default `active` filter hid those records, so search again with that `status` when older or replaced Knowledge is relevant, and say it is archived when you cite it. `otherStatusFullMatches` marks statuses whose records contain every word (the re-query answers strictly); the rest are partial leads. `effectiveQuery` means the query was cut at 8 words: resend exactly that with the status.
