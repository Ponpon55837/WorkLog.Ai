# Knowledge candidates, Knowledge pages, and recorded Knowledge

Read this guide with the core [Work Intelligence skill](../SKILL.md) when the user asks to extract Knowledge candidates, update the project's Knowledge pages, or record Knowledge, or when `pendingRequests.knowledgePages` in the context lists a page. The Knowledge candidate and Knowledge page contracts in the matching operation contracts apply as well.

## Git state and memory

Git is the source of truth for branch, commit, PR, and merge state. Knowledge pages do not record them; when asked, check Git live. Project facts already recorded in Knowledge or Knowledge pages are not copied into your own memory files; keep only a pointer (one fact, one place).

## Record Knowledge

Record or update Knowledge only when the user asks or when the MCP workflow explicitly calls for it, and only with reusable, source-supported facts; do not turn guesses or an entire Session transcript into Knowledge. When recording, set the paths it applies to when they are clear, and name the older Knowledge it replaces instead of leaving both active.

## Check the scope of recorded Knowledge

`work_record_knowledge`, and `work_update_knowledge` when it changes `appliesTo` on an active Knowledge, return `appliesToBreadth`: `share` is the fraction of the project's newest Sessions that changed 1–20 files and touched `appliesTo`, `sessions` is how many were compared, and `truncated` means more exist. When `broad` is `true` (at least 10 Sessions and a share above 0.15), `warnings` asks you to narrow the scope. Then replace the wide entries (a whole folder or a broad glob) with the specific files or subdirectories the Knowledge is about, and update it again. Keep a wide scope only when the Knowledge really covers it, and say so when you report. A replayed `idempotencyKey` returns no breadth.

Restoring an archived Knowledge (`status: "active"`) that an active successor supersedes returns `outcome: "rejected"` with `reason: "superseded_by_active"`. Do not retry it: update the successor instead, or leave the old record archived.

## Propose Knowledge candidates

When the user asks to organize or extract Knowledge from recorded work (整理 Knowledge 候選), use the project's open candidate request or create one, read its context, and submit only reusable, source-supported candidates, each naming its source Session and the part of the record that supports it. Skip one-off status and anything already in `existingKnowledge`, which also lists archived Knowledge and rejected candidates (flagged by `status`): do not revive those without new evidence. The context gives outcomes, decisions and nextSteps; read scope or verification with `work_get_session` (`view: "handoff"`) only when a candidate depends on them. An empty submission is fine. Submitted candidates may carry advisory `overlaps` (possible duplicate, overlaps archived, overlaps rejected); they change nothing, are stored with the candidate and shown to the user in the Web review, so mention them instead of resubmitting. Candidates are not Knowledge: tell the user how many you proposed and that they accept or reject them on the Knowledge page. Never record candidates as Knowledge yourself.

Candidate requests are created only when the user asks; never create one because the context mentions a backlog. When `pendingRequests.knowledgeBacklog` is present (`uncoveredSessions`, `highValueSessions`; it appears only without an open request, with at least five high-value Sessions, and a week after the last request), mention it to the user at most once in the conversation as an offer, for example "12 Sessions are not yet organized into Knowledge candidates, 7 of them with confirmed decisions; want me to organize them?", then continue the task. A request takes at most 10 Sessions, ranked by confirmed decisions, recovered verification, later work built on them and repeated reads rather than by recency only; a new request result reports `remaining` counts, so tell the user how many are still left instead of requesting again. A request listed in `pendingRequests.knowledgeCandidates` with `status: "failed"` (or `processing`) blocks a new request: resume it with `work_get_knowledge_candidate_context` instead of creating another.

## Update standing Knowledge pages

When the user asks to update the project's knowledge pages (更新知識頁), or `pendingRequests.knowledgePages` in the project context lists a page, read its context and assess its Sessions. Context Sessions are previews (the first outcomes, decisions, and open items); read a Session in full (`work_get_session`, view handoff) before relying on a detail they leave out. The context is mode `full` (empty page or explicit update request: recent Sessions for a complete rewrite) or `review` (only Sessions after the page's coverage, reason `new`, oldest first, plus changed cited sources, reason `source_changed`). `has_new_data` means 有新資料 to review, not an automatic rewrite request: if those Sessions do not change the page answer, call `work_mark_knowledge_page_checked` with the last Session you actually reviewed. This only advances the review cursor; it creates no version and does not clear an explicit update request or `needsReview`. Rewrite the whole page only when requested or when its answer needs a change. Treat `page.needsReview` and `page.reviewSections` as a required source check: reread each named Session and check the listed reason codes. If context summaries omit citation ids or review details, use `work_get_knowledge_page_context` for the full list. To answer a question rather than maintain the page, add `query` or `headings` for a focused read (matching sections in full, `otherSections` sizes for the rest, no Sessions); `match: "none"` means pick a heading from `otherSections`. When it returns `not_found`, retry with its `suggestedSlug` or one of `existingSlugs`; never request a new page to work around a typo or an id passed as the slug. A restored Session is not automatically verified; compare its current summary, workSummary, verification, and void state with the page before saving. Save with the `reviewToken` from the context read you wrote the page from. `version_conflict` means the page was saved after that read: read it again and apply your change to the current version; never drop the token to get past it. When the context is `truncated`, the Sessions it left out stay new after the save, so the next review continues from them. Every section cites the Sessions that support it; a part the Sessions do not answer is a section whose content is exactly 資料不足 with no sources. Drop facts later Sessions contradict, never invent plans or recommendations, and tell the user which page you updated or checked and that its versions are on the Knowledge page. When you finalize that work, pass the slugs in `maintainedKnowledgePages` so this Session does not count as new data for those pages. Context prompts pages on explicit update requests or source-review warnings immediately, and after at least three unreviewed Sessions have accumulated; a finalize result may include `knowledgePageMaintenanceHint` for the same ordered list.

### Page maintenance steps

- Choose the read by the request. To check a page and update what changed, read its context as it is (`review` for a written page). Request a page update, which switches the read to `full`, only when the user asks for a complete rewrite; a `full` read asks you to rewrite the whole page, not to add to it or mark it checked.
- When the context is `truncated`, expect more than one read: save (or mark checked) only what the Sessions you were shown support, read the context again for the Sessions it left out, and repeat until it shows no more `new` Sessions. Do not report the page as up to date while Sessions are left; the server keeps them new, so a save that claims them is wasted work.
- When the Sessions change nothing on the page, call `work_mark_knowledge_page_checked` with the last Session you reviewed instead of saving the same sections again.
