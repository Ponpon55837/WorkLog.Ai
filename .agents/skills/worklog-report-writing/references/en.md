# Clear English for work reports

Use this guide after reading the canonical evidence and reporting contract.

Apply principles inspired by ASD-STE100: use familiar words consistently, keep each sentence focused, state the actor and action, and put conditions before actions. Prefer “Run the checks after the build finishes” to “Verification should subsequently be undertaken.” Use the same technical name for the same object. Preserve API names, commands, quotations, and user-supplied titles.

Lead with the delivered behavior and its scope. Describe verification separately: say which check passed or failed, and which environment was used. Explain a material limit once. Keep pending, failed, not run, and unavailable evidence distinct. Use parallel headings and short paragraphs; do not split related facts into fragments merely to reduce sentence length.

Before: “The implementation was completed and the related implementation verification was completed, with coverage caveats repeated below.”

After: “The report now reads its saved source IDs in pages. The regression test retained three older sources after 205 newer records arrived. Sources that were voided remain unavailable.” Only use this example's numbers when the actual evidence supports them.

This is a project writing guide, not the complete ASD-STE100 rules or approved-word dictionary. For a request explicitly requiring formal STE, consult the current standard and approved technical vocabulary, and perform a separate compliance review. Do not claim compliance based on an AI rewrite or a sentence-length check.

Primary references: [ASD-STE100 background](https://www.asd-ste100.org/about_STE.html), [Issue 9](https://www.asd-ste100.org/assets/files/ASD-STE100_ISSUE9.pdf), [STE software guidance](https://www.asd-ste100.org/STEsoftware.html). The standard addresses English; do not apply its certification label to Chinese.
