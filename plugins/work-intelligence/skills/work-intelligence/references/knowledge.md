# Knowledge candidates, Knowledge pages, and recorded Knowledge

Read this guide with the core [Work Intelligence skill](../SKILL.md) when the user asks to extract Knowledge candidates, update the project's Knowledge pages, or record Knowledge, or when `pendingRequests.knowledgePages` in the context lists a page. The Knowledge candidate and Knowledge page contracts in the matching operation contracts apply as well.

## Git state and memory

Git is the source of truth for branch, commit, PR, and merge state. Knowledge pages do not record them; when asked, check Git live. Project facts already recorded in Knowledge or Knowledge pages are not copied into your own memory files; keep only a pointer (one fact, one place).

## Record Knowledge

Record only reusable, source-supported facts; do not turn guesses or an entire Session transcript into Knowledge. When recording, set the paths it applies to when they are clear, and name the older Knowledge it replaces instead of leaving both active.

## Check the scope of recorded Knowledge

`work_record_knowledge`, and `work_update_knowledge` when it changes `appliesTo` on an active Knowledge, return `appliesToBreadth`: `share` is the fraction of the project's newest Sessions that changed 1–20 files and touched `appliesTo`, `sessions` is how many were compared, and `truncated` means more exist. When `broad` is `true` (at least 10 Sessions and a share above 0.15), `warnings` asks you to narrow the scope. Then replace the wide entries (a whole folder or a broad glob) with the specific files or subdirectories the Knowledge is about, and update it again. Keep a wide scope only when the Knowledge really covers it, and say so when you report. A replayed `idempotencyKey` returns no breadth.

Restoring an archived Knowledge (`status: "active"`) that an active successor supersedes returns `outcome: "rejected"` with `reason: "superseded_by_active"`. Do not retry it: update the successor instead, or leave the old record archived.

## Propose Knowledge candidates

When the user asks to organize or extract Knowledge from recorded work (整理 Knowledge 候選), use the project's open candidate request or create one, read its context, and submit only reusable, source-supported candidates, each naming its source Session and the part of the record that supports it. Skip one-off status and anything already in `existingKnowledge`, which also lists archived Knowledge and rejected candidates (flagged by `status`): do not revive those without new evidence. The context gives outcomes, decisions and nextSteps; read scope or verification with `work_get_session` (`view: "handoff"`) only when a candidate depends on them. An empty submission is fine. Submitted candidates may carry advisory `overlaps` (possible duplicate, overlaps archived, overlaps rejected); they change nothing, are stored with the candidate and shown to the user in the Web review, so mention them instead of resubmitting. Candidates are not Knowledge: tell the user how many you proposed; they accept or reject them on the Knowledge page. Never record candidates as Knowledge yourself; only an Agent review request the user opened may accept them (agent-review guide).

Candidate requests are created only when the user asks; never create one because the context mentions a backlog. When `pendingRequests.knowledgeBacklog` is present (`uncoveredSessions`, `highValueSessions`; it appears only without an open request, with at least five high-value Sessions, and a week after the last request), mention it to the user at most once in the conversation as an offer, for example "12 Sessions are not yet organized into Knowledge candidates; want me to organize them?", then continue the task. A request takes at most 10 Sessions, ranked by confirmed decisions, recovered verification, later work built on them and repeated reads rather than by recency only; a new request result reports `remaining` counts, so tell the user how many are still left instead of requesting again. A request listed in `pendingRequests.knowledgeCandidates` with `status: "failed"` (or `processing`) blocks a new request: resume it with `work_get_knowledge_candidate_context` instead of creating another.

## Update standing Knowledge pages

When the user asks to update the project's knowledge pages (更新知識頁), or `pendingRequests.knowledgePages` lists a page, read its context and assess its Sessions. The context is mode `full` (empty page or explicit update request: recent Sessions for a complete rewrite) or `review` (Sessions after the page's coverage, oldest first, and changed cited sources, each once with `reasons` `new` and/or `source_changed`). `has_new_data` means 有新資料 to review, not an automatic rewrite request: if those Sessions do not change the page answer, call `work_mark_knowledge_page_checked` with the last Session you actually reviewed. This only advances the review cursor; it creates no version and does not clear an explicit update request or `needsReview`. Rewrite the whole page only when requested or when its answer needs a change; otherwise use a section update (below). Treat `page.needsReview` and `page.reviewSections` as a required source check: reread each named Session and check the listed reason codes. To answer a question rather than maintain the page, add `query` or `headings` for a focused read (matching sections in full, `otherSections` sizes for the rest, a `reviewToken`, no Sessions); `match: "none"` means pick a heading from `otherSections`. When it returns `not_found`, retry with its `suggestedSlug` or one of `existingSlugs`; never request a new page to work around a typo or an id passed as the slug. A restored Session is not automatically verified; compare its current summary, workSummary, verification, and void state with the page before saving. Save with the `reviewToken` from the context read you wrote the page from. `version_conflict` means the page was saved after that read: reapply your edits to the current version with the fresh `reviewToken` and `changedHeadings` it returns (Sessions read since stay new until marked checked); never drop the token to get past it. Every section cites the Sessions that support it (over 20, the newest are kept); a part the Sessions do not answer is a section whose content is exactly 資料不足 with no sources. Drop facts later Sessions contradict, never invent plans or recommendations, and tell the user which page you updated or checked. When you finalize that work, pass the slugs in `maintainedKnowledgePages` so this Session is not new data for them.

### Page maintenance steps

- Choose the read by the request. To check a written page and update what changed, prefer `reviewOnly: true` (below); read it as it is (`review`) to reassess the whole page. Request a page update (the read becomes `full`, a whole-page rewrite, not an addition or a checked mark) only when the user asks for a complete rewrite.
- When the context is `truncated`, expect more than one read: save (or mark checked) only what the Sessions you were shown support, read the context again for the Sessions it left out, and repeat until it shows no more `new` Sessions. Do not report the page as up to date while Sessions are left.
- To fix or add a few sections, save with `upsertSections` (a section with the same heading, ignoring case and surrounding spaces, is replaced in place, else appended) and/or `removeHeadings` instead of `sections`, with the read's `reviewToken`; other sections stay as stored. `section_not_found` and `page_limit_exceeded` (over 12 sections or 8,000 characters once merged) write nothing.
- Near the limits (11 sections or 7,200 characters), reads and saves add `size` and `splitSuggestion` (the largest `headings`; `page_limit_exceeded` carries it too). First remove what no longer answers the page question (finished items, overturned facts); never shorten still-true text. If it still does not fit, offer the user a custom page for those sections and, once they agree, request it, save them there and remove them here.
- A review-only read (`reviewOnly: true`, not with `query` or `headings`) returns only the sections that need review in full with `reasons` (a new Session maps to at most 3 sections whose sources it links to or shares a file with), previews of those Sessions, `otherSections` and `size` for the layout and room left, and `unmappedSessions` by title. Update those sections, add one for an unmapped Session only when it adds a topic, then mark checked through `checkedThroughCandidate`. `review: "none"`: nothing to do; `"full_rewrite"` or `"use_full_read"`: read without it; `truncated`: read again.
- A section update does not count new Sessions as covered or clear the user's update request. Pass `checkedThroughSessionId` (a reviewed, finished Session) to advance the cursor in the same save; else mark checked. Replaced and added sections lose `needsReview`; untouched ones keep it.
