# Handoff：2026-09-28 Claude Code → Codex（第七輪：Agent 脈絡的用量與準確度）

第六輪的功能都完成了。使用者請 Codex 以實際資料做了兩次使用測試。結論是：

- 查詢速度可以接受：單筆 0.56–0.86 秒。
- **回應太大**：token 成本比等待時間更值得處理。
- **排序會被舊內容干擾**。
- **查不到時沒有明確訊號**。
- **知識頁太快被標成過時**。

這一輪只處理這些問題。

1. **Agent 拿到的內容要更少、更準**：整份回應有預算、跨區去重、可以只取摘要。
2. **沒有答案時要說沒有**，不要回傳湊數的結果。
3. **已完成的工作排在舊規劃片段前面**。
4. **知識頁只在真的需要時要求更新**。

這是長任務，請依階段順序進行，每一項開獨立 PR。完成後使用者會再請 Claude 複檢。

> **使用者決定（維持不變）**：授權為 MIT。開機自動啟動、發行（tag／release／發行 workflow）、版本號升到 1.0.0，以及實機驗證，都等所有功能完成後再處理，這一輪不要做。

## 階段 A：回應用量（最優先）

### A1. 先量測，再訂上限

1. 新增一組固定的「用量基準」：
   - 使用合成資料，不要用使用者的資料庫。
   - 資料要能重現上面的情況：多筆 Session 引用同一段規劃內容、有知識頁、有任務相關的決策與陷阱。
   - 量測 `work_get_context`（有 `task` 與沒有 `task`）、`work_recall`（預設筆數）、`work_search`（預設筆數）的序列化大小。
2. 把量測結果寫進 `docs/testing.md`，當作本輪的基線。
3. 在 CI 加上大小上限。之後的項目只要讓回應變大，就會被擋下來。
4. 上限先用下面的目標。如果基線量測顯示目標不合理，在 PR 說明理由後調整：

   | 工具                            |    目標上限 |
   | ------------------------------- | ----------: |
   | `work_get_context`（有 `task`） | 12,000 字元 |
   | `work_recall`（5 筆）           |  3,500 字元 |
   | `work_search`（20 筆）          |  8,000 字元 |

5. 「變小」不能靠丟掉正確答案：檢索品質門檻必須維持通過。

### A2. `work_get_context`：跨區去重、整份預算、任務優先

**現況**：`context-recall-service.ts` 把近期 Session、近期決策、近期 Knowledge、任務相關結果與知識頁並列。各區有自己的筆數或字數上限，但是：

- 同一筆 Session 可能同時出現在「近期」與「相關」，內容重複。
- 沒有整份回應的上限。
- 知識頁依預設順序挑選（每頁 1,500 字、合計 4,500 字），不看這次的 `task`／`paths`。

**要做的**：

1. **跨區去重**：以 Session／Knowledge 的 id 辨識。同一筆只輸出一次主要內容，其他區塊只留 id 與命中理由。
2. **任務優先**：有 `task`／`paths` 時，預算先給相關的決策、陷阱、未結項與相關的知識頁段落，最後才是近況；沒有 `task` 時，維持有限的專案近況。
3. **整份預算**：
   - 在各區上限之外，再加一個整份回應的上限，數值取自 A1 的量測。
   - 來源 id、`possiblyStale`、矛盾標記、待處理請求一定保留，不能被預算擠掉。
4. **省略要看得出來**：
   - 回應帶 `omitted`：每區省略幾筆，以及用哪個工具讀完整內容（`work_get_session`、`work_get_knowledge_page_context` 等）。
   - 截斷的摘要在句子邊界結束並標示已截斷，不要切在字中間。
5. **驗收**：
   - 同一筆來源同時命中多區的案例，主要內容只出現一次。
   - 大量資料下，整份回應不超過上限，省略訊號與讀取入口仍然正確。
   - 過時、矛盾與「查不到」的情境，不會被近期記錄蓋掉。
   - 專案範圍限制不變。

### A3. `work_recall`／`work_search`：更精簡的結果

1. 每筆結果只保留判斷是否要讀全文所需的欄位：
   - id、標題、專案、日期、驗證狀態、命中欄位、最佳片段、`termHits`。
   - 片段長度要有上限。
   - 不要重複放同一段文字（例如摘要與片段相同）。
2. 預設筆數維持不變，改讓每筆變小。筆數的上限另外寫在工具說明中。
3. 需要完整內容時，照工具說明改用 `work_get_session`。
4. 改完後同步更新：
   - MCP 工具說明、`work-intelligence` skill、`docs/mcp-tools.md` 的欄位說明。
   - REST `/api/search`：Web 工作歷程的搜尋也使用這個 API，要確認 UI 仍顯示正確。

## 階段 B：檢索準確度

每一項都要先在 `retrieval-quality.test.ts` 加入會失敗的案例，再修正。

### B1. 查不到時明確說「資料不足」

**現況**：查詢「星際量子記憶加速器」仍回傳 5 筆無關結果。

**要做的**：

1. 定義「有意義的命中」：
   - 查詢詞中，有足夠比例的詞真的命中（沿用現有的 IDF 加權命中比例）。
   - 或者命中了查詢的檔案路徑。
2. 沒有任何結果達到門檻時，`hits` 回傳空陣列，並附上 `confidence: "none"`。
3. 只有少數結果勉強達到門檻時，附上 `confidence: "low"`；結果正常時是 `"high"`。
4. `work_get_context` 的任務相關區塊也照同樣的規則，查不到就明說。
5. 工具說明要告訴 Agent：`confidence` 是 `"none"` 時，不要把結果當成依據。
6. 案例：
   - 不存在的詞，回傳 0 筆與 `confidence: "none"`。
   - 精確關鍵字的既有案例，排名不變。
   - 只命中一個常見詞的查詢，是 `"low"`。

### B2. 已完成的工作排在舊規劃片段前面

**現況**：多筆 Session 的 raw handoff 引用同一段舊規劃內容，這段內容在每一筆 Session 都被計分一次；已完成的實作記錄反而排到後面。

**要做的**：

1. **重複片段只算一次**：
   - 建索引時，對 raw handoff 片段內容做正規化並算雜湊。
   - 同一專案內，同一片段只讓一筆 Session 取得完整分數，建議是最早引用的那一筆。
   - 其他 Session 引用同一片段時要降權。
   - 雜湊存在 `search_chunks`（新欄位要照 `worklog-backend` §4 處理，並通過 `project-data-coverage` 測試）。
2. **結構化欄位優先於 raw 片段**：
   - Session 的標題、摘要或 workSummary 命中時，排序要高於只有 raw 片段命中的 Session。
   - 調整 `FIELD_WEIGHTS` 或加成方式時，保留現有的分數組成說明（`search-repository.ts` 開頭的註解）。
3. 案例（使用合成資料，重現下面的情況）：
   - 自然語句「新增 REST endpoint 的慣例」：實作路由拆分的 Session 排第 1，舊規劃片段在後面。
   - 「FTS 效能問題」：已完成的修正記錄排在規劃片段前面。
4. 效能：索引重建與查詢的效能門檻維持通過。

## 階段 C：知識頁的更新判斷

**現況**：`knowledge-page-service.ts` 只要同專案出現 `completed_at > sourced_through` 的 Session，就把頁面標成 `needs_update`。因此：

- 無關的新工作也會要求所有頁面重寫。
- 「更新知識頁」這件工作自己的 Session，會讓剛存好的頁面馬上過時。
- 已引用的來源事後被更正或作廢，不會被發現。

### C1. 已引用的來源被更正、作廢或還原時，標示需要核對

1. 頁面每一段已經記錄來源 Session。以下情況，把頁面標成「需要核對」：
   - 來源 Session 在頁面保存之後被作廢或還原。
   - 來源 Session 的摘要、workSummary 或 verification 在頁面保存之後被修改。
   - 判斷依據用既有的 `updatedAt` 與作廢紀錄，不要新增逐筆查詢；照 `worklog-backend` §5 批次處理。
2. `work_get_context` 的知識頁摘要、`work_get_knowledge_page_context` 與 Web 的知識頁分頁，都要顯示受影響的段落、來源與原因。
3. 來源還原後重新判定，不要直接把舊內容當成已驗證。
4. 案例：
   - 作廢已引用的 Session，頁面立即顯示需要核對，不用等新 Session。
   - 修改沒有被引用的 Session，頁面狀態不變。

### C2. 新 Session 不再直接等於「需要更新」

1. **分開兩種狀態**：
   - 「需要核對」：來自 C1，一定要處理。
   - 「有新資料」：有尚未評估的新 Session，只是提示，不要求重寫。Web 與 `work_get_context` 用不同的標示。
2. **記錄已評估到哪裡**：
   - Agent 取得頁面 context 後，如果判斷新 Session 不影響結論，可以回報「已檢查、不需要改」。
   - 這時記下已評估到哪個時間點，頁面內容與版本不變。
   - 做法可以是 `work_save_knowledge_page` 的新選項，或是一個新的 MCP 工具。請在 PR 說明取捨。
   - 這個能力不能刪除或改寫既有版本。
3. **更新知識頁的工作不要讓頁面自己過時**：
   - 如果一筆 Session 只是在更新知識頁，而且保存頁面時已經把它算進來源範圍，它不應該再讓同一頁變成「有新資料」。
   - 判斷規則要寫進測試，不要依標題文字判斷。
4. 案例：
   - 存頁之後，完成一筆無關的 Session：頁面只顯示「有新資料」，不是「需要核對」。
   - Agent 回報已檢查：提示消失，版本不變。
   - 使用者的回饋情境（存成 v2 之後，更新頁面的 Session 與 PR #143）：不會出現需要重寫的標示。
5. Web：知識頁分頁的狀態標籤與篩選要跟著改。照 `worklog-ui` 的狀態顏色對應，並更新 E2E。

## 階段 D：其他

### D1. 跨專案情境的自動化測試

使用者的環境只有一個記錄中的專案，所以「另一個專案的 Agent 沒讀文件也能找到內容」只做了同專案模擬。請補一組 storage 測試：

1. 兩個記錄中的專案，外加一個暫停的專案。
2. 驗證 `work_get_context`／`work_recall` 只回傳該專案的內容。
3. 驗證不指定專案時，跨專案的結果正確標示專案。
4. 暫停專案的內容完全不出現。

### D2. Mermaid 在嚴格 CSP 下的 console 警告

D5 的圖表在 Web 正確顯示，但瀏覽器 console 仍有 CSP 警告（已知問題）。

1. 找出是哪一段 Mermaid 程式碼觸發（例如動態插入的 `<style>`、inline style 或字型量測）。
2. 在**不放寬主頁 CSP** 的前提下消除警告。
3. 如果不可能消除，在 `docs/troubleshooting.md` 寫明原因與影響。
4. E2E 的 Mermaid 測試要檢查 console 沒有 CSP 錯誤（或只剩文件記載的那一條）。

## 工作規則（重申）

- 繁體中文。
- 開工前讀對應的 skill：後端讀 `worklog-backend`；前端讀 `worklog-ui`＋`worklog-web-code-style`；Agent 工具的使用方式讀 `work-intelligence`；程式碼的擺放順序讀 `worklog-code-layout`。

- 每項開獨立 PR。CI 對應最新 commit 且全綠才合併；用 merge commit 合併並刪除分支。
- 健康檢查逐步確認：build、test、typecheck、coverage、效能、檢索品質、E2E。
- 效能：先量測再優化；新的讀取路徑都要有基準情境與上限。本輪的輸出大小也要有上限（A1）。

- 不修改使用者的實際資料庫、Agent 設定或全域 hook；暫緩項目維持不做。
- MCP 不提供任何刪除或改路徑的能力。
- 使用 pnpm，不使用 npm／npx。
