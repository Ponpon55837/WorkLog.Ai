# Work Intelligence 1.6.33 更新說明

日期：2026-11-13。應用程式與 plugin 版本為 1.6.33；資料庫 schema 維持 33，沒有 schema 變更，也不需要 migration。

## 摘要

這一版接續 1.6.32，依真實使用資料副本（6 個專案、650 筆 Session）的量測，處理三個問題，並修正 CLI、保存 hook 與 Git 讀取上的幾個缺陷。產品方向不變：有效沉澱 → 精準再利用 → 持續修正。

| 問題 | 量到的現象 | 這一版 |
| --- | --- | --- |
| Agent 沒有回報變更狀態 | 最近 101 筆 Claude Code Session 中，有 8 筆完全沒有變更狀態 | 保存時伺服器向 Git 查詢缺少狀態的路徑，並標示來源 |
| 只給任務描述時，綁檔案的 Knowledge 不會出現 | 因任務本身而顯示的 Knowledge 配對由 11 組增加到 60 組 | 只帶 `task` 時，依相似 Session 改過的檔案提供最多 3 筆推論指標 |
| 讀一頁 Knowledge 要讀整頁 | 完整讀取中位數 14,648 字 | 可依查詢或標題只讀需要的段落 |

資料內容沒有進入 repository；以下數字都是彙總計數。

## 伺服器補上變更狀態

Agent 有時會在 `changedFiles` 中列出路徑，卻沒有為這些路徑填入 `changedFileChanges`（`added`、`modified`、`deleted`，或帶 `previousPath` 的 `renamed`）。保存時，伺服器會向 Git 查詢這些路徑的狀態，並以 `changedFileChangesSource: { serverObservedGit: <數量> }` 標示。Agent 已回報的狀態一律優先，伺服器不猜測。

- 只在 tracked 專案、呼叫沒有 `completedAt`，而且不是同一個 `idempotencyKey` 的重試時才查詢。補登已完成的工作時，目前的工作樹已不代表那個時間，所以不查。
- 比較的基準是這段工作第一次 MCP 呼叫抵達時，伺服器看到的 HEAD commit；若該 commit 已不是目前 HEAD 的祖先，改用目前 HEAD。未追蹤或新增的檔案記為 `added`，內容改變為 `modified`，已移除為 `deleted`；Git 偵測到的改名記為 `renamed` 並帶 `previousPath`。
- 整批最多執行 3 個 Git 行程，不經過 shell，每個 1.5 秒逾時，並在資料庫寫入鎖之前執行。繼承來的 `GIT_*` 環境變數會被忽略，這些呼叫也停用 fsmonitor。
- 每個由伺服器補上的狀態都會在 Session 上留下一筆 `note` 事件（`field` 為 `changedFileChanges`、`source` 為 `server_observed_git`，並記錄 `base` 與 `paths`）。
- Git 沒有回報的路徑不給狀態。回條會附 `changedFileChangesFollowUp` 與 `suggestedCall`，請 Agent 以 `work_update_session_metadata` 加上 `changedFilesMode: "merge"` 補回。Git 查詢失敗（沒有 git、不是 Git repository、逾時）只會略過這次觀察，保存仍會成功。

`work_update_session_metadata` 的 `changedFileChanges` 採用與 `changedFiles` 相同的合併規則。`merge` 時，同一路徑的新狀態會取代舊狀態，改名會取代其 `previousPath` 的既有項目，因此修正後不會同一路徑留下兩種狀態。`replace` 時若帶了 `changedFiles` 卻沒有 `changedFileChanges`，只保留仍在清單中的既有狀態。

Claude Code 的開始時間暫停（PreToolUse）同時會請 Agent 依真實 diff 補上各檔案的狀態。只缺狀態時不會單獨暫停，hook 也不讀取 Git。

在真實資料副本上，Git 推得的狀態與 Agent 回報的狀態在 3,312 個檔案中有 3,299 個一致（99.6%），211 個缺少狀態的路徑都能由 Git 補上。

## 只給任務時的 Knowledge 指標

`work_get_context` 只帶 `task`、不帶 `paths` 時，會依相似 Session 改過的檔案，找出可能相關的 Knowledge，放在 `relevant.supplements`，最多 3 筆，`includedBecause.kind` 為 `inferred_path`。

- 相似 Session 取相關 Session 中最相似的前五筆。改動超過 20 個檔案的 Session（可能是髒的工作樹）不計入。
- 只收 `appliesTo` 或 references 涵蓋這些檔案、而且至少兩筆不同的相似 Session 都支持的 active Knowledge。
- 指標只包含推論出的檔案（`path`）與最多兩筆來源 Session（`sourceSessionIds`）。它的意思是「由相似工作推論」，不是證據；引用前要用 `work_search_knowledge` 依標題讀取原文。
- 只使用回應的剩餘空間。為了容納指標，`recentKnowledge` 中沒有被這批檔案命中的項目會先縮成只剩標題，仍放不下才移除；命中的項目改以指標出現。`relevant.*` 的內容、順序與上限都不變，整份回應仍不超過 9,800 字。
- 帶 `paths`，或沒有 `task` 的呼叫，回應與功能關閉時完全相同。

真實資料回放（273 筆只帶 `task` 的回應，221 組 Knowledge／任務配對）的結果如下：

| 項目 | 數值 |
| --- | --- |
| 因任務本身而顯示的配對（不計只靠 `recentKnowledge` 出現的） | 由 11 組增加到 60 組 |
| 推論指標 | 69 個，其中 49 個是預定的 Knowledge（71%） |
| 出現在沒有適用 Knowledge 的任務上的指標 | 8 個 |
| 原本顯示的內容遺失 | 0 |
| 最大回應長度 | 9,799 字（上限 9,800） |

研究前的基線把 109 組寬鬆命中算成顯示，但其中 98 組只出現在最近 12 筆的 `recentKnowledge` 清單，與任務無關。因此上表只計「因任務本身而顯示」的 11 組作為基線。

效能：5,000 筆合成 Session 上，只帶 `task` 的 `work_get_context` 中位數 55 ms、p90 62 ms（含推論，門檻 250 ms）。壓力情境（2,000 筆 Knowledge、每筆 10 個 glob、100 個檔案）為 62 ms。

## Knowledge 頁聚焦讀取

`work_get_knowledge_page_context` 新增 `query`（最多 200 字）與 `headings`（最多 12 個，來自 `relevant.knowledgePages` 或上一次回傳的 `otherSections`，去除空白後不分大小寫比對）。

- 帶任一參數即為聚焦讀取：只回符合段落的全文（`heading`、`content`、`sourceSessionIds`），附頁面層級的 `slug`、`title`、`version`、`status`、`newSessionCount`、`updatedAt` 與旗標；其餘段落以 `otherSections`（標題與字數，依頁面順序）列出；不回 Session 清單，並標示 `sessionsOmitted: true`。
- `query` 使用搜尋的斷詞比對：詞彙要整個符合一個詞元，或在拉丁字母至少 4 個字元時符合詞元的前綴。
- 沒有符合的段落時 `match` 為 `none`，從 `otherSections` 挑選標題再呼叫一次即可。要整頁改寫或核對時，不帶 `query` 與 `headings` 即可取得原本的完整讀取（含 Session 清單）。

真實頁面的完整讀取中位數 14,648 字（最大 30,705 字）；依標題聚焦中位數 1,334 字（最大 2,927 字）；依查詢聚焦中位數 1,437 字（最大 5,357 字）。

`work_get_context` 的 `relevant.knowledgePages` 段落原本只取前 500 字，現在改以符合的詞為中心擷取，超出字數上限時以同樣方式縮短至 240 字。

## 搜尋提示

`work_search_knowledge` 帶 `q` 且嚴格搜尋沒有結果時，回應會附上以下欄位：

- `otherStatusFullMatches`：其他狀態中包含全部詞的筆數。改傳該 `status` 會得到嚴格結果。只出現在 `otherStatusMatches` 的狀態只有部分符合，`hint` 會分別說明。
- `effectiveQuery`：嚴格搜尋截斷查詢時出現（超過 8 個詞，或單詞過長）。它是計數與改傳 `status` 重查時實際使用的查詢，可原樣重送。
- `queryTruncated`：寬鬆排序達到詞元或路徑詞的上限時出現。

## CLI、匯入與 Git 讀取

- `pnpm db:export --help` 不再把 `--help` 當成輸出路徑，寫出完整快照。指令在碰資料庫或檔案系統之前先檢查參數：`--help` 與 `-h` 印出該子指令的用法並以 0 結束；未宣告的選項，或值看起來像選項的參數（例如 `--out --foo`），會把錯誤與用法印到 stderr，並以非零結束。`db:backup` 拒絕多餘的參數，未知的指令印到 stderr。
- 匯入專案時，根目錄以其他寫入者與查詢共同使用的規範化 key 儲存。在 Windows 上，大小寫不同的資料夾匯入後，要等下次啟動修復才會被找到，現在不會。在目前平台不是絕對路徑的根目錄（例如從 Linux 匯入的 Windows 路徑）原樣保留，預覽仍顯示原本的拼法。
- 分支與 HEAD commit 現在也能在 linked worktree（`.git` 是檔案）與 packed refs 下讀取。一般情況仍由 loose `.git` 檔案直接讀取，不啟動子行程；只有讀不到時才詢問 Git，而且只對本身就是 checkout 的根目錄詢問。

## 保存 hook 修正

- Claude Code 的 hook 忽略失敗的 `Edit`、`Write`、`MultiEdit` 與 `NotebookEdit`，工具結果標示錯誤者不算改動。
- 根目錄互相巢狀時，以最具體（最深）的 tracked 專案根目錄判斷。

## 實驗與測試

- `docs/experiments/task-path-replay.mjs` 改為唯讀：`--db` 與 `--project` 指定資料庫與專案，`--self-check` 以虛構資料庫自我檢查，只輸出彙總 JSON。說明見 [task-path-replay.md](../experiments/task-path-replay.md)。
- `pnpm test:start-smoke`（`scripts/smoke-start.mjs`）以暫存資料庫啟動真正的 `pnpm start` 入口，檢查 `/api/health` 與 Web UI，並確認 SIGTERM 後程序結束、連接埠已釋放。CI 在每個 OS 的 Quality job 建置後執行。

## 未驗證與已知限制

- Claude Code 的變更狀態流程以真實 `claude` CLI 驗證了四個情境。Codex 沒有可用的 CLI，沒有以真實用戶端驗證。
- Windows 專屬的行為（E2E 修正中的路徑處理、CLI 參數、匯入根目錄）沒有在真實 Windows 上執行。
- Agent 是否實際讀取或使用推論指標沒有量測。只有一個專案的資料足夠量測，而且指標出現在回應中不代表 Agent 用了它。
- Claude Code 的 hook 只計 `Edit`、`Write`、`MultiEdit` 與 `NotebookEdit` 造成的改動；Bash 指令造成的改動看不到。
- 20,000 筆合成 Session 上，只帶 `task` 的 `work_get_context` p90 約 263 ms，有無推論都一樣。這是既有的成本，這一版沒有處理。

## 升級

1. 取得 1.6.33 原始碼後，依 [1.6.32 更新說明](1.6.32.md)的步驟建置與檢查。已安裝登入自動啟動服務者執行 `pnpm service:restart`，確認輸出「服務已在執行 1.6.33」。
2. Agent 重新連線一次，才看得到更新後的操作與工具說明。
3. 沒有 schema 變更（33），匯出檔與既有資料不受影響。
