# Work Intelligence 1.6.25 更新說明

日期：2026-11-12。應用程式與 plugin 版本為 1.6.25；資料庫 schema 維持 33，不需要 migration。

## MCP 在資料庫被鎖定時啟動

以前每次開啟資料庫都會取得寫入鎖並執行 schema 語句，即使沒有任何 migration。另一個行程（另一個 Agent 的 MCP、`pnpm db:*` 命令）持有寫入鎖 9 秒時，MCP 等了 5.3 秒，然後對每個 tool 呼叫回報 `DATABASE_MIGRATION_FAILED`，要使用者「從備份還原」；資料庫其實是最新的，而且鎖釋放 9 秒後仍然回報同一個錯誤，因為啟動失敗會保留到行程結束。叫 Agent 在沒有問題時從備份還原，本身就是資料風險。

現在：

- 已是最新 schema（版本、基本資料表與索引齊全、WAL 模式）的資料庫，開啟時只讀取，不需要寫入鎖。同樣的情境下 MCP 0.3 秒啟動，鎖定期間與之後都能讀取。
- 需要 migration 時，先取得並釋放一次寫入鎖，再寫 migration 前備份。鎖被占用時回傳 `DATABASE_BUSY`，不會每次重試都寫出一份備份；釋放後正常備份並升級。migration 前備份與「schema 比程式新」的拒絕維持不變。
- 因忙碌、唯讀或磁碟已滿而無法開啟時，下一次 tool 呼叫會再試一次開啟（每次呼叫最多一次，兩次嘗試至少間隔 1 秒），成功後照常服務，不必重新連線。schema 過新、版本資訊無效、備份或 migration 失敗、檔案無法開啟仍會保留到重新啟動，需要使用者處理。
- REST server 啟動同樣受惠：資料庫是最新的就不需要寫入鎖，忙碌時顯示忙碌訊息而不是 migration 失敗。

## 唯讀與磁碟已滿有自己的代碼

以前對唯讀資料庫的寫入，MCP 回傳 SQLite 原文「attempt to write a readonly database」（沒有代碼，也不是 JSON），REST 回傳一般的 500，Web 無法告訴使用者原因。現在：

| 情況 | MCP | REST |
| --- | --- | --- |
| 另一個行程正在寫入 | `DATABASE_BUSY` | 503 `database_busy` |
| 檔案、資料夾或磁碟唯讀 | `DATABASE_READ_ONLY` | 503 `database_read_only` |
| 磁碟空間不足 | `DATABASE_DISK_FULL` | 507 `database_disk_full` |

回應沿用既有的 `{ code, error }` 形狀，`error` 是固定文字，不含 SQL、SQLite 訊息或路徑；Web 依代碼顯示繁體中文或英文訊息。三種情況都表示這次寫入沒有保存、已保存的資料沒有變更，不需要從備份還原。唯讀時讀取照常可用。專案與 Session 永久刪除遇到這三種情況，也回傳對應代碼，不再誤報為備份失敗或刪除失敗。磁碟已滿無法在測試中可攜地重現，以建構的錯誤驗證分類。處理方式見[疑難排解](../troubleshooting.md#資料庫忙碌唯讀或磁碟已滿)。

## REST 拒絕未知欄位

35 個寫入 schema 會默默丟掉未知欄位，例如 `PATCH /api/sessions/:id/title` 帶 `{"title":"x","extra":1}` 回傳 200，打錯的欄位就這樣消失。MCP 早已拒絕未知參數。現在每個 REST body，以及整組送進 schema 的查詢參數，都在 REST 層以嚴格模式驗證：未知欄位（包含巢狀物件內的）回 400 `invalid_input`，`details` 點名每個欄位。共用 schema 沒有改變，MCP 行為不變。

先盤點了 Web client 與 E2E 測試送出的內容：Web 沒有多送欄位；一個 E2E fixture 對標題路由多送了 `idempotencyKey`，已修正。新的測試對每個寫入路由送出未知欄位並要求 400；沒有 body 的路由必須列在測試內並寫明原因，所有路由也必須經同一個嚴格解析函式驗證。

## 列表載入失敗時不再說「還沒有紀錄」

API 失敗（中斷或 500）時，工作歷程頁同時顯示錯誤與「還沒有工作紀錄」，後者不是事實。工作知識、專案、總覽、工作圖譜與工作報告也有同樣情形。現在列表在第一次載入成功之前不顯示空狀態，只顯示錯誤；工作歷程另有自己的錯誤訊息與可用的重試。

## 文件與實作一致

`docs/mcp-tools.md` 補上原本沒提到的 8 個 operation（metadata 回補的查詢、context、套用與取消，報告提煉的查詢、取消與摘要保存，以及報告匯出），並說明資料庫錯誤與啟動失敗的處理；`docs/rest-api.md` 補上 Agent 決策審核、handoff 匯入與其他遺漏的路由，以及未知欄位與新錯誤代碼。新的一致性測試在已註冊的 operation 或路由沒有文件、或文件提到不存在的名稱時失敗。

## 相依套件

`pnpm audit --prod` 原本有 6 個低／中風險通報，都在 MCP SDK 之下（fast-uri、qs、ip-address）。SDK 1.32.2 的相依範圍沒有改變，所以只在既有範圍內更新 lockfile：fast-uri 3.1.9、qs 6.17.1、ip-address 10.7.6，不需要 overrides。之後 `--audit-level high`、`moderate`、`low` 都沒有通報。開發用相依（vitest 底下的 vite、minimatch）仍有通報，不影響執行。`lucide-vue-next` 已被上游標為淘汰，替代套件是 `@lucide/vue`，本版沒有更換。

## 修正

- `pnpm db:maintain` 遇到不是 SQLite 資料庫的檔案時，回報「資料庫使用中，請停止 server」；現在回報 `DATABASE_INVALID`，且不修改檔案。
- handoff 匯入預覽遇到無法讀取的檔案時，顯示檔案系統訊息（含絕對路徑）；現在顯示固定文字與專案內相對路徑。
- 專案刪除、資料庫維護與 handoff 掃描補上錯誤路徑測試：找不到專案、名稱不符、備份目錄不可用、寫入鎖被占用、唯讀資料庫、非 SQLite 檔案、完整性檢查失敗、schema 過新、排除檔案不讀取、`maxFiles` 上限、超出專案根目錄的路徑與符號連結，每種都確認資料沒有被改動。

## 未納入

- 只讀取指定名稱的 GET 查詢參數，不會拒絕其他參數。
- MCP 未分類的錯誤仍由 SDK 回傳原始訊息。

## 升級

1. 取得 1.6.25 原始碼後執行 pnpm bootstrap（或 pnpm install --frozen-lockfile、pnpm build 與 pnpm check）。
2. 若已安裝登入自動啟動服務，執行 pnpm service:restart，確認輸出「服務已在執行 1.6.25」。
3. 透過 launcher 連線的 Agent 會自動切換到新版，不需要重新連線；只有 Agent 回報 `restartRequired` 時才重新連線一次。
