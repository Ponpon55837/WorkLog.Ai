# Work Intelligence 1.6.52 更新說明

日期：2026-11-17。應用程式與 plugin 版本為 1.6.52。資料庫 schema 仍為 33，沒有 schema 變更，不需要 migration。

## 摘要

本版補上資料庫升級與還原的驗證，並加入多程序寫入的壓力測試：

- migration 前備份與 N→N+1 樣本升級測試（DT-32），包含中斷與還原；
- 多程序 WAL 寫入與 checkpoint 壓力測試（DT-07），`pnpm test:sqlite-stress`；
- 還原前先驗證遷移後的副本（產品變更）：驗證失敗時現行資料庫不被取代。

CI 可驗證的部分已實作。Windows 11 與 macOS 的實機驗收尚未進行，仍為**待實機驗收**。CI 結果待 PR 檢查完成後補上。

### 樣本升級、中斷與還原（DT-32）

- **舊版樣本**：三份由真實建置產生的升級樣本（`tests/fixtures/upgrade`），分別來自 v1.6.8（schema 31）、v1.6.21（schema 32）與 1.6.51（schema 33）。內容是合成資料，以 `node scripts/generate-upgrade-fixtures.mjs` 手動重新產生，不在 CI 執行。v1.6.8 早於私人區塊（private blocks）。
- **升級測試**（`tests/storage/upgrade-samples.test.ts`）：每份樣本都以真實的 store 升級，並檢查：
  - 升級前的備份與樣本相同，且只有一份；
  - `integrity_check`、外鍵與 FTS 都正常；
  - 原有的資料列與舊欄位不變，新增欄位為 NULL；
  - 搜尋可用；
  - 私人文字不會出現在升級後的資料中；
  - 第二次開啟不做任何事。
- **規則**：新增 migration 時必須附上前一個 schema 的樣本。守護測試失敗時會指出要執行的指令。
- **中斷測試**（`tests/storage/migration-interruption.test.ts`）以真實程序執行：
  - 在 migration 交易中途強制結束：資料庫維持舊版且完整，備份完整，下次開啟時只升級一次；
  - 在 migration 前備份途中強制結束：不會發布不完整的備份，下次開啟時清除 staging；
  - 20 次隨機時間點的強制結束（種子會印出，時間有上限）：結果永遠是全部舊版或全部新版；
  - 從 migration 前的備份還原：之後寫入的資料列會被捨棄，並保留一份安全快照；
  - 還原途中強制結束：現行資料庫不變。
- **桌面 smoke**（`apps/desktop/tests/desktop-smoke/migration-interruption.spec.ts`）：migration 開始後後端被強制結束，App 進入 `NEEDS_REPAIR`，操作日誌記錄 `migrationStarted` 與只能修復（repair-only），之後不會回到舊的（EXTERNAL）服務；下一次修復只升級一次。測試用的切換開關只存在於測試建置（`__WI_TEST_BUILD__ && !isPackaged`），正式版的打包檢查會禁止它。 讓後端在開啟資料庫前停住的測試 hold 只存在於 smoke 用的 runtime（`--desktop-test-build`，esbuild define `__WI_DESKTOP_TEST_BUILD__`）；打包 App 內建的 runtime 沒有這段程式碼與變數名稱，並由 `check-production-bundle.mjs --runtime` 檢查。

### 還原前驗證遷移後的副本（產品變更）

- 還原時，備份會先遷移到暫存副本，並對副本執行 `quick_check` 與 `foreign_key_check`，通過後才取代現行資料庫。
- 驗證失敗時回傳新的錯誤代碼 `RESTORE_VERIFY_FAILED`。現行資料庫不變，暫存副本會被移除。
- 適用 CLI 的 `pnpm db:restore`。桌面 App 目前還沒有還原流程。

### 多程序 WAL 寫入與 checkpoint 壓力（DT-07）

- **指令**：`pnpm test:sqlite-stress`，不屬於 `pnpm test`。測試檔為 `tests/stress/sqlite-wal-stress.test.ts`。
- **負載**（45 秒）：
  - 4 個寫入程序，透過真實的 store；
  - 2 個唯讀程序，其中一個持有長時間的讀取交易；
  - 一個 checkpointer，循環執行 PASSIVE、FULL、RESTART、TRUNCATE；
  - 一個以 `VACUUM INTO` 製作快照的程序；
  - 隨機以 SIGKILL 結束部分寫入程序。
- **絕對檢查**：`integrity_check` 與 `foreign_key_check` 通過；FTS5 完整性通過；每筆已確認的寫入恰好存在一次；被中斷的寫入全部成功或全部不存在；快照都是無缺口的前綴；還原的快照與來源指紋相同。
- **SQLITE_BUSY**：只計入實際拋給呼叫端的 BUSY（等滿 5 秒 `busy_timeout` 仍失敗）。寫入程序合計不得超過 `max(5, ceil(寫入數 × 2%))`（最低 5 次，短時間的執行因此不會被少數幾次擋下）；讀取程序、checkpointer 與 snapshotter 必須是 0。`PRAGMA wal_checkpoint` 回傳的 `busy` 旗標仍只回報、不設門檻。結果檔 `perf-results/sqlite-stress-<系統>.json` 的 `busyGate` 記錄每個系統的實際數字與套用的上限（`writerLimit`、`writerBusy`、`writerOps`、`passed`），之後可依資料調整；未通過時結果檔仍會先寫出再讓測試失敗。打包 smoke 的 6 秒壓力測試套用同一個門檻（下限 5 次涵蓋短時間的執行）。
- **CI**：新增 `SQLite stress (ubuntu-latest)`、`SQLite stress (windows-latest)` 與 `SQLite stress (macos-latest)` 三個工作。必要的 CI 檢查由 20 項增為 23 項。
- **量測**（CI，每個系統各跑一次 45 秒）：

| 系統 | SQLite | 寫入數 | 寫入速率 | 寫入程序 BUSY |
| --- | --- | --- | --- | --- |
| Linux | 3.53.4 | 1580 | 35.1/s | 1 |
| Windows | 3.53.4 | 488 | 10.8/s | 3 |
| macOS arm64 | 3.54.1 | 1878 | 41.7/s | 1 |

讀取程序、checkpointer 與 snapshotter 的 BUSY 皆為 0；FULL、RESTART、TRUNCATE checkpoint 都能完成。

- **不取代修補證據**：這個測試不取代 SQLite WAL-reset 修補的證據（DT-06、ADR-19）。

### 打包版的 SQLite 執行期檢查

- 打包 smoke 會執行已安裝 App 內建的 `launcher --print-runtime-info`，並斷言使用的是含 WAL-reset 修補與 FTS5 的真實 Node。
- 記錄（Node 與 SQLite 版本、修補狀態、FTS5）寫入打包結果。同一次打包 smoke 會以內建 runtime 執行 6 秒的壓力測試。
- 「Storage (Node 26)」CI 工作現在也會執行 `check-sqlite-version`。
- 本機量測的 Linux 打包 runtime：Node 24.22.3，SQLite 3.54.1。
- Windows x64、macOS x64、macOS arm64 的打包 runtime 皆為 Node 24.22.3、SQLite 3.54.1（含修補）；6 秒壓力測試全部通過，每個 OS 的總時間 14.0／16.7／11.9 秒（PR #374 CI）。

## 變更

- **還原**：驗證遷移後的副本才取代現行資料庫；新的錯誤代碼 `RESTORE_VERIFY_FAILED`。
- **測試**：新增 `pnpm test:sqlite-stress`、三個 SQLite stress CI 工作與升級樣本守護測試；必要的 CI 檢查增為 23 項。
- **CI**：「Storage (Node 26)」工作加入 `check-sqlite-version`。
- **Schema**：沒有變更（33）。
