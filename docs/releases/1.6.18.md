# Work Intelligence 1.6.18 更新說明

日期：2026-11-12。應用程式與 plugin 版本為 1.6.18；資料庫 schema 維持 32，不需要 migration。

## 安全性：appliesTo glob 不再回溯

Knowledge 的 `appliesTo` 可以寫成 glob（`*`、`**`、`?`）。舊的比對方式把 glob 轉成正規表示式，每個星號都成為可回溯的群組；1.6.16 與 1.6.17 起，這些儲存的樣式會拿來比對呼叫端提供的路徑（`work_get_file_history` 的 `paths`，以及寬鬆 Knowledge 搜尋中查詢裡像路徑的詞）。由大量星號組成的樣式對 60 字元的路徑就要數秒，到 500 字元的路徑上限時，單執行緒的 MCP 與 API 程序會停住，所有連線都受影響；這種樣式也可能經由專案匯入進入資料庫。

新的比對器同時追蹤樣式的所有位置，成本最多是「樣式長度 × 路徑長度」，不會指數成長。比對結果與舊版完全相同：測試以舊的正規表示式為基準，比對一般樣式的對照表與 2,000 組產生的大量星號樣式。同一個大量星號樣式對三個 500 字元路徑現在遠低於 1 ms（效能測試門檻 20 ms）。另外，寬鬆 Knowledge 搜尋最多使用查詢中 5 個像路徑的詞，每次 `appliesTo` 掃描（寬鬆 Knowledge 搜尋、檔案歷史）最多讀最新的 2,000 筆 Knowledge，沒有以 `projectRoot` 限定範圍時成本仍有上限。

## Session 讀取：預設改用精簡的 handoff 投影

`work_get_session` 占 Agent 讀取的近一半。以實際資料（328 筆 Session）量測，完整讀取中 `changedFiles`、`changedFilesProvenance`、`changedFileChanges` 三份清單重複列出相同路徑，平均約 3,000 字、占回應四成。完整讀取的形狀維持不變（REST 與 Web 也使用它），改為讓 Agent 預設走精簡路徑：

- 新增投影欄位 `session.files`：每個路徑只列一次，附 `status`、`previousPath`、`sources` 與 `references`，依 changedFiles 順序。`view: "handoff"` 現在包含它。
- 伺服器指示、`work_get_session` 的契約與 work-intelligence skill 都改為預設使用 `view: "handoff"`，只有需要原始 provenance、events、evidence、Knowledge 或 diagrams 時才完整讀取。`work_get_file_history` 在 `readWith` 旁回傳 `readArguments: { view: "handoff" }`。

20 筆抽樣 Session：

| | 完整讀取 | handoff 投影 |
| --- | --- | --- |
| 合計 | 150,728 字 | 95,720 字 |
| 中位數 | 6,907 字 | 4,021 字 |
| p95 | 18,909 字 | 12,922 字 |

合併後的檔案清單平均 1,861 字，原本三份清單平均 2,977 字。

## 帶 task 的 context：省下的預算留給 Session

帶 task 的 `work_get_context` 上限 9,800 字，實際五個 task context 都已用滿：相關未結項每筆都帶來源 Session 的標題與日期，同一個 Session 的多條決策也重複這兩項，結果只放得下 1–2 筆相關 Session。現在：

- `relevant.outstandingItems` 每筆只有 `id`、`sourceSessionId` 與最多 240 字的文字摘錄；來源標題在 `relevant.sessions` 或讀一次 `work_get_session` 即可取得。finalize 的 `relatedOutstandingItems` 不變。
- `relevant.decisions` 中同一個 Session 的決策連續排列，只有第一條帶 `sessionTitle` 與 `completedAt`。

| task context | 未結項（前→後） | 決策（前→後） | 相關 Session 數 | 一跳補充 |
| --- | --- | --- | --- | --- |
| 1 | 1,709 → 1,141 字 | 2,119 → 1,689 字 | 1 → 3 | 無（現在保留省略指標） |
| 2 | 1,541 → 1,006 字 | 2,375 → 1,797 字 | 2 → 3 | 無 |
| 3 | 1,628 → 1,073 字 | 2,753 → 2,038 字 | 1 → 2 | 無 → 1 筆 |
| 4 | 1,534 → 960 字 | 2,636 → 1,996 字 | 1 → 3 | 無 |
| 5 | 1,630 → 1,098 字 | 1,663 → 1,407 字 | 2 → 3 | 2 筆 → 2 筆 |

原本有兩個 context 連補充的省略指標都放不下，現在五個都有。既有的保證（必要 metadata、排序、省略指標）不變。

## Knowledge 候選：看得到已經決定過的事

`work_get_knowledge_candidate_context` 原本只列 active Knowledge 的標題，Agent 看不出某個主題已經封存，或相關候選已被拒絕。現在 `existingKnowledge` 依新到舊列出 active Knowledge（最多 150 筆）、archived Knowledge（`status: "archived"`，最多 30 筆）與已拒絕的候選（`status: "rejected"`，最多 20 筆），只有 id、kind 與標題，超出上限的數量為 `existingKnowledgeOmitted`。為了不讓回應變大，來源 Session 只附 workSummary 的 outcomes、decisions 與 nextSteps；scope 與 verification 列在 `omittedWorkSummarySections`，需要時用 `work_get_session` 讀取。實際資料中 context 由 19,625 字降到 17,910 字，列出的標題由 31 個增為 69 個。

`work_submit_knowledge_candidates` 送出後，每筆候選若與同專案的記錄相似，會附參考用的 `overlaps`（最多 3 筆）：與 active Knowledge 或仍待審的候選相似為 `possible_duplicate`，與 archived Knowledge 相似為 `overlaps_archived`，與已拒絕的候選相似為 `overlaps_rejected`，附對象 id、標題、狀態與分數。分數是標題與「標題＋內文」兩組檢索詞元的 overlap coefficient 各占一半，0.3 以上才列出。以實際資料的 72 筆 Knowledge 與候選逐一模擬送出，只標出已知的那一組近似重複（0.33），沒有誤報；其次最高的無關組合是 0.23。

這只是提示：不會拒絕、合併、封存或修改任何資料，只比對同專案、在這次送出前已存在的記錄，由使用者在 Web 決定。對已完成的請求再次送出完全相同的內容時，回傳原本保存的候選、相同的提示與 `duplicate: true`，不會新增候選。

## 未納入

- Web 的候選審核畫面不顯示重疊提示：保存提示需要新欄位與 migration，這一版不做。
- `work_get_context` 的省略指標沒有附建議參數：context 預算已用滿，改由指引說明以 handoff 讀取 Session。
- 完整讀取 `work_get_session` 的形狀不變，未移除重複的檔案清單。

## 升級

1. 取得 1.6.18 原始碼後執行 pnpm bootstrap（或 pnpm install --frozen-lockfile、pnpm build 與 pnpm check）。
2. 若已安裝登入自動啟動服務，執行 pnpm service:restart，確認輸出「服務已在執行 1.6.18」。
3. 透過 launcher 連線的 Agent 會自動切換到新版並收到工具清單更新通知，不需要重新連線；只有 Agent 回報 `restartRequired` 時才重新連線一次。

完整流程見發行與升級指南（docs/release.md）。
