# Work Intelligence 1.6.39 更新說明

日期：2026-11-15。應用程式與 plugin 版本為 1.6.39；資料庫 schema 維持 33，沒有 schema 變更，也不需要 migration。

## 摘要

這一版調整 Knowledge 的「可能過時」判斷，並讓檢索結果說清楚找到多少 Knowledge。兩件事的依據是一次可行性研究，研究的數字來自單一專案的私有副本，於研究時量測，不是本版的實測。完整研究見 [可行性研究](../experiments/retrieval-trust-feasibility-2026-11-15.md)。

| 問題 | 研究時的量測 | 這一版 |
| --- | --- | --- |
| 大範圍改動把 Knowledge 標為過時 | 有 appliesTo 的 active Knowledge 中 22／35（63%）可能過時；排除超過 20 檔的 Session 後降為 6（17%） | 超過 20 檔的後續 Session 不單獨觸發 `possiblyStale`，改計入 `broadChangesSince` |
| 寬範圍的 appliesTo 讓標記失去意義 | 被 10 個以上後續 Session 觸發的 9 則，appliesTo 寬度中位數 0.223，沒有一則低於 0.05 | `possiblyStale` 附上原因與寬度；寫入太寬的 appliesTo 時提示縮小範圍 |
| getContext 的 confidence 容易被誤讀 | 50 次中 41 次沒有 Knowledge，`relevant.confidence` 卻都是 high | 分開回報 `knowledgeConfidence`；沒有命中 Knowledge 時附 `knowledgeHint` |

## 這一版修正什麼

- `termHits` 不再誤報：超過 32 個詞的查詢會回報 `termHitsTruncated`，並不計入上限之後的詞；非 CJK 的複合詞只要任一部分命中就算命中，和排序一致。
- 格式錯誤的 `changed_files_json`（非 JSON 文字、`null`、物件，或含非字串項目的陣列）一律當成空清單。衍生圖、`getContext`、相關工作、熱點與審閱提示不再因這類資料出錯。
- Knowledge 頁的段落也以中文字對（至少 2 個不同字對）比對中文任務。
- 補登的 finalize 不再把最後確認時間往回推；仍會記錄 `applied` 回饋。
- 還原一則已被 active 後繼版本取代的 Knowledge 會被拒絕（`outcome: "rejected"`、`reason: "superseded_by_active"`），不再產生兩筆 active 版本；`updateKnowledge` 改在單一寫入交易中完成。

## 改變什麼

過時判斷：

- 超過 20 檔的後續 Session 不再單獨設定 `possiblyStale`，改計入 `broadChangesSince`。`possiblyStale` 的第一筆 Session、路徑與 `sessionCount` 只看 20 檔以內的 Session，與共變、相關工作、熱點與推論路徑的規則一致。基準改為建立時間與最後確認時間中較晚者。
- `possiblyStale` 新增 `reason`（`applies_to_changed` 或 `broad_applies_to`）與 `appliesToBreadth { share, sessions }`。當 appliesTo 觸及專案最新 200 個（至少 10 個）一般 Session 中超過 15% 時（與寫入時同一個專案範圍的定義，不只看基準時間之後的 Session），標記會說明這是弱訊號。
- 寫入 Knowledge，或更新其 appliesTo 時，會回報 `appliesToBreadth { share, sessions, truncated, broad }`（以專案最新 200 筆、1–20 檔的 Session 計算），太寬時附上提示。

檢索：

- `recall` 與 `getContext` 回報 `knowledgeConfidence`，規則同為 `none`、`low`、`high`，只計算 Knowledge 命中。`relevant.confidence` 仍是 Session 與 Knowledge 合算的結果。
- `getContext` 沒有命中 Knowledge 時附 `knowledgeHint`。
- `work_search_knowledge` 在範圍內零命中時回傳每個詞的 `termHits`，提示會指出查詢全部為零；限定範圍時透傳 `appliesToScanTruncated`；查詢被截斷時一律回傳 `effectiveQuery`。
- 只靠同義詞命中的 Knowledge 會標示 `matchedVia: "synonym"`。MCP 的 `work_recall` 最多保留 4 個 `matchedIn`；`work_search` 不再把 `matchedIn` 填成 `title`。
- 精簡格式的 Knowledge 保留 `possiblyStale: true`，並在有值時附上 `staleReason` 與 `broadChangesSince`。recall 中 appliesTo 的命中也套用 `from` 與 `to`。

Web：

- Knowledge 列以次要文字顯示較弱的訊號（`broad_applies_to` 與 `broadChangesSince`）。只被大範圍改動影響的 Knowledge 不顯示「可能過時」標籤。
- 儲存被後端量為寬範圍的 appliesTo 時顯示提示；還原被拒時說明是因為已被取代。

## Agent 會看到的變化

- `possiblyStale` 會變少，因為大範圍改動不再單獨觸發它。需要看原因時，讀 `reason`、`appliesToBreadth` 與 `broadChangesSince`。
- MCP 回應多了上述可選欄位；沒有這些欄位的舊讀法仍然有效。
- `work_update_knowledge` 還原被取代的 Knowledge 時，可能回 `outcome: "rejected"`，`reason` 為 `superseded_by_active`，並附 `successorId`。
- Agent 需要重新連線一次，才會看到更新後的工具描述。

## 不變的部分

沒有 schema 變更（33），沒有 migration。匯出檔與既有資料不受影響。

## 升級

1. 取得 1.6.39 原始碼後重新建置並重新啟動。已安裝登入自動啟動服務者可執行 `pnpm service:restart`。
2. Agent 重新連線一次。
3. 不需要 migration，也不需要重新匯入資料。

## 未驗證與已知限制

- 三種瀏覽器的 E2E（120 項）已通過。
- 真實資料的前後比較已由協調端在私有副本上以同一支探針執行（單一專案，364 個 Session，只回彙總數字）：
  - 有 appliesTo 的 active Knowledge 35 則中，`possiblyStale` 由 21 則降為 5 則；其中 4 則的原因是 `broad_applies_to`，1 則是 `applies_to_changed`。
  - 另有 16 則只回報 `broadChangesSince`，不再標為可能過時。
  - 被確認過卻仍可能過時的由 7 則降為 2 則。
  - 過時判斷的寬度與寫入時的寬度判定一致（5 則相同，0 則不同）。
  - 349 次以 Session 標題查詢中，`knowledgeConfidence` 為 none 320、low 23、high 6；改版前沒有這個欄位。
- 研究數字只來自單一專案，沒有其他專案的量測。`appliesToBreadth` 的門檻（15%，至少 10 個 Session）是初始值，尚未以更多資料校準。
- 其他 Agent 用戶端是否立即採用新的工具描述，尚未實測。
