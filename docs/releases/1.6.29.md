# Work Intelligence 1.6.29 更新說明

日期：2026-11-12。應用程式與 plugin 版本為 1.6.29；資料庫 schema 維持 33，不需要 migration。

## 摘要

這一版處理可攜式匯入的三個問題：匯入前沒有備份、所屬資料不在檔案裡的列會默默消失、線上匯入會卡住整個 API；另外讓匯入檔只驗證一次，並加快專案資料匯出。以下時間都在開發機上，以同一份合成資料比較 1.6.28 與 1.6.29。

| 情境 | 1.6.28 | 1.6.29 |
| --- | --- | --- |
| REST 匯入 5,000 個 Session（8.5 MiB）期間 `/api/health` 最慢一次 | 1,453 ms | 7 ms |
| 同上，20,000 個 Session（34 MiB） | 5,574 ms | 13 ms |
| 匯入的寫入交易（5,000／20,000 個 Session，空資料庫） | 670／2,440 ms | 280–390／1,260–1,310 ms |
| 匯入預覽，空資料庫（5,000／20,000 個 Session） | 718／2,426 ms | 325／973 ms |
| 匯入預覽，資料已存在（5,000／20,000 個 Session） | 737／3,178 ms | 408／1,356 ms |
| 匯入預覽峰值 RSS，空資料庫（5,000／20,000 個 Session） | 188／455 MiB | 160／345 MiB |
| 專案資料匯出（效能門檻的 5,000 個 Session 資料，程序內） | 155 ms | 83 ms |

## 匯入前先備份

確認匯入後（Web、`POST /api/import` 與 `pnpm db:import` 都一樣），程式先建立並檢查一份整個資料庫的快照（`pre-import-…`，「資料備份」列為「專案資料匯入前」），才寫入任何匯入資料；回應帶 `backupFileName`，CLI 會印出檔名。要撤銷一次匯入，停止服務後以 `pnpm db:restore` 還原這份快照。

- **寫不出備份就不匯入**：與永久刪除專案相同，快照無法建立或檢查失敗時匯入不執行，REST 回 503 `project_backup_failed`，Web 顯示「無法建立並檢查安全備份，資料沒有變更」；資料庫忙碌、唯讀或磁碟已滿仍回各自的代碼。
- **保留份數**：匯入前快照自成一組，保留份數與自動備份相同（預設 3 份），不會擠掉手動、刪除前或 migration 前的備份。
- **預覽不寫入**：預覽仍只讀，不寫資料也不寫備份。
- **中途失敗**：匯入仍是一個 SQLite 交易；寫到一半失敗時資料庫保持原狀，已建立的快照保留。
- in-memory 資料庫沒有檔案可備份，照常匯入，結果不帶 `backupFileName`。

## 所屬資料不在檔案裡的列

列所屬的專案、Session、報告請求或報告原始版本不在匯入檔中時，這些列無法匯入，以前會直接從筆數中消失：5,000 個 Session 有一個指向不存在的專案時，匯入 4,999 個，結果完全沒有提到另一個。現在這些列在預覽與結果中算在各資料表的「衝突」，類別為 `missing_parent`（Web 顯示「匯入檔缺少上層資料」），並沿用 1.6.13 的彙總方式列出原因、筆數與最多 5 個範例 id。

- 匯入哪些列與先前完全相同；同一份資料中 4,999 個 Session 照常匯入，另一個現在列為 1 筆衝突。
- 本機已經有完全相同的列時算「略過」：沒有資料遺失，就不列為衝突。
- 從全專案匯出檔只挑一個專案時，其他專案的列屬於範圍外，不列入。

## 匯入改在背景執行

以前 `POST /api/import` 在 API 主執行緒上解析、驗證並匯入，期間其他請求與即時更新都要等；20,000 個 Session 時寫入鎖持有超過 2 秒，同時 finalize 的 Agent 要等它。現在與預覽相同，主執行緒只把 request body 的 bytes 轉交背景 worker，由 worker 解析、驗證、寫入匯入前備份、計算計畫、寫入，並在 commit 後同步搜尋索引；資料版本改變照常觸發 Web 的 `changed` 事件。CLI 匯入仍同步執行。

- worker 原本只開唯讀連線；匯入改用新的 `existing` 模式開寫入連線：要求資料庫已存在且 schema 正好是目前版本，不做 migration（schema 由 API 程序負責）。
- **寫入鎖只在寫入時持有**：計畫在讀取快照上計算，寫入交易只寫入資料列。每筆專案資料寫入都會提高 `data_revision`，所以寫入交易一開始確認它與計畫時相同；不同（計畫期間有其他寫入）就在交易內重新計算計畫，結果與以前一樣正確。
- 寫入鎖持有時間（`BEGIN IMMEDIATE` 到 `COMMIT`）：5,000 個 Session 約 280–390 ms，20,000 個約 1.26–1.31 秒。另一個程序以不等待的方式持續嘗試寫入，量到最長的等待：5,000 個 364–402 ms（以前 568–602 ms），20,000 個 1.63–1.73 秒（以前 2.40–2.70 秒）。這段最長等待其實是 commit 後的搜尋索引同步：它是另一個交易，約 420 ms／1.7 秒，沒有變。兩段都在 5 秒 busy timeout 內；長度與寫入的列數成正比，由匯入檔 50 MiB 的上限限制（這種形狀約 29,000 個 Session）。

## 匯入檔只驗證一次

以前一次預覽或匯入會驗證整個檔案四次（路由或 worker、遮蔽前、計畫時兩次），5,000 個 Session 每次約 116 ms，記憶體也跟著放大。現在只驗證一次，結果是只有驗證能建立、計畫只接受的 `ValidatedProjectDataImport`，未驗證的檔案無法進入計畫；CLI 選擇新資料夾後只重新驗證路徑轉換等小選項。驗證器也不再為每一列重建兩個欄位集合。每條路徑上每條規則仍只執行一次：測試把每一類無效檔案（格式、未知或缺少欄位、重複 id、無效 JSON 欄位、相對根路徑、不支援的狀態、超過上限的 `appliesTo`、缺少專案的單一專案範圍、太新或太舊的 schema、未知的輸入欄位、重複的路徑轉換）分別送進直接呼叫 store、REST（同程序與背景 worker）與 `db:import`，都以相同代碼拒絕且不寫入任何東西，也確認有效檔案在每條同程序路徑上只驗證一次。

## 專案資料匯出

匯出時的可攜式遮蔽對每個儲存字串跑 11 個正規表示式，並複製每一列。現在每條規則只在文字含有它一定需要的字面文字（例如 `sk-`、`AKIA`、`://`）時才執行，沒有任何一種的文字直接略過；只有內容或遮蔽筆數改變的列與 Session 才複製。匯出的 bytes 完全相同：真實資料複本與 5,000 個 Session 的效能門檻資料，修改前後的匯出（除了 `exportedAt`）逐 byte 相同。效能門檻的 `exportProjectData` p90 由 334 ms 降為 245–300 ms（上限 400 ms，約 61–75%）。

整份 SQLite 匯出（`exportTo`）是 SQLite 的 `VACUUM INTO`、對副本的 `quick_check` 與下載：程序內 10.5 MiB 的資料庫 `VACUUM INTO` 約 43 ms、`quick_check` 約 9 ms，其餘是傳輸；要更快只能改變它產生的檔案或拿掉檢查，所以沒有改，門檻內的差異（189–269 ms）來自機器負載。

## 過時判斷上限的實測

1.6.28 說讀入索引到上限「最多約 2.4 秒、380 MB」，審查推估最長路徑可能到 0.7 GB。這一版實測最長的合法路徑：每個 Session 200 個不同的 1,000 字元路徑，約 800 個 Session 到 22 億單位上限，費時 1.6 秒，程序峰值 RSS 330 MB（讀取前 75 MB），所以原本的數字仍然成立。另外補上 1.6.28 缺少的回歸測試：一頁 50 筆 Knowledge，每筆指定一個底下有 4,000 個之後路徑的目錄與其中一個子目錄（4,000 個 Session × 50 個約 110 字元路徑），全部判斷完、沒有 `stalenessUnchecked`，用 8,400 萬解析單位，高於當初選的 5,000 萬、低於 3 億上限的三分之一。

## 其他

- Web 讀不到匯入檔，或檔案不是 JSON 時，改顯示翻譯過的訊息，不再顯示瀏覽器的英文原因。
- 效能門檻新增 `importProjectData (all projects, already present)`（1,500 ms）：在 worker 中完成整個線上匯入，並套用 API 事件迴圈阻塞的 100 ms 門檻；本機 p90 580–604 ms、事件迴圈阻塞約 14 ms。

## 未納入

- 匯入後的搜尋索引同步仍是一個交易（20,000 個 Session 約 1.7 秒）；它在 worker 中執行，不卡住 API，但期間其他程序的寫入要等它。
- 一頁 50 筆、每筆有 6 個約 100 字元的目錄項目，在 4,000 個 Session × 50 個不同路徑上會用完 3 億解析單位，其中 4 筆標 `stalenessUnchecked`；這比上面的回歸測試重，本版沒有調整上限。

## 升級

1. 取得 1.6.29 原始碼後執行 pnpm bootstrap（或 pnpm install --frozen-lockfile、pnpm build 與 pnpm check）。
2. 若已安裝登入自動啟動服務，執行 pnpm service:restart，確認輸出「服務已在執行 1.6.29」。
3. 透過 launcher 連線的 Agent 會自動切換到新版，不需要重新連線；只有 Agent 回報 `restartRequired` 時才重新連線一次。
4. 匯入前要多一份資料庫大小的磁碟空間給匯入前快照。

完整流程見發行與升級指南（docs/release.md）。
