# Work Intelligence 1.6.28 更新說明

日期：2026-11-12。應用程式與 plugin 版本為 1.6.28；資料庫 schema 維持 33，不需要 migration。

## 摘要

1.6.27 的發行審查以同一份資料比較 1.6.14 與 1.6.27，結論是不發行，原因只有一個：讀取 Knowledge 時的過時判斷比 1.6.14 還慢，而且沒有上限。這一版把過時判斷改成以索引解析，再恢復每次呼叫的固定上限；列表搜尋也找出變慢的原因並修正。以下時間都在開發機上以三個版本讀同一份資料量測。

| 情境（之後的 Session） | 1.6.14 | 1.6.27 | 1.6.28 |
| --- | --- | --- | --- |
| 2,000 個 Session × 50 個不同的約 100 字元路徑，200 筆 Knowledge × 5 項（2 項單星號 glob），第 20／50 筆一頁 | 0.96 秒／2.1 秒 | 2.97 秒／6.8 秒 | 0.19 秒／0.17 秒 |
| 同上，5,000 個 Session | 2.4 秒／5.4 秒 | 6.8 秒／14.8 秒 | 0.49 秒／0.47 秒 |
| 200 個 Session × 200 個不同的 1,000 字元路徑，30 項 1,000 字元，一頁 20 筆 | 8.6 秒 | 54.7 秒 | 0.34 秒（答案相同） |
| 同上，每筆另有一個 15 星號 glob | 9.1 秒 | 58.3 秒 | 0.46 秒（到上限，標 `stalenessUnchecked`） |
| 一般資料：5,000／20,000 個 Session（重複路徑），2,000 筆 Knowledge，一頁 20 筆 | 31 ms／112 ms | 41 ms／124 ms | 23 ms／75 ms |
| 單筆 Knowledge（1 項），5,000 個 Session × 20 個不同路徑 | 0.17 秒 | 0.18 秒 | 0.18 秒 |

## 過時判斷：先建索引，再解析每個項目

過時判斷要回答的是：這一頁的每筆 Knowledge，在它記錄或最後確認之後完成的 Session 中，有沒有改到它 `appliesTo` 涵蓋的檔案。1.6.27 把每個項目和之後所有 Session 改過的每個不同檔案逐一比對（項目數 × 不同檔案數），預算隨歷史成長、沒有上限，所以資料越多越慢，而且同步卡住整個 API。

現在每次呼叫、每個專案只建一次索引：

- 之後的 Session 逐筆讀入，同一個儲存字串出現在很多 Session 時只正規化一次（最多記住最近 4,096 個），每個不同的路徑記下改過它的 Session。這次呼叫要解析超過兩個樣式時，再把每個不同路徑依它的每個路徑段（兩個 `/` 之間的部分）歸檔一次；只解析一、兩個樣式（例如讀取單筆 Knowledge）時，直接拿它們測試每個不同路徑比歸檔快，就不建路徑段索引。
- 每個不同的 `appliesTo` 項目每次呼叫只解析一次，所有共用它的 Knowledge 都沿用結果，而且只測試可能符合的路徑：
  - 一般路徑：符合時它一定以完整路徑段出現在檔案路徑中（相等、目錄、路徑尾段、中間一段），所以只測試含有它「最少見的路徑段」的路徑；另外它的某個尾段本身就是檔案路徑時也算符合，這幾個以雜湊直接查。
  - glob：必須整個路徑符合，開頭與結尾的字面文字一定是路徑的開頭與結尾，所以只測試含有這段字面文字中某個完整路徑段的路徑；完全沒有這種路徑段的 glob（例如 `*.ts`）才測試所有不同路徑。
  - 每個候選仍由原本的比對規則判斷，所以結果與逐一比對相同；為什麼候選一定包含所有符合的路徑，寫在 `later-change-index.ts` 開頭的註解。
- 每筆 Knowledge 只要把它各項目的 Session 清單中、晚於它的時間點的部分合起來（去掉建立與最後確認它的 Session），第一筆就是 `possiblyStale` 的 Session。

索引只在一次呼叫內、一個專案內使用，不跨呼叫或跨專案共用；專案的 policy 檢查與只看 tracked 專案的規則不變。

### 固定上限

演算法改完後，合法資料的成本低到可以再設固定上限，而且離一般用量很遠。兩個上限都是每次呼叫一份，所有專案共用，每項工作在執行前先扣除：

- **讀入索引**：2,200,000,000 單位。每筆 Session、每個清單的 JSON 文字、每個儲存路徑、每個新的不同路徑與每個新的路徑段都先計費（常數依量測調整，讓一字元路徑、大量兩字元的不同路徑與路徑段很多的路徑，每單位的時間都與一般路徑相近）。實測最大的合法歷史，5,000 個 Session × 50 個不同路徑（專案根目錄 110 字元），用 7.1 億單位；20,000 個一般 Session 用 5,300 萬。上限是前者的 3.1 倍；開發機上到上限最多約 2.4 秒、380 MB（9,200 個 Session × 200 個不同的兩字元路徑；前一種形狀到上限是 20,500 個 Session、1.7 秒）。
- **解析項目**：50,000,000 單位。一般一頁約用 100 萬（20,000 個一般 Session 一頁 50 筆 126 萬）；200 × 200 × 1,000 字元的資料 1,270 萬。每個路徑都是候選、每個都要模擬的 15 星號 glob 在這裡停止，約 0.2 秒。

到任一上限時，受影響的 Knowledge 標 `stalenessUnchecked`，不會被當成仍然有效。1.6.26 固定的 5,000 萬單位曾讓合法的大量歷史被標成未檢查，所以 1.6.27 改成隨歷史成長；現在合法成本只剩讀入歷史本身，固定上限可以放在遠高於它的地方。

### 結果相同的證據

- 真實資料複本：所有回報過時狀態的 Knowledge 讀取（兩種狀態、全部與單一專案、每頁 20／50／200 筆的每一頁、每筆的 history、7 個查詢），加上每個真實 Session 的 finalize `knowledgeToReview`，共 406 個序列化結果的雜湊與 1.6.27 全部相同；1.6.21 的等價工具 220 個結果也全部相同。
- 審查的不同路徑資料（2,000 與 5,000 個 Session）、一般資料 5,000 與 20,000 個 Session，以及 200 × 200 × 1,000 字元的資料：每筆的 `possiblyStale` 與 `stalenessUnchecked` 與 1.6.14、1.6.27 相同。
- 儲存庫中新增隨機差分測試：25 組固定種子的 Knowledge 與 Session（glob、目錄、尾段、比檔案長的項目、改名、大小寫與分隔符號、`./`、專案根目錄與名稱前綴、行號錨點、作廢的 Session、相同的完成時間、自己的 Session），與測試內獨立寫的逐一比對實作相同。

## 列表搜尋：恢復短路求值

1.6.27 為了單筆上限，把每個詞的欄位測試放在 `CASE WHEN 檢查 THEN (標題 OR 內文 OR …) END` 的 `THEN` 裡。SQLite 在那裡把 `OR` 當成值計算，不會在找到之後停下，所以每個詞都搜尋了每個欄位；Session 搜尋還對每個詞重新加總一次事件位元組。現在：

- 檢查與詞的測試一起放在 `CASE WHEN 檢查 AND (標題 OR 內文 OR …)` 的條件裡，SQLite 由左到右求值、找到就停。
- Session 的事件摘要只在詞沒有出現在 Session 本身的欄位、要讀事件時才加總並檢查，每筆最多一次；之後的詞在 SQL 裡重複同一個欄位位元組的比較，不再每個詞呼叫一次計數函式。
- 單筆上限仍在每個詞讀取之前檢查。一筆 Session 本身的欄位在 4 MiB 內、加上事件才超過時，現在仍能以出現在欄位中的詞找到，要讀事件的詞照樣拒絕並計數；只有直接改寫的資料庫會有這種列。
- 結果相同：真實資料複本上 206 個查詢（Knowledge 兩種狀態 412 組、Session 206 組、41 個 Agent 搜尋）與 5,000 個合成 Session 上 44 個查詢的 id、順序與總數都與舊的 `LIKE` 查詢相同。

| 5,000 個合成 Session | 1.6.14 | 1.6.27 | 1.6.28 |
| --- | --- | --- | --- |
| Knowledge 列表，三個詞（2,000 筆 Knowledge） | 2.3 ms | 4.2 ms | 3.3 ms |
| Session 列表，三個詞 | 5.6 ms | 23.3 ms | 11.1 ms |
| recall | 75 ms | 67 ms | 75 ms |
| 2,000 筆寫入上限大小的 Knowledge，三個一般詞 | 75 ms | 757 ms | 98 ms |

`normalizePath` 的三個取代只在可能符合時才執行，專案根目錄的小寫形式也會記住（有上限），結果不變。

## 其他

- finalize 的 `knowledgeToReview` 原本就只為少數命中本次 changed files 的候選、由新到舊讀一次之後的 Session 並提早停止，沒有重複上述工作，所以保留自己的流程；只有 SQL 篩選改成找到第一個片段就停。結果不變。
- 效能門檻新增兩個案例（各自的資料庫）：審查的不同路徑過時判斷（1,000 ms）與在解析上限停止的 15 星號 glob（1,000 ms）。
- `docs/architecture.md` 的盤點表更新過時判斷一列，並補上缺少的 Knowledge 候選重疊提示（同專案最新 1,000 筆 Knowledge 與 1,000 筆候選、內文各取前 4,000 字元）。`docs/mcp-tools.md` 說明 MCP 只在 `warnings` 文字中說明略過的筆數，`searchSkippedRecords` 是 REST 與 Web 的欄位。

## 從 1.6.14 或更早的版本升級

1.6.14 之後所有可能影響既有 Agent、REST client 或匯出檔的變更，集中列在這裡。**從 1.6.8 或更早（schema 31）升級時，也請閱讀 1.6.9–1.6.14 的說明**：1.6.9 引入 schema 32（Agent 讀取耗時與錯誤代碼），升級後舊的 MCP 連線會回報 `restartRequired`；這樣的資料庫第一次啟動時會在一次 migration 前備份之後，從 31 直接升到 33。

- **Schema 與連線**：1.6.24 起第一次啟動時升級到 schema 33，之前會自動建立 migration 前備份；Agent 回報 `restartRequired` 時重新連線 Work Intelligence MCP。仍在執行 1.6.24 之前版本的 Agent 連到已升級的資料庫，會收到 `DATABASE_SCHEMA_VERSION_TOO_NEW`。除了還原 migration 前備份（`pnpm db:restore`），無法降回 schema 33 以下。
- **匯入與匯出**：匯入接受 schema 31（v1.6.7 起）到 33 的匯出檔，更舊或更新的檔案以 `unsupported_schema` 拒絕（1.6.24）；1.6.26 起另外拒絕超過 100 筆或單筆超過 4,096 字元的 Knowledge 與候選 `applies_to_json`（任何版本都不會寫出）。匯出檔新增 `knowledge_candidates.overlaps_json`（1.6.24），schema 32 的檔案匯入時此欄為空。
- **REST**：body 的未知欄位，以及整組驗證的查詢參數中的未知欄位，回 400 `invalid_input`，不再默默忽略（1.6.25；匯出 body 自 1.6.26）。以前回 500 的情況，唯讀資料庫改回 503 `database_read_only`、磁碟已滿改回 507 `database_disk_full`（1.6.25）。`GET /api/knowledge` 也比對 `appliesTo` 路徑（1.6.16）。`GET /api/knowledge` 與 `GET /api/sessions` 截短查詢詞或略過超大記錄時回 `warnings`，略過時另帶 `searchSkippedRecords`（1.6.27）。
- **MCP 錯誤代碼**：新增 `DATABASE_READ_ONLY` 與 `DATABASE_DISK_FULL`（1.6.25）；啟動時遇到忙碌、唯讀或磁碟已滿，之後的呼叫會再試，不必重新啟動。
- **回應形狀**：`work_finalize_session`（1.6.20）與 `work_update_session_metadata`、`_summary`、`_title`、`_work_summary`（1.6.22）回傳回條，不再回顯 Session，需要時以 `work_get_session` 讀取。以 `projectRoot` 限定的呼叫只列一次專案，項目省略 `projectId`／`projectName`（1.6.15）。`work_get_context` 的 `omitted` 只保留簡短指標（1.6.15），`relevant.outstandingItems` 每筆只有 id、來源 Session 與最多 240 字元的摘錄（1.6.18）。
- **上限與標示**：寬鬆 Knowledge 搜尋最多使用 5 個像路徑的詞，`appliesTo` 掃描最多讀最新的 2,000 筆 Knowledge（1.6.18）。新的 `appliesTo` glob 超過 16 個星號時，新增與候選審核會拒絕，更新會接受並回傳 `warnings`（1.6.23）。`appliesToScanTruncated`、`knowledgeToReviewTruncated` 與 `stalenessUnchecked` 標示被比對預算截斷的掃描（1.6.23），1.6.26 起也標示略過了超限項目的掃描；`relatedOutstandingItems` 與 context 的未結項最多讀 2,000 筆並帶 `truncated`（1.6.23），1.6.27 起評分預算用完時也帶。列表搜尋最多採用 8 個詞、每詞 200 字元，截短或略過超大記錄時回 `warnings`（1.6.27）。1.6.28 起 Knowledge 讀取的過時判斷改以每次呼叫的不同路徑索引解析，`stalenessUnchecked` 改由兩個固定的每次呼叫上限決定（讀入索引 2,200,000,000 單位、解析項目 50,000,000 單位），遠高於合法用量。
- **新增、不影響既有用法**：`work_get_file_history`（1.6.17）、`work_get_session` 的 `session.files`（1.6.18）、候選的 `overlaps`（1.6.18，1.6.24 起保存）、finalize 的 `knowledgeToReview`（1.6.20）、`work_list_sessions` 的 `commitSha`（1.6.24）、列表搜尋與 recall 的 `warnings`（1.6.27）。

## 未納入

- **與歷史成正比的讀取**：過時判斷仍要把之後的 Session 讀入索引，這部分與歷史的大小成正比：2,000 個 Session × 50 個不同路徑約 0.19 秒、5,000 個約 0.49 秒；超過讀入上限（約上述 5,000 個 Session 的 3 倍，開發機上最多約 2.4 秒）時標 `stalenessUnchecked`。項目解析本身只與候選數成正比；只解析一、兩個樣式時，每個樣式測試所有不同路徑，與歷史成正比。
- **列表搜尋仍比 1.6.14 慢**：Knowledge 三個詞 3.3 ms 對 2.3 ms，Session 三個詞 11.1 ms 對 5.6 ms，寫入上限大小的 Knowledge 98 ms 對 75 ms。差距來自 1.6.27 加上的保護與範圍：每個 Knowledge 詞先呼叫一次計數函式檢查單筆位元組、`appliesTo` 也納入搜尋；Session 搜尋為了總數與換頁一次取出所有符合的 id，並在詞要讀事件時加總事件位元組。
- metadata backfill 預覽、圖譜、時間軸、熱點與回傳記錄的 JSON 解析，仍與合法歷史筆數成正比，見 1.6.27 說明。
- 時間以開發機的量測換算；較慢的機器上會花更久。
- `appliesToScanTruncated`、`knowledgeToReviewTruncated` 與 `stalenessUnchecked` 在 Web 上仍不顯示。

## 升級

1. 取得 1.6.28 原始碼後執行 pnpm bootstrap（或 pnpm install --frozen-lockfile、pnpm build 與 pnpm check）。
2. 若已安裝登入自動啟動服務，執行 pnpm service:restart，確認輸出「服務已在執行 1.6.28」。
3. 透過 launcher 連線的 Agent 會自動切換到新版並收到工具清單更新通知，不需要重新連線；只有 Agent 回報 `restartRequired` 時才重新連線一次。

完整流程見發行與升級指南（docs/release.md）。
