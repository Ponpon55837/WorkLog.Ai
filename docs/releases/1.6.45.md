# Work Intelligence 1.6.45 更新說明

日期：2026-11-16。應用程式與 plugin 版本為 1.6.45；資料庫 schema 維持 33，沒有 schema 變更，也不需要 migration。

## 摘要

- **桌面版階段 5 的打包部分**：以 electron-builder 26.18.1 產出安裝包。Windows 11 x64 為 NSIS 一鍵安裝、目前使用者安裝（`perMachine` 為 false、`allowElevation` 為 false，不會跳出 UAC）。macOS 產出 DMG 與 ZIP，arm64 與 x64 分開建置，不做 universal。Windows ARM 與 Linux 仍不在 V1；Linux 的 `dir` 目標只供本機驗證。`appId` 為 `ai.worklog.workintelligence`，產品名稱為 Work Intelligence。
- **隨包 runtime**：官方 Node.js 24.22.3 與後端放在 `extraResources` 的 `runtime-bundle/`，位於 asar 之外。manifest 的 SHA-256 內嵌在主程式包中（asar integrity 開啟）。首次啟動時，App 把 runtime 複製到 launcher root：先寫入 staging 目錄，再以退避重試更名（處理 Windows Defender 的檔案鎖），接著對照內嵌 manifest 做完整雜湊，寫入指紋快取，最後以原子切換把 `current` 指向新版本。同版本已安裝時走快速路徑，約 2–3 ms，不做雜湊。損毀的既有副本會被隔離後重裝；權限與 ACL 錯誤（`RUNTIME_UNSAFE_PERMISSIONS`、`RUNTIME_ACL_UNREADABLE` 等）直接進入修復視窗，附 zh-TW／English 提示，不重試；只有 `RUNTIME_MISSING` 與內容或完整性錯誤會自動重裝一次。
- **launcher root**：打包後的 App 使用固定位置。Windows 為 `%LOCALAPPDATA%\WorkIntelligence\runtime`（不是 Roaming）；macOS 為 `~/Library/Application Support/WorkIntelligence/runtime`。若以 `--user-data-dir` 啟動，則為 `<userData>/runtime`。
- **Windows ACL 檢查**：從 `not-implemented` 改為實作。以 SDDL 讀取，分兩層：第一層以 .NET（`Directory`／`File.GetAccessControl`）讀取，不載入 PowerShell 模組；只有第一層失敗才以 `Get-Acl` 加 `whoami /user` 讀取（供 Constrained Language Mode 使用）。Windows PowerShell 5.1 以絕對路徑啟動，環境採允許清單（`PSModulePath` 固定為 System32 的 Modules、乾淨的 `Path`），因此已安裝的 PowerShell 7 或自訂的 `PSModulePath` 不會影響它；每層 10 秒逾時，進度輸出靜默並忽略。依 SID 判斷：擁有者必須是目前使用者、SYSTEM 或 Administrators；其他主體若有可寫的 allow ACE，或 DACL 為 null，一律拒絕；檢查失敗時封閉（fail closed）。於安裝、切換、完整驗證時讀取，或 root、bin、runtimes、current、shims、launcher 的時間戳改變時讀取；快取命中的 MCP 啟動不會呼叫 PowerShell。判定為不安全即為最終結果，不再換層。兩層都讀取失敗時回報 `RUNTIME_ACL_UNREADABLE`，附兩層的錯誤訊息與各層耗時，同樣封閉失敗。未採用 `icacls`，因為 `icacls /save` 沒有擁有者，而擁有者必須被驗證。每層實際使用的層級與耗時寫入日誌（`[shell] runtime … acl=<tier> <ms> ms`；spike 輸出 `ACL read:` 行）。目前只以 fixture 驗證；真實 Windows 的行為待 CI 或實機確認。
- **`--quit` 指令**：第二個實例透過 `requestSingleInstanceLock` 的附加資料傳送 `{action:"quit"}`，經嚴格的 zod schema 驗證後，執行中的實例做一般的非互動退出（停止後端，並確認 port 已釋放）。NSIS 安裝與解除安裝程式使用此指令：等待最多 40 秒（App 最壞情況的退出約 31 秒），之後只對目前使用者以 `taskkill /T /F` 結束程序。
- **解除安裝保留資料（DT-34）**：解除安裝只移除程式檔。設定、資料庫（`~/.work-intelligence`）與備份都保留（`deleteAppDataOnUninstall` 為 false）。注意：electron-builder 的解除安裝程式仍接受明確的 `--delete-app-data` 參數，它只會移除 userData，不會動資料庫。macOS 拖入垃圾桶後的清理入口尚未實作。
- **沒有後門進入正式版**：測試 hook 與測試環境開關在編譯時移除（esbuild define `__WI_TEST_BUILD__`），由 `check-production-bundle.mjs` 檢查，並在打包煙霧測試中掃描 asar。Electron fuses 關閉 RunAsNode、NODE_OPTIONS 與 `--inspect`，開啟 cookie 加密與內嵌 asar integrity，只從 asar 載入 App，並不給 `file://` 額外權限。打包後的 App 拒絕 `--remote-debugging-port`、`--remote-debugging-pipe` 與 `--inspect`。
- **macOS 簽章（僅 ad-hoc）**：electron-builder 的 `mac.identity` 為 null，不由它簽章或翻轉 fuses。`afterPack` hook（`apps/desktop/scripts/after-pack.mjs`）先翻轉 fuses，再由內而外（Mach-O 檔、framework、Helper app，最後是 .app）以 `codesign --force --sign - --timestamp=none` ad-hoc 簽署，不含 hardened runtime 與 entitlements。`runtime-bundle` 不動，官方 Node.js 保有自己的簽章。PR 與發行建置走同一條路徑（electron-builder 在 PR 會略過簽章，曾造成 CI 失敗）。硬性閘：所有平台回讀 fuses；`codesign --verify --deep --strict` 且 `Signature=adhoc`；隨包 Node 的 `codesign --verify --strict`；runtime 的 symlink 必須是相對路徑且位於 App 內；並重新驗證由發行 zip 解壓出的 App。`spctl` 只記錄結果。沒有 Developer ID，也沒有公證。
- **CI 打包流程**：新增 `.github/workflows/desktop-package.yml`（pull request、手動觸發與 `workflow_call`）。windows-x64、macos-arm64（macos-latest）與 macos-x64（macos-15-intel）平行執行，各自快取 Electron、electron-builder、runtime 下載與 pnpm store，並顯示命中或未命中。產出的安裝包、打包結果 JSON 與打包效能 JSON 由 CI 上傳。`release.yml` 以發行的 commit 呼叫此流程；發行必須等它成功（ADR-03／DT-33，任一平台失敗即整版不發）。安裝包加入 `SHA256SUMS.txt` 與 GitHub Release。既有的 dispatch 版本輸入與 main 的 CI 檢查沒有改動。
- **應用程式圖示**：原創圖示（圓角方形、記錄時間軸與火花），用於安裝程式、執行檔、`.app` 與系統匣。唯一來源是 `apps/desktop/build/icon.svg`；`icon.ico`、`icon.icns`、`icon.png` 與 `tray.png` 由 `pnpm --filter @work-intelligence/desktop generate-icons` 產生並一併提交。打包時若圖示檔缺少或格式錯誤，或 macOS 打包出的 `icon.icns` 不是自訂圖示，打包會失敗。
- **安裝包壓縮**：Windows 安裝包預設 normal，DMG 預設 UDZO，兩者都是暫定值。`workflow_dispatch` 的 `compare-compression` 輸入（以及暫時性地，所有 pull request 的執行，結果印在 job log）會量測 normal 與 maximum、UDZO 與 ULFO 的差異。
- **效能與記憶體**：打包後的 App 在 Linux（xvfb）閒置時，三次中位數的 PSS 由 352 MiB 降到 292 MiB，RSS 合計由 662 MiB 降到 538 MiB。主因有二：session 政策改在第一個視窗開啟時套用，而不是啟動時（太早讀取 `session.defaultSession` 會讓 Chromium 保留一個備用 renderer，約 28 MiB PSS）；後端 Node 以 `--max-old-space-size=1024 --max-semi-space-size=2` 執行，一個合成的 47.6 MB 匯入與匯出在 256 MiB 上限下可以完成。打包效能 JSON 新增各程序的拆分（main、gpu、renderer、utility、zygote、backend）。關閉 GPU（Linux 上 PSS 無變化，需 Windows 與 macOS 的資料）與把網路服務放進主程序（安全考量）都已拒絕。
- **匯出效能門檻**：`exportProjectData`（全部專案）改為量到回應最後一個位元組，上限由 400 ms 收緊為 360 ms。備份、整庫匯出、專案資料匯出、匯入預覽與線上匯入各跑 10 次（先前 5 次），p90 取第 9 小的值。
- **伺服器關閉與請求本文**：SIGTERM 與 SIGINT 會先關閉閒置連線，寬限 10 秒後再關閉所有連線，停在標頭中途的 client 不會再讓程序存活到 Node 的 headers timeout。匯出、匯入預覽與匯入之後，備份 worker 閒置 5 秒即退出（輕量操作仍為 15 秒），解析後的文件不會被持續持有，預覽後接著匯入也不必付 worker 冷啟動。請求本文讀進一個依 `Content-Length` 配置的 buffer。

## 不變的部分

沒有 schema 變更（33），沒有 migration。CLI、MCP 與 HTTP API 的既有行為不變。plugin、standalone 與 MCPB 的 Agent 設定沒有改動，Agent 設定仍未接到 launcher。

## 升級

1. 本版的安裝包由 `desktop-package` 流程產生，並隨發行附上；只有三個平台的打包都成功，發行才會公開（ADR-03）。文件撰寫時尚未取得三平台的 CI 結果。
2. 不需要 migration，也不需要重新匯入資料。
3. 解除安裝後，資料庫、設定與備份保留在原位置；若要完整移除，須自行刪除這些資料夾。
4. 安裝包沒有 Developer ID 簽章、沒有公證，也沒有自動更新。Windows 安裝包未簽章，會顯示 SmartScreen 警告；macOS 只做 ad-hoc 簽章，會顯示 Gatekeeper 警告，在 macOS 15 上須於「系統設定 → 隱私權與安全性」按「強制打開」（Open Anyway），右鍵 → 打開已不能繞過；請只從官方 Releases 下載，並核對 `SHA256SUMS.txt`。

## 未驗證與已知限制

- **沒有自動更新**：electron-builder 26 不驗證 v27 的 Ed25519 簽名 update manifest（DT-28，見 R4 §7.1）。`publish` 為 null，沒有 electron-updater 依賴。更新需手動下載新版安裝包。
- **只有 ad-hoc 簽章，沒有 Developer ID 與公證**：Windows 安裝包未簽章；macOS 由 `afterPack` hook 做 ad-hoc 簽章（electron-builder 的 `mac.identity` 為 null），因為翻轉 fuses 會使 arm64 的既有簽章失效。沒有 Developer ID，也沒有公證。
- **實機尚未驗收**：Windows 11 的安裝、以 `/D=` 靜默安裝、在執行中的 App 上重裝（會先以 `--quit` 優雅退出）、靜默解除安裝並保留資料庫與備份、Windows ACL 的真實行為、Windows 與 macOS 的 DMG 掛載與 Gatekeeper；macOS 的 `codesign --verify`（打包閘）與 `spctl` 結果（只記錄）。這些都需要 CI 或實機紀錄。
- **Windows ACL 的殘餘風險**：擁有 WRITE_DAC 的主體可以重設 ChangeTime，因此時間戳不是完整的竄改證據。
- **macOS 拖入垃圾桶**：不會清理，清理入口（DT-34）未實作。
- **DT-24 只完成一部分**：背景清理只保留目前與前一版 runtime；尚未證明「沒有現役連線」，因此不做更進一步的 GC。
- **macOS 架構**：建議 arm64 與 x64 分開產出，不做 universal（兩份 runtime 的 Node 執行檔與 manifest 雜湊不同，universal 會使安裝包約加倍，且非 Mach-O 檔案會互相衝突）。此建議仍待產品確認；x64 在 macos-15-intel 建置與測試。
- **效能數字**：目前只有本機 Linux 的數字；Windows 與 macOS 的打包、啟動與記憶體數字待 CI；Windows 與 macOS 的記憶體門檻（1024 MiB、192 MiB）為暫定值。啟動流程並行化的效益亦同。
- **CI 待確認項目**：Windows NSIS 的安裝、升級與解除安裝；真實的 ACL 讀取（兩層各自的結果與耗時）；Defender 更名重試的實際行為；macOS 的 codesign 與 spctl，以及解壓後的 zip 重新驗證；安裝包壓縮比較（PR 執行會暫時比較 NSIS normal／maximum 與 DMG UDZO／ULFO，以選定預設值）；Windows 與 macOS 的安裝包大小、效能與記憶體門檻。
- **階段 5 gate 未通過**：`docs/desktop/desktop-v1-design-r4.md` §9.4 的階段 5 表格列為「自動更新與 schema」，本版只完成其中的打包部分；自動更新、簽名驗證、schema 屏障與斷電復原演練都未做。打包的實機驗收與 Windows、macOS 的 CI 結果也尚未取得。
