# Work Intelligence 1.6.27 更新說明

日期：2026-11-12。應用程式與 plugin 版本為 1.6.27；資料庫 schema 維持 33，不需要 migration。

## 安全性：先盤點，再為每條路徑設上限

前幾輪只修正審查點名的路徑，相鄰的路徑留著同一類問題：工作量隨「儲存文字的長度」或「呼叫端的詞與路徑」增加，卻沒有上限也沒有計入預算。這次先盤點所有 MCP 或 REST 觸發、會這樣成長的地方（SQL 的 `LIKE`／`instr`／`lower`／`json_each`、由呼叫端文字組成的 FTS 查詢、讀取路徑上沒有 `LIMIT` 的 `.all()`、走訪已解析 JSON 的迴圈、每個候選各掃一次的 N × M），再依盤點修正：以寫入上限允許的最大資料加上最貴的呼叫端輸入，可能同步阻塞超過約 300 ms 的每一條都設了上限。精簡版盤點表放在 [架構說明](../architecture.md) 的「儲存文字上的有界工作」。

| 路徑 | 修正前（最壞情況） | 修正後 |
| --- | --- | --- |
| Knowledge／Session 列表搜尋（`q`） | 2,000 筆最大 `appliesTo` 配一個 500 字元近似詞 38.6 秒；200 筆配 8 個近似詞 15.7 秒 | 123–132 ms 停止並回 `warnings` |
| recall／context 的路徑比對 | 1,000 字元近似路徑每個儲存位元組約 400 ns | `instr()` 並計入整次呼叫共用的上限 |
| finalize `knowledgeToReview` 第二階段 | 200 筆候選 × 5,000 個之後的 Session 2.9 秒，仍標示未截斷 | 一次掃描 18–23 ms，結果相同 |
| Knowledge 讀取的過時判斷 | 5,000 個 Session × 50 × 100 字元 433 ms、235 MB；500 × 200 × 1,000 字元 783 ms、431 MB | 逐筆讀取並先計費，56 ms／40 ms 停止並標 `stalenessUnchecked` |
| finalize／context 的相關未結項 | 2,000 筆 × 24 個詞 × 20 個路徑 2.1 秒 | 156 ms，預算用完標 `truncated` |

## 列表搜尋：`instr()`、詞數與詞長上限、文字掃描上限

Web 的 Knowledge 與 Session 列表、`work_search_knowledge`、`work_list_sessions` 的 `q` 原本以 `LOWER(欄位) LIKE '%詞%'` 比對，SQLite 會從每個儲存位置重新比對整個詞。1.6.16 把 `appliesTo` 加入比對後，最大的儲存資料變大了很多。

- 每個詞改用 `instr()` 比對，結果與原本相同（萬用字元原本就已跳脫、詞已轉小寫、`LIKE` 只折疊 ASCII 大小寫），但不會從每個位置重試。
- 最多採用前 8 個詞（原本也是 8 個，但多的詞會被默默丟掉），每個詞最多比對前 200 個字元。依據：41 個真實 Knowledge 查詢最長的詞是 41 字元的路徑，真實資料最長的 changed file 是 81 字元；實際的 Agent 查詢多為 2–6 個短詞。被截短的詞以前 200 個字元比對，原本符合的記錄仍然符合。
- 每個詞在讀取一筆記錄之前，先依該筆被搜尋欄位的位元組數（從 SQLite 記錄標頭讀出，不會先載入文字）計入單次搜尋的上限 24,000,000 單位；SQLite 遇到第一個不符合的詞就停，所以一般查詢約只付一次文字掃描的成本。開發機上最慢的文字每單位約 5.3 ns，用完約 130 ms；Agent 的嚴格搜尋最多跑兩份（清單，以及嚴格零命中時其他狀態的計數）。
- 截短的詞、被略過的詞與用完的上限都寫在新的 `warnings` 陣列（REST 回應、`work_search_knowledge`、`work_list_sessions`），不會默默改變查詢；一般查詢沒有 `warnings`。

同一套做法也用在 `work_recall`、`work_get_context` 與寬鬆 Knowledge 搜尋的路徑比對：儲存路徑改用 `instr()` 比對，每筆比對前依位元組數計入，同一次呼叫的所有路徑共用一份上限；用完時 recall 回 `warnings`，寬鬆搜尋標 `appliesToScanTruncated`。

結果完全相同的證據：真實資料複本上 206 個查詢（41 個 Knowledge 查詢、15 個 recall 查詢與其中每個單詞），Knowledge 列表兩種狀態 412 組與 Session 列表 206 組的 id 順序與總數都與舊的 `LIKE` 查詢一致，41 個 Agent 嚴格搜尋也一致，沒有任何 `warnings`。真實資料最重的一次 Session 列表搜尋用掉上限的 6.7%，20 個路徑的 recall 用掉 8%。

## knowledgeToReview：所有候選共用一次掃描

finalize 的 `knowledgeToReview` 原本對每個候選各跑一次 SQL 掃描之後的 Session，而且只有回傳的列計入預算；SQL 為了篩選讀過、但沒有回傳的列都不算。現在對所有候選只讀一次之後的 Session（新到舊）：SQL 以所有候選需要的片段（最多 16 個不同片段，否則每筆都解析）篩選，每一列在 `instr()` 讀取前依位元組數 × 片段數計費，留下的 Session 在解析變更檔案前再計費；一個候選在某個 Session 碰到它時、或掃描已經早於它的確認時間時就決定，前 3 個可提示的候選都決定後即停止。預算用完時沿用 `knowledgeToReviewTruncated`。

在 1.6.26 版與本版對真實資料複本全部 319 個 Session 的輸出完全相同；v1.6.20 的重播工具（每個 Session 當時的 Knowledge 狀態）照樣得到 50 個 Session 中 5 個有提示、共 6 筆。

## 過時判斷：逐筆讀取、先計費

讀取 Knowledge 時的過時判斷原本以一次 `.all()` 載入同專案所有之後的 Session 與其變更檔案。現在逐筆讀取，解析每份清單前依長度計費，正規化每個路徑前也計費；預算用完時，該專案這次讀取的記錄都標 `stalenessUnchecked`，不會因為沒讀完就被當成仍然有效。1.6.21 的等價測試工具（真實資料複本上 220 個序列化結果的雜湊）在 1.6.26 與本版之間 220 個全部相同。

## 相關未結項：先計費再評分

finalize 與 `work_get_context` 的相關未結項最多讀 2,000 筆待辦，以最多 24 個詞與 20 個路徑評分，原本沒有上限，而且把來源 Session 的變更檔案複製到每一筆待辦的資料列（2,000 列 × 200 KB 的清單約 400 MB）。現在變更檔案每個來源 Session 只讀一次；每筆待辦評分前先計費（50,000,000 單位，開發機約 100 ms），用完時沿用既有的 `truncated`，`total` 只計已評分的筆數。

## 超過讀入上限的儲存值不載入

- 長於匯入結構上限（100 筆 × 4,096 字元，以每字元 6 位元組的 JSON 跳脫計約 2.5 MB）的 `appliesTo` 文字，SQL 以 `octet_length` 判斷後不載入，掃描把它當成超過寫入限制的項目：永遠不比對、標示掃描不完整。以前要等 SQLite 載入後才計費，100 MB 每次讀取 290–370 ms。
- 長於約 1.2 MB（200 個 1,000 字元路徑的最壞跳脫）的變更檔案清單，過時判斷、`knowledgeToReview` 與相關未結項都不載入，並標示結果不完整。
- 只有直接改寫的資料庫會有這種值；正常寫入與匯入都不會產生。

## 計費調整

- 解析儲存的 `appliesTo` 清單改計每字元 4 單位（原本 1），與量測到的 `JSON.parse` 成本一致。
- 判斷一個項目是 glob 還是一般路徑時，依項目長度計費（已編譯並在快取中的 glob 只計 1）；`knowledgeToReview` 每個項目只判斷與編譯一次，不再每個變更檔案各一次。
- 編譯快取的淘汰迴圈不另外計費：它只在已計費的未命中之後執行，搬動次數不超過命中時設的標記加上曾放入的項目數，攤提後在已付的成本之內（理由寫在程式註解）。

## 修正：效能門檻的重案例看到的資料庫不再隨其他案例變大

`pnpm run test:performance` 在 Ubuntu CI 連續兩次因 `exportTo (whole database)` 超過 300 ms 失敗。產品本身沒有變慢：以 `--backup-worker-only` 量測，v1.6.14 與現在的備份／匯出時間相同。原因是這一系列版本加入的案例（finalize、每輪新增的 Knowledge、未結項清理等）會寫入共用資料庫，跑到備份與匯出時要複製的檔案比只跑 `--backup-worker-only` 時大約 5%（26.5 → 27.9 MB）。現在四個重案例改讀種子資料建好、任何案例執行前複製出的同一份資料庫檔；結果表的 `databaseBytes` 顯示它們看到的大小，完整執行與 `--backup-worker-only` 相同。300／400 ms 的上限不變。

其他讀取案例仍共用 store，會看到前面 finalize 案例新增的約 48 個 Session 與 16 筆 Knowledge（約 1%）；年報 ANALYZE、大量變更後第一次讀取、候選重疊與本版新增的三個最壞情況各用自己的資料庫。

## 文件修正

`docs/mcp-tools.md` 曾寫檔案歷史的 `appliesTo` 比對「與 `work_recall` 相同」，但 `work_recall` 根本不比對 `appliesTo`，只有 `work_search_knowledge` 嚴格零命中後的寬鬆備援會比對。文件已改成程式實際的行為。

## 從 1.6.14 或更早的版本升級

1.6.14 之後所有可能影響既有 Agent、REST client 或匯出檔的變更，集中列在這裡。**從 1.6.8 或更早（schema 31）升級時，也請閱讀 1.6.9–1.6.14 的說明**：1.6.9 引入 schema 32（Agent 讀取耗時與錯誤代碼），升級後舊的 MCP 連線會回報 `restartRequired`；這樣的資料庫第一次啟動時會在一次 migration 前備份之後，從 31 直接升到 33。

- **Schema 與連線**：1.6.24 起第一次啟動時升級到 schema 33，之前會自動建立 migration 前備份；Agent 回報 `restartRequired` 時重新連線 Work Intelligence MCP。仍在執行 1.6.24 之前版本的 Agent 連到已升級的資料庫，會收到 `DATABASE_SCHEMA_VERSION_TOO_NEW`。除了還原 migration 前備份（`pnpm db:restore`），無法降回 schema 33 以下。
- **匯入與匯出**：匯入接受 schema 31（v1.6.7 起）到 33 的匯出檔，更舊或更新的檔案以 `unsupported_schema` 拒絕（1.6.24）；1.6.26 起另外拒絕超過 100 筆或單筆超過 4,096 字元的 Knowledge 與候選 `applies_to_json`（任何版本都不會寫出）。匯出檔新增 `knowledge_candidates.overlaps_json`（1.6.24），schema 32 的檔案匯入時此欄為空。
- **REST**：body 的未知欄位，以及整組驗證的查詢參數中的未知欄位，回 400 `invalid_input`，不再默默忽略（1.6.25；匯出 body 自 1.6.26）。以前回 500 的情況，唯讀資料庫改回 503 `database_read_only`、磁碟已滿改回 507 `database_disk_full`（1.6.25）。`GET /api/knowledge` 也比對 `appliesTo` 路徑（1.6.16）。`GET /api/knowledge` 與 `GET /api/sessions` 截短查詢詞或用完文字掃描上限時回 `warnings`（1.6.27）。
- **MCP 錯誤代碼**：新增 `DATABASE_READ_ONLY` 與 `DATABASE_DISK_FULL`（1.6.25）；啟動時遇到忙碌、唯讀或磁碟已滿，之後的呼叫會再試，不必重新啟動。
- **回應形狀**：`work_finalize_session`（1.6.20）與 `work_update_session_metadata`、`_summary`、`_title`、`_work_summary`（1.6.22）回傳回條，不再回顯 Session，需要時以 `work_get_session` 讀取。以 `projectRoot` 限定的呼叫只列一次專案，項目省略 `projectId`／`projectName`（1.6.15）。`work_get_context` 的 `omitted` 只保留簡短指標（1.6.15），`relevant.outstandingItems` 每筆只有 id、來源 Session 與最多 240 字元的摘錄（1.6.18）。
- **上限與標示**：寬鬆 Knowledge 搜尋最多使用 5 個像路徑的詞，`appliesTo` 掃描最多讀最新的 2,000 筆 Knowledge（1.6.18）。新的 `appliesTo` glob 超過 16 個星號時，新增與候選審核會拒絕，更新會接受並回傳 `warnings`（1.6.23）。`appliesToScanTruncated`、`knowledgeToReviewTruncated` 與 `stalenessUnchecked` 標示被比對預算截斷的掃描（1.6.23），1.6.26 起也標示略過了超限項目的掃描；`relatedOutstandingItems` 與 context 的未結項最多讀 2,000 筆並帶 `truncated`（1.6.23），1.6.27 起評分預算用完時也帶。列表搜尋最多採用 8 個詞、每詞 200 字元，截短或用完文字掃描上限時回 `warnings`（1.6.27）。
- **新增、不影響既有用法**：`work_get_file_history`（1.6.17）、`work_get_session` 的 `session.files`（1.6.18）、候選的 `overlaps`（1.6.18，1.6.24 起保存）、finalize 的 `knowledgeToReview`（1.6.20）、`work_list_sessions` 的 `commitSha`（1.6.24）、列表搜尋與 recall 的 `warnings`（1.6.27）。

## 未納入

盤點中以下路徑仍與資料量成正比、沒有另設預算，理由如下：

- **與合法歷史筆數成正比的讀取**：metadata backfill 預覽會讀入所有有缺漏的 Session 完整資料列；圖譜（每個專案最多讀固定筆數的 Session）、時間軸與熱度日曆（日期範圍最多 366／400 天）、熱點（`search_paths` 的 SQL 彙總）都隨合法的歷史筆數線性成長，不會因為呼叫端的輸入重複掃描。單筆內容受寫入上限約束，效能門檻以 5,000 個合成 Session 量測。
- **回傳記錄的 JSON 欄位解析**：回傳的每筆 Session 與 Knowledge 都要解析其 `*_json` 欄位，筆數受分頁限制（最多 100／200 筆），單筆大小受寫入上限約束；只有直接改寫的資料庫能讓單筆超過上限。
- **FTS 查詢**：recall、search 與寬鬆搜尋的 `MATCH` 最多 32 個 token，由索引驅動，成本與符合的文件數成正比，不隨儲存文字長度重試。
- **列表搜尋的列數**：每個詞的成本有上限，但符合結構條件（專案、狀態、日期）的列數本身不設限；上限用完時回 `warnings`，不會無限掃描。非常長的歷史（真實資料的十倍以上）配上多個詞時，結果可能只涵蓋較新的記錄。
- 預算以開發機的量測換算時間；較慢的機器上同樣的預算會花更久。
- Web 仍不顯示截斷、`warnings` 與 `stalenessUnchecked` 標示。

## 升級

1. 取得 1.6.27 原始碼後執行 pnpm bootstrap（或 pnpm install --frozen-lockfile、pnpm build 與 pnpm check）。
2. 若已安裝登入自動啟動服務，執行 pnpm service:restart，確認輸出「服務已在執行 1.6.27」。
3. 透過 launcher 連線的 Agent 會自動切換到新版並收到工具清單更新通知，不需要重新連線；只有 Agent 回報 `restartRequired` 時才重新連線一次。

完整流程見發行與升級指南（docs/release.md）。
