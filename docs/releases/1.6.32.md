# Work Intelligence 1.6.32 更新說明

日期：2026-11-13。應用程式與 plugin 版本為 1.6.32；資料庫 schema 維持 33，不需要 migration。

## 摘要

這一版依一份真實使用資料的副本（6 個專案、647 筆 Session）量測後才決定要改什麼。產品方向不變：有效沉澱 → 精準再利用 → 持續修正。量測找到這個循環實際漏掉的四個地方，這一版逐一處理：

| 問題 | 量到的現象 | 這一版 |
| --- | --- | --- |
| 開始時間常常沒填 | 多次由使用者要求批次補填；1.6.31 當天仍有記錄沒有開始時間 | Agent 保存前就拿得到開始時間；仍省略時由伺服器記錄觀察到的時間並標明來源 |
| Knowledge 沒有被提供給後續工作 | 後續 Session 改到某筆有效 Knowledge 適用的檔案時，帶路徑查詢只有 3.3% 拿到完整內容 | 帶路徑查詢時比對適用路徑；同一批情境提高到 56.7%，回應長度變化不到 0.5% |
| 多數 Session 從未被整理成 Knowledge 候選 | 候選請求一共 13 次，每次只取最新 10 筆，只有 20% 的 Session 被檢視過 | 改依記錄中的價值訊號挑選，並在適當時機顯示還有多少未整理 |
| 未結項靠使用者手動結案 | 45% 的未結項由使用者在 Web 批次結案；Agent 只在保存當下結案，之後 0 次 | 保存前後都列出相連 Session 的待辦，Agent 可一次附依據結案 |

資料內容沒有進入 repository；以下數字都是彙總計數。

## 開始時間不必再提醒

先前只有 Claude Code 的 Stop hook 會告知這段工作的開始時間，而且只在「改過檔案又還沒保存」時才提醒。Agent 主動先保存、用戶端沒有 hook，或 Codex 用 shell 改檔時，都拿不到開始時間，保存回條也不會要求補。

- **Claude Code**：plugin 新增 PreToolUse hook。保存時 `startedAt` 與 `completedAt` 都沒填，而且對話紀錄裡有這段工作的開始時間時，這次保存會被暫停一次並告知時間，Agent 帶上後重試。每段工作只暫停一次。
- **Codex**：一段工作的第一則訊息就告知開始時間，另有對等的 PreToolUse 檢查。
- **伺服器觀察**：Agent 仍省略時，MCP 伺服器改用「上次成功保存之後，這個專案第一次工具呼叫」的時間。回條以 `startedAtSource: "server_observed"` 標示，記錄中留下一筆 note。超過 7 天的觀察值不採用；帶 `completedAt` 補記舊工作時不使用。
- **回條**：存完仍沒有開始時間時，回條附上 `startedAtFollowUp` 與 `suggestedCall`，要求只依證據補上，不可估計。
- **更正留下記錄**：`startedAt` 的更正與 `completedAt` 一樣會留下 note event。

`work_update_session_metadata` 另有兩項調整：

- `changedFiles` 可以省略，省略時已保存的檔案、來源與變更事件都不動。先前只想補時間也必須重送檔案清單，送 `[]` 會清掉已保存的檔案。
- 新增 `completedAtNow: true`（與 `completedAt` 互斥）：同一筆 Session 續做完成時，由伺服器記錄當下時間。真實資料有 112 次「完成時間更正」，其中 111 次是把時間往後推，也就是續做後由 Agent 自己讀時鐘填值；現在不必自己填。

## 帶路徑查詢會比對 Knowledge 的適用路徑

先前 `work_get_context` 與 `work_recall` 選 Knowledge 時只比對文字與 `references`，不比對 `appliesTo`。只靠適用路徑相連的 Knowledge，就算 Agent 正要改那個檔案也不會被提供。

- 帶 `paths` 時，在既有的有上限掃描內比對 `appliesTo`；只靠 `appliesTo` 命中的權重是 `references` 命中的 0.85 倍。
- 同一個檔案有很多 Session 時，最多保留 3 個位置給路徑命中的 Knowledge。
- 放不進正文的路徑命中 Knowledge，以帶標題與命中路徑的指標列在 `omitted`（最多 5 筆），不會只剩 id。
- 字數上限不變；不帶 `paths` 的呼叫行為不變。

真實資料回放（後續 Session 改到某筆目前有效 Knowledge 適用的檔案，共 337 次）：

| 帶路徑查詢 | 1.6.31 | 1.6.32 |
| --- | --- | --- |
| 完整提供 | 3.3% | 56.7% |
| 只有指標 | — | 37.7% |
| 沒有出現 | — | 5.6% |

只給任務描述、不帶路徑時，完整提供仍是 7.4%。所以 Agent 指引與工具說明現在要求開工時把預計要改的檔案放進 `paths`，知道更多檔案後再查一次。

效能：資料沒有變動時重用 Knowledge 過時判斷的結果。5,000 筆合成 Session 上，帶路徑的 `work_recall` 中位數約 11 ms、`work_get_context` 約 50 ms，與 1.6.31 相當；寫入後第一次呼叫較慢（約 26 ms 與 140 ms）。

## Knowledge 候選改依價值挑選

- `work_request_knowledge_candidates` 不再只取最新 10 筆，改取訊號最強的 10 筆未整理 Session：已確認的決策、驗證失敗後修好、被後續 Session 連結、被刻意重讀。較舊但有價值的 Session 會被排到。
- 限定專案的 `work_get_context` 在同時符合三個條件時回報 `pendingRequests.knowledgeBacklog`：沒有未結請求、高價值未整理 Session 至少 5 筆、7 天內沒有建立過請求。Agent 只向使用者提一次，不會自行建立請求。
- 中斷（failed）的請求現在會列在 `pendingRequests`；先前它會擋住新請求卻不顯示。
- Web 候選區顯示還有多少 Session 未整理。

真實資料顯示候選品質不是問題（88 筆候選接受 80 筆，有效 Knowledge 之間沒有近似重複），所以這一版沒有改候選內容的規則。

## 未結項

- **改寫保留身分**：同一筆 Session 改寫 `nextSteps` 的文字時（字元 bigram 相似度至少 0.5、一對一配對），未結項原地更新，不再標成不再需要再新建一筆。
- **來源減量**：工作記錄契約明定任務內的進度（尚未 commit、PR 待合併、CI 執行中、階段尚未開始）不寫進 `nextSteps`。伺服器不會用關鍵字自動丟棄任何項目。
- **保存前後都能結案**：`work_get_context` 可帶 `linkedSessionIds`，回傳 `relevant.continuedOutstandingItems`；保存回條也有 `continuedOutstandingItems`（將連結的同專案 Session 仍待處理的項目，最多 10 筆）。新操作 `work_resolve_outstanding_items` 讓已保存的 Session 一次結案它驗證過的項目，保存之後也能用，event 記錄該 Session 為依據。
- **區分呈現**：清單新增 `closedBy`（來源 Session、後續 Session、使用者、整理審核、遷移），REST 可篩選，Web 會標示並可隱藏「來源 Session 更新時移除」的項目。
- **整理未結項**：新操作 `work_request_outstanding_cleanup`，使用者開口要求時 Agent 直接建立請求；接受與拒絕仍只在 Web。

用歷史記錄回放：使用者手動結案的 785 筆中，有 586 筆（75%）在新機制下會於後續 Session 保存時列給 Agent。

## 未驗證與已知限制

- 兩個 PreToolUse hook 只有單元測試，沒有在真實的 Claude Code 或 Codex 用戶端實測。
- Claude 桌面版可能讓多個對話共用同一個 MCP 行程，伺服器觀察到的開始時間可能早於目前對話；已標示來源，超過 7 天不採用。
- Agent 看到可結案的未結項後是否真的結案、開工時是否帶上路徑，取決於 Agent 的行為，要在使用一段時間後用兩支量測腳本比較前後才知道。
- 同一筆 Session 整批換掉（不是改寫）的未結項仍會標成不再需要，只是清單上分開呈現。
- 「Knowledge 有提供但 Agent 沒有回報使用」這一段沒有處理：樣本太少，也沒有可靠又不增加負擔的觀察方式。

## 量測腳本

兩支腳本都以唯讀方式開啟資料庫，只輸出彙總數字，並內建合成資料自檢：

- `node docs/experiments/outstanding-items-probe.mjs --db <資料庫副本> [--split YYYY-MM-DD]`
- `node docs/experiments/knowledge-reuse-attribution.mjs --db <資料庫副本> --json <新檔>`

升級一段時間後以 `--split <升級日>` 比較前後，可以看出 Agent 結案與保存後結案的次數是否增加。

## 升級

1. 取得 1.6.32 原始碼後執行 pnpm bootstrap（或 pnpm install --frozen-lockfile、pnpm build 與 pnpm check）。
2. 更新 plugin，或手動設定者執行 pnpm setup:agents，以取得 PreToolUse hook；pnpm check 會提示缺少的 hook。
3. 若已安裝登入自動啟動服務，執行 pnpm service:restart，確認輸出「服務已在執行 1.6.32」。
4. Agent 重新連線一次，才看得到新的操作與工具說明。

完整流程見發行與升級指南（docs/release.md）。

從 1.6.14 或更早的版本升級時，請先讀 1.6.28 更新說明（docs/releases/1.6.28.md）的「從 1.6.14 或更早的版本升級」，再讀 1.6.29 與 1.6.30 的說明。
