# Work Intelligence 1.6.26 更新說明

日期：2026-11-12。應用程式與 plugin 版本為 1.6.26；資料庫 schema 維持 33，不需要 migration。

## 安全性：appliesTo 比對預算成為實際工作量的上限

1.6.23 的步數預算只計「每組樣式與路徑 1 步」加上模擬比對，比對前的檢查、編譯樣式與讀取儲存清單都沒有計入。一個約 600 字元、只有 2 個星號的儲存 glob 對 1,000 字元路徑，字面片段搜尋每組要 44 µs，卻只計 1 步；在現有上限內，一次呼叫可能讓 MCP 與 API 程序停住約 50 秒。這是同一個子系統的第三輪修正，所以這次改的是計算方式本身，並用測試固定下來：

- **先扣再做**：每項成本會隨儲存項目或呼叫端路徑長度增加的工作，執行前都先從預算扣除，單位統一為字元操作，且每次比較至少扣 1 單位。涵蓋解析與正規化儲存清單、編譯 glob（快取未命中時）、每組樣式與路徑的固定成本、開頭／結尾與完全相同的比較、依序搜尋字面片段，以及模擬比對。扣不下時該項工作不執行，預算標示用完，之後的工作都不再執行。
- **線性搜尋**：字面片段與一般路徑的 `/路徑/` 搜尋改用 Knuth-Morris-Pratt，每個路徑字元最多比較兩次；原本的 `indexOf` 遇到近似重複的長字面片段沒有這個保證。
- **強制測試**：性質測試以固定種子產生 140 組上限內的惡意組合（近似重複的長字面片段、交錯的 `?*`、16 個星號夾長字面片段、重複前綴、用來讓快取失效的不重複 1,000 字元樣式、長的一般路徑、隨機 glob），以除錯計數器記錄迴圈實際比較的字元數，檢查每組都不超過已扣的單位，少 1 單位的預算不會執行該組的任何檢查，預算用完後掃描停止且不再做任何工作。測試不比對時間。

預算依時間目標設定。開發機上最慢的路徑每單位 3.7 ns（模擬比對；字面片段搜尋 3.1、編譯 3.6–4.0、一般路徑 3.2–3.5、一般樣式組合 3.3）：

| 掃描 | 每次呼叫的預算 | 開發機上最多 | 實際資料用量 |
| --- | --- | --- | --- |
| recall、寬鬆 Knowledge 搜尋、檔案歷史、finalize 的 `knowledgeToReview` | 20,000,000 單位 | 約 75–90 ms | 最重一次 300,000（1.5%） |
| 讀取 Knowledge 時的 staleness 檢查 | 50,000,000 單位 | 約 200 ms | 整份 Knowledge 清單 3,400,000（7%） |

staleness 檢查比對的是儲存的項目與儲存的歷史，在讀取中同步執行、無法讓出，所以上限另外訂為約 200 ms。預算仍是每次呼叫共用一份，不會每筆重設。

| 情境 | 修正前 | 修正後 |
| --- | --- | --- |
| 2 個星號夾約 600 字元近似重複的字面片段，2,000 筆 × 30 項 × 20 個路徑 | 每組 44 µs、只計 1 步，約 50 秒 | 預算用完即停，75–110 ms |
| 5 MB 的單一 `appliesTo` 項目 | 編譯 1.7 秒、674 MB 記憶體 | 不解析即略過 |
| 6 萬筆不重複的 1,000 字元樣式 | 編譯約 5 秒且不計入，快取滿了整個清空 | 每次未命中都計入，預算用完即停，約 75 ms |

一般樣式的結果完全相同：原本的正規表示式基準與 6,000 組產生樣式測試照常通過；實際資料複本中 65,170 組樣式與變更檔案的組合、3,533 個路徑的正規化結果都一致。

## 超過寫入上限的 appliesTo 不進入比對

不論資料怎麼存進來，比對只看一筆記錄的前 30 個 `appliesTo` 項目、每項最多 1,000 字元，與寫入時的限制相同。超過的項目不正規化也不解析，已儲存的記錄照原樣讀出與顯示。掃描時略過了這類項目，結果會與預算用完一樣標示為不完整：`appliesToScanTruncated`、`knowledgeToReviewTruncated`，或該筆 Knowledge 的 `stalenessUnchecked`。編譯過的 glob 快取改為依筆數與字元數設上限、以 second-chance 方式逐筆淘汰，不再在滿了時整個清空。

## 匯入檢查 applies_to_json

可攜式 JSON 匯入（預覽與匯入，REST、Web 與 `pnpm db:import`）檢查 `knowledge` 與 `knowledge_candidates` 的 `applies_to_json`：必須是最多 100 筆、每筆最多 4,096 字元的文字陣列。這是結構上限，刻意比寫入限制（30 筆、1,000 字元）寬：寫入時遮蔽憑證會把短的密碼換成較長的標記（8 字元的連線字串密碼變成 37 字元的 `[REDACTED:connection_string_password]`），合法的 1,000 字元項目存下來可能約 2,700 字元，舊版也可能存過較長的值。這類項目照原樣匯入、永遠不比對，掃描時照上一節標示不完整；測試會遮蔽一個 1,000 字元的項目、匯出、以 0 筆衝突重新匯入並讀回原樣。只有超過結構上限的清單（任何版本都不會寫出）會與無效 JSON 一樣整份拒絕，顯示「匯入檔格式錯誤：knowledge.applies_to_json 必須是最多 100 筆、每筆最多 4,096 字元的文字清單。」，不寫入任何資料，訊息不含檔案內容。實際匯出檔複本匯入時 0 筆衝突、各表筆數相同，已提交的 schema 31 與 32 fixture 照常匯入。可匯入的最大清單讀取時同樣計入預算（先計 JSON 文字，之後最多 30 個寫入限制內的項目），掃描逐筆讀取資料列，預算用完就不再讀。星號上限仍不在匯入時套用。

其他會在讀取時依大小跑迴圈的 `*_json` 欄位都檢查過，沒有一併在匯入時設限：

| 欄位 | 寫入上限 | 讀取時與大小成正比的工作 | 不在匯入設限的原因 |
| --- | --- | --- | --- |
| `sessions.changed_files_json` | 每次 200 筆，merge 會累加，沒有總數上限 | staleness 與 `knowledgeToReview` 逐筆比對、檔案歷史與熱點 | 正常使用就可能超過 200，不能拒絕；比對都已計入預算 |
| `changed_files_provenance_json`、`changed_file_changes_json` | 每次 200 筆，同樣累加 | Session 讀取時合併成 `session.files` | 同上；只在讀單一 Session 時處理一次 |
| `knowledge.tags_json`、`references_json`（含候選） | 30 筆 × 80／1,000 字元 | 輸出與搜尋索引，逐筆一次 | 遮蔽憑證時標記可能比原文長，嚴格限制會拒絕正常匯出；沒有成對比對的迴圈 |
| 決策、圖表、報告區塊等其他 `*_json` | 各自的寫入上限 | 輸出時序列化一次 | 不做成對比對，成本與輸出大小相同；整份匯入仍受 50 MiB 上限 |

## 路徑正規化不再有平方時間

每個儲存與查詢路徑都會經過的正規化，原本有兩個正規表示式在刻意構造的輸入上需要平方時間：移除結尾斜線（1,000 個斜線 354 µs）與移除長數字前的 `#L` 行號（381 µs）。兩者都改為單次掃描，結果相同（2 萬組產生字串與所有實際路徑一致）。

## 未知欄位訊息有長度上限

點名未知欄位的錯誤訊息，每個位置最多列 10 個名稱，名稱與路徑片段最多 64 字元，其餘以數量表示。適用於所有 REST body、`POST /api/export`（改用與其他 body 相同的嚴格解析）、匯入與匯入預覽，以及 `pnpm db:import`；以前大量的長欄位名稱會原樣回傳。

## 修正：commitSha 篩選不分大小寫

`work_list_sessions` 的 `commitSha` 自 1.6.24 起以小寫比對，但 finalize 照原樣保存 sha，所以以大寫保存的 sha 找不到。現在 finalize 與 metadata 更新會把十六進位 sha 存成小寫；篩選先找小寫範圍，前綴含英文字母時再找大寫範圍，同一個 commit 的兩種寫法不再被當成有歧義的前綴。大小寫混合的 sha 不是 Git 的輸出，找不到。實際資料複本有 323 個 sha，沒有任何大寫；不需要 migration。

`knowledgeToReview` 掃描 Session 時用來縮小範圍的片段最多 64 字元，SQLite 的 `instr()` 每個儲存字元最多比較這麼多次；這一段的完全相同比對也計入預算。

## 從 1.6.14 升級

1.6.14 之後所有可能影響既有 Agent、REST client 或匯出檔的變更，集中列在這裡：

- **Schema 與連線**：1.6.24 起第一次啟動時升級到 schema 33，之前會自動建立 migration 前備份；Agent 回報 `restartRequired` 時重新連線 Work Intelligence MCP。仍在執行 1.6.24 之前版本的 Agent 連到已升級的資料庫，會收到 `DATABASE_SCHEMA_VERSION_TOO_NEW`。除了還原 migration 前備份（`pnpm db:restore`），無法降回 schema 33 以下。
- **匯入與匯出**：匯入接受 schema 31（v1.6.7 起）到 33 的匯出檔，更舊或更新的檔案以 `unsupported_schema` 拒絕（1.6.24）；1.6.26 起另外拒絕超過 100 筆或單筆超過 4,096 字元的 Knowledge 與候選 `applies_to_json`（任何版本都不會寫出）。匯出檔新增 `knowledge_candidates.overlaps_json`（1.6.24），schema 32 的檔案匯入時此欄為空。
- **REST**：body 的未知欄位，以及整組驗證的查詢參數中的未知欄位，回 400 `invalid_input`，不再默默忽略（1.6.25；匯出 body 自 1.6.26）。以前回 500 的情況，唯讀資料庫改回 503 `database_read_only`、磁碟已滿改回 507 `database_disk_full`（1.6.25）。`GET /api/knowledge` 也比對 `appliesTo` 路徑（1.6.16）。
- **MCP 錯誤代碼**：新增 `DATABASE_READ_ONLY` 與 `DATABASE_DISK_FULL`（1.6.25）；啟動時遇到忙碌、唯讀或磁碟已滿，之後的呼叫會再試，不必重新啟動。
- **回應形狀**：`work_finalize_session`（1.6.20）與 `work_update_session_metadata`、`_summary`、`_title`、`_work_summary`（1.6.22）回傳回條，不再回顯 Session，需要時以 `work_get_session` 讀取。以 `projectRoot` 限定的呼叫只列一次專案，項目省略 `projectId`／`projectName`（1.6.15）。`work_get_context` 的 `omitted` 只保留簡短指標（1.6.15），`relevant.outstandingItems` 每筆只有 id、來源 Session 與最多 240 字元的摘錄（1.6.18）。`work_get_report_context` 只在 `sessionPage: 1` 回傳報告區塊，每個專案與風險最多列 8 個 `sourceSessionIds`，證據只以 id 指出 Session（1.6.19）。`work_get_knowledge_page_context` 的 Session 是預覽（1.6.19）。`work_search_knowledge` 嚴格比對沒有結果時，`items` 為空，並帶 `match: "relaxed"` 或 `"none"` 與 `relaxedMatches` 摘要（1.6.16）。
- **上限與標示**：寬鬆 Knowledge 搜尋最多使用 5 個像路徑的詞，`appliesTo` 掃描最多讀最新的 2,000 筆 Knowledge（1.6.18）。新的 `appliesTo` glob 超過 16 個星號時，新增與候選審核會拒絕，更新會接受並回傳 `warnings`（1.6.23）。`appliesToScanTruncated`、`knowledgeToReviewTruncated` 與 `stalenessUnchecked` 標示被比對預算截斷的掃描（1.6.23），1.6.26 起也標示略過了超限項目的掃描；`relatedOutstandingItems` 與 context 的未結項最多讀 2,000 筆並帶 `truncated`（1.6.23）。
- **新增、不影響既有用法**：`work_get_file_history`（1.6.17）、`work_get_session` 的 `session.files`（1.6.18）、候選的 `overlaps`（1.6.18，1.6.24 起保存）、finalize 的 `knowledgeToReview`（1.6.20）、`work_list_sessions` 的 `commitSha`（1.6.24）。

## 未納入

- staleness 讀取前載入專案後續 Session 的變更檔案，成本隨歷史筆數增加，沒有計入比對預算；它與儲存的樣式長度無關。
- `knowledgeToReview` 第二階段每個候選的 SQL 篩選會掃描後續 Session，只有回傳的資料列計入預算。
- 預算以開發機的量測換算時間；較慢的機器上同樣的預算會花更久。
- Web 仍不顯示截斷與 `stalenessUnchecked` 標示。

## 升級

1. 取得 1.6.26 原始碼後執行 pnpm bootstrap（或 pnpm install --frozen-lockfile、pnpm build 與 pnpm check）。
2. 若已安裝登入自動啟動服務，執行 pnpm service:restart，確認輸出「服務已在執行 1.6.26」。
3. 透過 launcher 連線的 Agent 會自動切換到新版並收到工具清單更新通知，不需要重新連線；只有 Agent 回報 `restartRequired` 時才重新連線一次。

完整流程見發行與升級指南（docs/release.md）。
