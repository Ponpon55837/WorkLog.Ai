# Work Intelligence 1.6.24 更新說明

日期：2026-11-12。應用程式與 plugin 版本為 1.6.24；資料庫 schema 由 32 升到 33，第一次啟動時自動 migration。

這一版是這一輪的第一次 schema 變更，只新增：一個可為空的欄位與兩個索引，不刪除或改型任何欄位，也不改寫既有資料列。新欄位為空時，所有既有行為都與之前相同。

## 升級

- 第一次以新版開啟 schema 31 或 32 的資料庫時，會先建立 `pre-migration-vN-...` 備份，再在一個交易內套用 migration；備份失敗時不升級。再次開啟不會再遷移或再備份。
- 舊版 MCP 連線在升級後會回報 `restartRequired`，請重新連線 Work Intelligence MCP。
- 可攜式 JSON 匯入現在接受 schema 31 到 33 的匯出檔（v1.6.7 以後匯出）。之前只接受與程式完全相同 schema 的檔案，所以若不修正，這一版會拒絕所有先前的匯出檔，包括 v1.6.9–v1.6.23 寫出的 schema 32 檔案。之後 migration 新增的欄位以匯入預設值補上，舊檔沒有的資料表視為空。比程式新的匯出檔仍以 `unsupported_schema` 拒絕，訊息請使用者先更新 Work Intelligence；Web 顯示相同的建議。

Migration 33 的完整內容：

```sql
ALTER TABLE knowledge_candidates ADD COLUMN overlaps_json TEXT;
CREATE INDEX idx_sessions_commit_sha ON sessions(commit_sha);
CREATE INDEX idx_sessions_live_project ON sessions(project_id) WHERE voided_at IS NULL;
```

| 對象 | 結果 |
| --- | --- |

## 候選審核看得到重疊提示

v1.6.18 起，`work_submit_knowledge_candidates` 會為每筆候選找出最多 3 筆相似的同專案記錄（可能與 active Knowledge 重複、與已封存的 Knowledge 重疊、與已拒絕的候選重疊），但只放在回應裡，真正做決定的人在 Web 看不到。現在：

- 提示與候選一起保存，只存 relation、對象類型與 id、送出時的狀態與分數，不存文字，所以沒有需要遮罩的內容。寫入前以嚴格的 Zod schema 驗證；讀取時不是這個格式的值一律當作沒有提示，不會顯示也不會出錯。
- `GET /api/knowledge/candidates` 以 `overlaps` 回傳；標題在讀取時只從候選所屬專案的記錄取得，其他專案的記錄不會被列出名稱；對象已不存在時省略標題。
- Web 候選卡片顯示一段簡短提示，說明這只是參考、由你決定，列出關係、相似紀錄與相似度；相似的 Knowledge 仍存在時可點標題開啟它。接受、修改後接受與拒絕都不受影響。繁中與英文、深色與淺色主題都有。
- 對已完成的請求重送相同內容時，回傳保存的提示而不重新計算，所以之後對象狀態改變也不會改變標示。schema 33 之前送出的候選沒有保存提示，重送時照舊重新計算。
- 可攜式匯出與匯入帶著這個欄位，視為本機衍生值：本機副本沒有提示（舊版送出）時視為同一筆候選，略過而不是衝突，也不覆寫本機值。它不納入搜尋索引，專案永久刪除時隨候選一起刪除。

## 依 commit 找 Session

`work_list_sessions` 新增 `commitSha`：完整 sha 或至少 7 個十六進位字元的前綴（7–64 字元，其他字元一律拒絕），只在範圍內的 tracked 專案比對。Agent 從 `git blame` 或 `git log` 拿到 commit 後，可以直接問是哪個 Session 做的。前綴符合範圍內超過一個 commit 時回傳 `ambiguous_commit_sha`，不列出 Session。已知限制：記錄的 sha 是 finalize 時看到的 HEAD，可能是這段工作 commit 之前的那個 commit；記錄方式沒有改變。實際資料 328 筆 Session 中 323 筆有 sha。

## 量測

部分索引 `sessions(project_id) WHERE voided_at IS NULL` 以數據決定是否加入：

| 項目 | 5,000 筆 Session | 20,000 筆 Session |
| --- | ---: | ---: |
| Dashboard 的 Session 計數（無索引 → 有索引） | 1.1–1.8 → 0.11 ms | 6.1 → 0.46 ms |
| Session 列表第一頁（與同 build 去掉索引比較，三輪交錯中位數） | — | 3.2 → 1.1 ms |
| commit 前綴查詢（純範圍條件 → rowid 子查詢） | 3.5 → 0.13 ms | — |

- 以 `EXPLAIN QUERY PLAN` 檢查 benchmark 執行的 352 個讀取 statement：21 個改用新索引，沒有任何一個變成全表掃描；commit 索引沒有改變任何既有計畫。
- 整個讀取路徑 benchmark 在 5,000 與 20,000 筆 Session 上與 v1.6.21 交錯三輪比較，沒有路徑在這台機器的執行間差異以外變慢；兩個 join 順序改變的查詢（Session 列表的未結項、已套用 Knowledge 回饋）逐一量 SQL 時間也沒有變慢。
- 新增 benchmark 案例 `listSessionsForAgent (commitSha prefix)`，p90 上限 50 ms。
