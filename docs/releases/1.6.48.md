# Work Intelligence 1.6.48 更新說明

日期：2026-11-17。應用程式與 plugin 版本為 1.6.48；資料庫 schema 維持 33，沒有 schema 變更，也不需要 migration。

## 摘要

- **大型匯入、預覽與匯出改在獨立子行程串流處理**：專案資料的匯入預覽、匯入與匯出，以及備份與整庫匯出，從 worker thread 改為由 API 行程 `fork` 出的背景子行程（有自己的 heap 上限，預設 1 GiB，`WORK_INTELLIGENCE_BACKGROUND_HEAP_MB` 可調）執行。
  - 匯入檔先串流存到資料庫旁的 `tmp/import-*`（權限 0700／0600），再逐列讀取驗證；資料列的文字移到同目錄的暫存檔，記憶體只保留合併規劃需要的欄位。匯出直接逐列寫成檔案再串流下載。記憶體不再隨檔案大小增加。
  - 子行程記憶體不足時只有子行程結束；API 回 413 `backup_worker_out_of_memory`，訊息為「匯入檔太大，背景處理記憶體不足；後端仍正常運作。」，下一個請求由新的子行程處理。1.6.47 已知的「Node 24 上 worker heap 耗盡可能讓整個後端結束」已修正，並以真實的記憶體耗盡測試（不是注入錯誤）在 CI 的 Node 24 三個 OS 上驗證。
  - REST、內建 fallback 與 `db:import` 使用同一個串流讀取器；`db:import` 在 CLI 行程內串流（不經子行程）。匯入仍是全有或全無，預覽與衝突結果、匯出的位元組都與 1.6.47 相同（逐位元組測試）。`--dry-run` 也走串流路徑。
  - 啟動時刪除 1 小時前留下的 `tmp/import-*`、`tmp/export-*`（例如程序被終止時留下的）。
- **匯入上限由 50 MiB 提高到 256 MiB**（REST、CLI 與 Web UI 相同）。上傳前檢查磁碟可用空間至少為檔案大小的 2.5 倍，不足時回 507 `database_disk_full`（「磁碟空間不足，無法暫存匯入檔；請先釋出空間再試。」）；宣告的 Content-Length 已超過上限時不讀 body 直接回 413。
  - 每個資料表最多 200,000 列（未改變的既有限制）。以每個 Session 約 14 筆工作事件計算，單一匯出檔約可容納 14,000 個 Session；超過時錯誤訊息會指出是哪個資料表，例如「匯入檔格式錯誤：work_events 超過 200,000 列的上限。」。
- **Web UI 匯入不再在瀏覽器讀取或解析檔案**：選擇的檔案以原始 body 串流上傳到新的 `POST /api/import/staged`，伺服器驗證一次後回傳暫存 id、檔案中的專案清單與第一次預覽；之後的預覽與匯入只帶 id，不必重新上傳。暫存檔在匯入成功、取消、30 分鐘後或下次啟動時刪除，同時最多保留 2 份。上傳與檢查期間顯示進行中狀態並停用選擇檔案。舊的 `{bundle}` JSON 端點保留不變。詳見 [REST API](../rest-api.md)。
- **桌面修復成功回饋**：使用者在修復視窗按下修復並成功後，視窗顯示「✓ 已恢復」與資料庫路徑、專案數，送出一次「Work Intelligence 已可使用」系統通知（通知失敗不影響結果），短暫停留後關閉修復視窗並開啟 Dashboard 一次。開機時的 `--background` 啟動與自動重試不會這樣做；修復失敗時保留視窗，只顯示這次的錯誤。後端就緒訊息新增選用的 `projectCount`（讀取失敗時省略，不影響啟動）。
- **桌面 App 圖示與 WI 品牌標誌一致**：`apps/desktop/build/icon.svg` 改由 `apps/web/public/favicon.svg` 產生（同一來源，測試鎖定幾何與顏色），重新產生 `.png`、`.ico`、`.icns` 與工作列圖示。macOS 選單列改用單色 template 圖示（`trayTemplate.png`／`@2x`），會隨淺色與深色選單列調整；Windows 與 Linux 的工作列圖示是深色圓角方形，淺色與深色工作列都看得清楚。NSIS 安裝與解除安裝程式、Windows 執行檔使用 `build/icon.ico`，macOS App 與 DMG 使用 `build/icon.icns`。

## 修正

- 只含空白的匯入 request body，或空的匯出檔，回 400「Invalid JSON request body.」（`db:import` 為「匯入檔不是有效的 JSON。」），與 1.6.47 相同。
- 專案匯出在含有架構圖的資料庫上，不再先寫完整份、遇到架構圖後再重寫一次：寫入前以一次索引查詢決定是否載入遮蔽。

## 測試

- 刪除匯入結構預檢與其單元測試、bench，以及注入 worker 記憶體不足的測試輔助程式；改以真實的子行程記憶體耗盡（32 MiB heap）測試 413 與後端存活。
- 新增：傳輸暫存目錄（清理、空間檢查、507、提早 413）、串流讀取器邊界情況（跨 1 MiB 邊界的跳脫字元、surrogate pair、多位元組 UTF-8、BOM、尾端垃圾、截斷、重複鍵、深層巢狀、單列過大）、48 個損毀檔與 1.6.47 錯誤訊息一致性、匯入中途終止子行程（資料庫完整、全有或全無、之後可重新匯入）、暫存匯入（過期、未發出的 id、使用中不刪除、上限、匯入後刪除、取消）、Web store 與超過 50 MiB 的 E2E 匯入。
- 所有傳輸測試都在「資料列文字全部移到暫存檔」的正式設定下執行；Proxy guard 測試保留。

## 與 1.6.47 不同的錯誤訊息

- 單一資料列超過 32 MiB：原為 400「Too big: expected string to have <=2000000 characters」，現為 413「匯入檔中有單筆資料過大，無法匯入。」。
- 大量極小 JSON 物件（原本由預檢擋下）：原為 413「匯入檔內容結構過於龐大…」，現為 400「匯入檔格式錯誤：內容結構異常或過於龐大。」。
- 資料表超過 200,000 列：訊息改為指出資料表名稱（見上）。

## 不變的部分

- schema 33，沒有 migration。匯出檔格式（`formatVersion` 1）與位元組不變。
- WAL 與 busy_timeout 行為不變：匯入寫入期間 API 仍可讀取。

## 升級

照常更新即可；不需要任何手動步驟。

## 未驗證與已知限制

- Web UI 上傳沒有百分比進度（瀏覽器 fetch 無法回報上傳進度），只顯示進行中狀態。
- 這個 API 沒有使用者 session，暫存 id 以 32 bytes 隨機值作為唯一憑證，只回給上傳的請求；仍受既有的 Origin 與 Host 檢查保護。
- 每次大型操作後，背景子行程閒置 1 秒即結束，下一次操作要重新 fork（本機約 100 ms）。

## 待實機驗收

- Windows 11 與 macOS 實機上的 256 MiB 匯入、修復成功回饋（通知、Dashboard 只開一次）與新的圖示外觀。
