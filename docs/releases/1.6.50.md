# Work Intelligence 1.6.50 更新說明

日期：2026-11-17。應用程式與 plugin 版本為 1.6.50。資料庫 schema 仍為 33，沒有 schema 變更，不需要 migration。

## 摘要

本版收尾桌面版階段 4 的舊服務處理與 Agent 接管：

- 在 App 內一鍵「停用舊的登入服務」（`pnpm bootstrap` 留下的服務）；
- Windows 停止舊服務時，確認 runner 的子孫程序都已結束（DT-13）；
- 「改由桌面 App 管理」只接管使用 App 目前資料庫的 checkout 項目；使用其他資料庫時改為提供「改用這份資料庫」；
- 桌面預覽可要求唯讀的 `PRAGMA quick_check`。

### 停用舊的登入服務

- **入口**：首次執行頁與修復視窗的舊服務卡片上的「停用舊的登入服務…」，以及工作列的同名項目（開啟修復視窗）。Web 狀態頁不提供這個按鈕。
- **適用範圍**：只限偵測結果「辨識得出」的服務定義，也就是內容與 `pnpm service:install` 寫入的一致，且知道 checkout 的位置。辨識不出時不提供按鈕，畫面照舊提供移除指令。
- **先預覽**：按下後先顯示會發生什麼，不做任何變更：
  - 會停下舊服務，並移除它在登入時自動啟動的設定；資料庫與備份都不會被刪除；
  - macOS 與 Linux：「舊服務會先把手上的工作完成再停下。」
  - Windows：「正在執行的舊服務會被立即結束；已儲存的資料不受影響，正在寫入的一筆可能需要重做。」
  - 舊服務使用 App 的資料庫時：「停下之後，App 會先檢查這份資料庫，沒有問題才會使用。」
  - 實際執行的指令只放在可展開的「詳細步驟」裡。
- **匯入或備份中**：舊服務看起來正在匯入（資料庫旁的傳輸暫存區有一小時內、帶標記檔的 `import-*` 資料夾）或備份（備份資料夾裡有擁有者程序仍在執行的暫存資料夾）時，預覽會提醒「舊服務可能正在匯入或備份，建議稍後再停用。」，按鈕改為「仍要停用」，由使用者決定。
- **確認**：按「停用」後會再跳出系統對話框確認，預設按鈕是「取消」。
- **只動預覽過的那一份**：
  - 動手前會重新偵測。服務定義的內容（SHA-256）、checkout 或連接埠與預覽時不同時，什麼都不做，並請使用者重新開始。
  - 刪除定義檔前會再確認它仍是同一個一般檔案（不是符號連結），內容雜湊也相同。
  - 指令一律以參數陣列執行，不經過 shell，只使用固定的服務名稱（`ai.workintelligence.server`、`work-intelligence.service`、`\Work Intelligence`）。
- **步驟**：與 `pnpm service:uninstall` 相同：
  - macOS：`launchctl bootout`，再刪除 plist；
  - Linux：`systemctl --user disable --now`，刪除 unit，再 `daemon-reload`；
  - Windows：`schtasks /End`，結束這個 checkout 的 runner 程序樹（`taskkill /PID <pid> /T /F`），再 `schtasks /Delete` 並刪除 XML 副本。
- **先證明停下，再移除**：等連接埠釋放；Windows 還要等 runner 程序樹裡的每個程序都結束，最多約 15 秒。逾時就不移除任何設定，請使用者稍後再試。最後再偵測一次，必須已偵測不到。
- **資料庫檢查**：舊服務使用的是 App 的資料庫時，App 會先以唯讀方式執行 `PRAGMA quick_check`，通過後才使用它。沒有通過時：
  - 記錄 `DB_INTEGRITY_CHECK_FAILED`「資料庫檢查沒有通過」；
  - 在修復視窗列出這份資料庫；
  - 不會啟動。
- **之後**：
  - 只有在「手動開啟的 App、已有設定、後端沒有在執行」時才提供「立即啟動」；
  - App 不會自行啟動；
  - 以 `--background` 啟動時不提供「立即啟動」。
- **操作日誌**：整個停用在操作鎖下執行，並以新的 `legacy-disable` 類型寫入操作日誌。

### Windows：結束 runner 的子孫程序（DT-13）

- **只結束這個 checkout 的 runner**：只結束命令列含有這個 checkout 的 `scripts\service-runner.mjs` 的 `node.exe`。比對時：
  - 不分大小寫，`/` 與 `\` 視為相同；
  - 路徑必須獨立出現，不能只是更長路徑的一部分。
- **不依連接埠或程序名稱結束程序**：其他程序一律不結束。
- **等整棵程序樹結束**：pnpm、舊伺服器與 conhost 這些子孫程序，依父程序編號找出後只等待、不單獨結束。所以即使 Windows 重複使用了程序編號，最壞情況也只是等待逾時、不移除設定，不會結束無關的程序。

### 「改由桌面 App 管理」只接管同一份資料庫

- **原則**：接管後，MCP 會保留原本的資料庫，hook 則會改用 App 的資料庫（ADR-39）。所以只有兩者是同一份資料庫時，才能保證接管後還寫入同一份。
- **比對方式**：以檔案身分比對 checkout 項目使用的資料庫與 App 的資料庫，所以硬連結也算同一份。
- **不同的資料庫**：
  - checkout 用的是其他資料庫（明確設定的 `WORK_INTELLIGENCE_DB`，或 checkout 預設的 `data/work-intelligence.sqlite`）時，不接管、也不改寫任何檔案；
  - 卡片會說明使用的是哪一份資料庫，並提供主要按鈕「改用這份資料庫」。按下後，修復視窗會以唯讀方式預覽那份資料庫，使用者確認後才切換。

### 唯讀的資料庫完整性檢查

- **協定**：桌面子程序的預檢訊息新增選填的 `quickCheck: true`。
- **檢查方式**：只在同一個唯讀連線上執行 `PRAGMA quick_check`，只檢查是 Work Intelligence 的資料庫、且 schema 不比這個版本新的檔案。
- **沒有通過時**：結果為 `unreadable`，原因固定為「the database failed its integrity check」，不帶 SQLite 原始訊息或路徑。
- **用途**：一般的預覽不受影響，目前只有停用舊服務後會要求這項檢查。

## 變更

- **工作列**：舊服務的項目由「如何移除舊服務」改為「停用舊的登入服務…」，一樣開啟修復視窗。

## 測試

- **桌面 smoke**：
  - 停用流程：預覽不做任何變更，指令只在「詳細步驟」裡，匯入中的提醒與「仍要停用」都會出現；確認後只移除預覽過的定義，並提供「立即啟動」，按下才會啟動；
  - 資料庫檢查沒有通過：不提供「立即啟動」，記錄錯誤，也不會自行啟動；
  - 其他資料庫的 checkout 不會被接管，「改用這份資料庫」會在修復視窗預覽那份資料庫；
  - preload bridge 的方法清單更新為完整的新清單。
- **單元測試**：
  - 每個平台的步驟，並且只使用固定名稱；
  - 每個中止情形都會中止，而且不移除任何東西：
    - 定義消失、被修改、不再辨識得出，或指向其他 checkout；
    - 連接埠一直被占用；
    - 刪除前內容被換掉；
    - 符號連結；
    - Windows 程序清單讀不到；
    - runner 的子孫程序還在；
    - `schtasks /Delete` 失敗；
  - runner 命令列的比對：大小寫、斜線方向、重複的分隔符號，以及前後還接著其他路徑的情形；
  - Windows 程序樹（含父程序迴圈）；
  - 匯入與備份中的判斷；
  - 頁面輸入只接受不透明的 id 與布林值；
  - 偵測結果只為辨識得出的定義帶上內容雜湊；
  - agent-setup 的同一份資料庫判斷（含硬連結、相對與絕對路徑、檔案不存在的情形）；
  - 預檢的 `quick_check`：毀損的資料庫只有在要求檢查時才判為 `unreadable`，檢查後檔案內容完全不變。

## 升級

照常更新即可，不需要任何手動步驟。

## 未驗證與已知限制

- 「仍要啟動」只在 App 執行期間有效；App 重新啟動後，如果舊服務仍在，會再詢問一次。
- 停用後無法在 App 內復原；要重新安裝舊服務，請在 checkout 執行 `pnpm service:install`。
- 舊服務因連接埠一直被占用而沒有移除設定時，在 macOS 上它可能已經從 launchd 卸載，所以偵測會暫時找不到它；App 的連接埠檢查仍會指出衝突。

## 待實機驗收

- Windows 11 與 macOS 實機上的：
  - 停用流程：真實的 LaunchAgent 與工作排程器、真實的 runner 程序樹；
  - 停用後的資料庫檢查；
  - 「改用這份資料庫」。
