# Work Intelligence 1.6.49 更新說明

日期：2026-11-17。應用程式與 plugin 版本為 1.6.49。資料庫 schema 仍為 33，沒有 schema 變更，不需要 migration。

## 摘要

本版完成桌面版階段 4 的第二部分：

- 首次執行頁（DT-01）；
- 在 App 內設定 Agent；
- 把 checkout 的 Agent 設定改由桌面 App 管理；
- 偵測舊的登入服務。

### 首次執行頁（DT-01）

- **觸發條件**：全新安裝（沒有 `desktop-settings.json`）時才顯示。已有設定的安裝（由 1.6.47、1.6.48 升級）一律不顯示，照常啟動，設定不變。有 smoke 測試涵蓋這個情形。
- **選項**：第一個畫面就有「使用預設設定開始」，按一下即可開始。這個按鈕在偵測還沒結束時就已出現並可使用。其他選項都是選用的：
  - 沿用偵測到的既有資料庫（「沿用這份資料」）；
  - 選擇其他檔案；
  - 登入時在背景執行（預設關閉）；
  - 展開的進階資訊：資料位置、本機網址、備份位置。
- **唯讀偵測**：偵測的來源包括：
  - 獨立版的預設位置；
  - 環境變數；
  - 舊的登入服務定義；
  - Agent 設定裡指向 checkout 的 MCP 項目。

  每個不同的資料庫都只做一次唯讀預覽，結果顯示狀態與專案數。需要升級 schema 的資料庫，要先勾選同意才能使用。
- **寫入時機**：使用者選擇並成功啟動之前，不寫設定、不建立資料庫，也不占用連接埠。
  - 「使用預設設定開始」會在預設位置建立新的空資料庫，啟動成功後才寫入設定，並開啟 Dashboard。
  - 啟動失敗（例如連接埠被占用）時，會刪除剛建立的空資料庫（ADR-27），設定也不會寫入。
- **之後再說**：選「之後再說」，或以 `--background` 啟動的全新安裝，不會跳出視窗；工作列選單會出現「完成首次設定…」。
- **完成後**：畫面提示下一步「設定 Agent」。

### 在 App 內設定 Agent

- **入口**：App 視窗的「設定 Agent」頁，也可以從工作列的「設定 Agent…」或 `--open-agent-setup` 開啟。
- **卡片**：每個 Agent（Codex、Claude Code）一張卡片，顯示：
  - 狀態（ADR-34）；
  - MCP 與 hook 目前由誰管理；
  - 偵測到的 checkout。
- **只看不寫**：打開頁面不寫入任何檔案。「預覽變更」只計算計畫並顯示每個檔案的差異，家目錄一律顯示為 `~`。
- **套用**：「套用變更」只套用剛才預覽的那份計畫，並寫入操作日誌（DT-21）。計畫有衝突時不能套用。
- **測試連線**：經由固定 launcher 完成 MCP `initialize` 與 `tools/list`。
- **復原**：「復原上次變更」依日誌把檔案還原。App 中途結束時，下次啟動會先處理未完成的日誌。

### 「改由桌面 App 管理」

- **按鈕**：Agent 設定裡有手動寫入、指向 checkout 的 Work Intelligence 項目時，頁面會出現「改由桌面 App 管理…」。
- **流程**：一樣先預覽差異，確認後才改寫為指向固定 launcher，也可以復原。不會在背景默默改寫。
- **無法接管的項目**：辨識不出的項目不會接管，頁面會說明原因。

### Web 的入口

- **條件**：只在由桌面 App 管理時（`/api/system/status` 的 `desktop.managed`）出現。
- **按鈕**：狀態頁的「在桌面 App 設定 Agent」按鈕會請 App 開啟 Agent 頁（`POST /api/desktop/open-agent-setup`，202，每秒最多一次）。Web 本身不寫任何設定。

### Agent 使用 App 的資料庫（Q1，ADR-39）

- **讀取方式**：沒有設定 `WORK_INTELLIGENCE_DB` 時，固定 launcher 每次執行都讀 App 設定裡的 `desired.databasePath`。MCP 與兩個 hook 因此一定使用 App 正在使用的資料庫，App 換資料庫後也一樣。
- **優先順序**：明確設定的 `WORK_INTELLIGENCE_DB` 一律優先。
- **設定無效時**：退回獨立版的規則，MCP 輸出一行 stderr，hook 保持靜默。
- **成本**：每次 hook 的額外成本在 Linux 上中位數 0.44 ms（預算 5 ms）。

### 舊的登入服務（`pnpm bootstrap`）

- **偵測方式**：App 以唯讀方式偵測 `pnpm service:install` 留下的服務（macOS LaunchAgent、Linux systemd user unit、Windows 工作排程器）。
- **警告**：服務可能使用同一個資料庫時，首次執行頁、修復視窗與 Web 狀態頁都會顯示：

  > 偵測到舊的登入服務（pnpm bootstrap）也在使用這份資料庫；同時執行兩個後端可能造成問題

  警告附上確切的移除指令（`cd <checkout> && pnpm service:uninstall`；不知道 checkout 時，改附作業系統的移除指令），可以一鍵複製。
- **啟動前確認**：App 在這個資料庫上不會自行啟動後端（`LEGACY_SERVICE_ACTIVE`，不會自動重試），使用者必須按「仍要啟動」並再次確認。這個選擇只在 App 執行期間有效，不寫入任何地方。
- **其他資料庫**：舊服務使用的是另一個資料庫時，不受影響。
- **連接埠衝突**：連接埠被占用，而占用者是舊服務時，訊息會直接指出：「連接埠已被舊的登入服務（pnpm bootstrap）使用。請先移除舊服務，再重試。」
- **不會自動移除**：App 不會停止、修改或移除舊服務。一鍵停用需要另外核准，延到 1.6.50。

## 測試

- **桌面 smoke**：
  - 升級（已有設定）不顯示首次執行頁；
  - 全新安裝：在使用者選擇前不寫入；「使用預設設定開始」後成為 MANAGED，並寫入設定；
  - 舊服務在同一個資料庫時擋下啟動，按「仍要啟動」後才啟動；在其他資料庫時不受影響；
  - Agent 頁：預覽不寫入，套用只寫入預覽過的內容，測試連線成功，復原後家目錄與套用前完全相同；
  - 第二次啟動帶 `--open-agent-setup` 會在執行中的 App 開啟 Agent 頁；
  - preload bridge 的方法清單更新為完整的新清單。
- **打包 smoke**：Agent skill 以單一檔案放在 asar 之外，內容與 repository 完全相同。
- **單元測試**：
  - 首次執行的畫面狀態；
  - 舊服務的關聯判斷（含 Windows 路徑大小寫）；
  - 工作列項目；
  - `--open-agent-setup`；
  - 家目錄遮蔽（不會誤遮 `/home/tester2` 這類同前綴的路徑）；
  - `LEGACY_SERVICE_ACTIVE` 不自動重試；
  - 中英文文案的鍵一致；
  - 建立新資料庫的預檢（只在檔案確定不存在時建立，不覆寫既有檔案）；
  - agent-setup 的接管、復原與差異。

## 升級

照常更新即可，不需要任何手動步驟。已有設定的安裝不會看到首次執行頁。

## 未驗證與已知限制

- 一鍵停用舊的登入服務尚未提供（1.6.50）；目前請依畫面上的指令自行移除。
- 「仍要啟動」只在 App 執行期間有效；App 重新啟動後，如果舊服務仍在，會再詢問一次。
