# Work Intelligence 1.6.16 更新說明

日期：2026-11-12。應用程式與 plugin 版本為 1.6.16；資料庫 schema 維持 32，不需要 migration。

## 知識搜尋不再停在空結果

`work_search_knowledge` 是嚴格清單搜尋：每個詞都必須出現在某個欄位。只要有一個詞對不上、或中文換了說法，就會得到空結果，Agent 也無從得知原因。以實際資料（64 筆 Knowledge，其中 33 筆已封存）的 41 個 Agent 式查詢量測，30 個得到空結果：22 個要找的是已封存的記錄，7 個要找的 active 記錄其實存在，用 `work_recall` 都找得到。

這一版的做法：

- 嚴格比對有結果時，回應與以前相同，另加 `match: "strict"`。Web 知識清單使用同一個嚴格搜尋，原本有結果的查詢結果不變。
- 嚴格比對沒有結果時，`items` 維持空陣列，改在同一個專案、`kind` 與狀態內用 recall 的斷詞與排序做寬鬆比對（中文雙字組、識別字拆分、任一詞命中即可），回傳最多 3 筆 `relaxedMatches` 與 `match: "relaxed"`。每筆是摘要而非完整記錄：id、kind、status、標題、最多 3 個 `appliesTo`、`matchedTerms`（共有的查詢詞元）、`matchedPaths`（命中的 `appliesTo`／references 路徑），以及以命中詞為中心最多 400 字的內文 `excerpt`（被截斷時帶 `excerptTruncated`），讓 Agent 分得出這是部分符合、不是答案。要讀完整內容時用既有的 `work_get_knowledge_history`。兩者都沒有結果時為 `match: "none"`。
- 空結果或寬鬆結果時，若其他狀態有符合記錄，附上 `otherStatusMatches`（例如 `{ "archived": 2 }`）與一句 `hint`，告訴 Agent 改傳哪個 `status` 才看得到。只有數量，不含內容。
- 嚴格搜尋也比對 `appliesTo` 路徑，直接查檔案路徑就能找到針對該檔案記錄的 Knowledge；REST `GET /api/knowledge` 與 Web 清單同樣受惠。

寬鬆比對與計數都只在通過 policy gate 的範圍內進行，不會透露其他專案或 paused／ignored 專案的 Knowledge。

## 實測結果

同一份實際資料、同樣 41 個查詢：

| 項目 | 1.6.15 | 1.6.16 |
| --- | --- | --- |
| 嚴格比對零命中 | 30 | 29（1 個路徑查詢改由 `appliesTo` 命中） |
| 空回答（Agent 什麼都沒拿到） | 30 | 0 |
| 7 個 active 目標漏查 | 0 個找回 | 7 個全部以第 1 名找回 |
| archived 目標查詢附上數量 | 0／22 | 21／21（第 22 個是路徑查詢，改由 `appliesTo` 嚴格命中另一筆 active 記錄） |
| 寬鬆回答大小 | — | 1,003–2,633 字，中位數約 2,000 字 |
| 單次查詢時間 | — | 1–9 ms |

5,000 筆合成 Session 的效能測試中，寬鬆備援的 p90 約 34 ms，門檻 250 ms。同一次排序同時算出各狀態的數量，比分開計算快約四成。

## Recall 的 termHits 更準確

`work_recall`、`work_search` 與 `work_get_context` 的 `termHits` 不再列出單一虛字（的、與、讓等），三字以上連續的中文詞只要有一半雙字組出現在同一筆紀錄就算找到，不再因為沒有完整詞段而回報 0。同一組 41 個查詢中，`termHits` 回報「完全沒命中」的查詢由 13 個降到 2 個，剩下的都是真的沒出現的英文詞。`work_recall` 的 `confidence` 只依實際回傳的 hit 判斷。排序沒有改變，retrieval-quality 基準不受影響。

## 讀取稽核

帶 `q` 的知識搜尋在讀取稽核記成 `knowledge_strict`、`knowledge_relaxed` 或 `knowledge_none`，不算失敗讀取，之後可依實際使用量測零命中率。同時修正 1.6.15 的回歸：以 `projectRoot` 限定的回應不再逐筆帶 `projectId`，稽核因此漏記其中的 Knowledge 與 Session id，現在會照常記錄。

## 未納入

- `appliesTo` 沒有加入全文索引：索引內容改變需要 migration 重建索引，所以寬鬆比對改為讀取範圍內帶 `appliesTo` 的記錄在記憶體比對。
- 只靠固定同義詞（例如 endpoint／路由）命中的記錄不列入寬鬆結果，因為每筆都必須說得出共有哪些詞。
- 實測中 `work_recall` 對 archived 目標查詢回報 `high` 的情況，來自確實回傳的 Session hit，不是未回傳的結果，所以 confidence 規則沒有改。

## 升級

1. 取得 1.6.16 原始碼後執行 pnpm bootstrap（或 pnpm install --frozen-lockfile、pnpm build 與 pnpm check）。
2. 若已安裝登入自動啟動服務，執行 pnpm service:restart，確認輸出「服務已在執行 1.6.16」。
3. 透過 launcher 連線的 Agent 會自動切換到新版並收到工具清單更新通知，不需要重新連線；只有 Agent 回報 `restartRequired` 時才重新連線一次。

完整流程見發行與升級指南（docs/release.md）。
