# Work Intelligence 1.6.42 更新說明

日期：2026-11-16。應用程式與 plugin 版本為 1.6.42；資料庫 schema 維持 33，沒有 schema 變更，也不需要 migration。

## 摘要

- **桌面版階段 0（契約與測試基座）**：新增純 TypeScript 套件 `@work-intelligence/desktop-core`（`packages/desktop-core`）。它不含 Electron，也不打包進 plugin 或 standalone 套件。內容包括設定存取（`DesktopSettingsV1`，原子寫入、讀取失敗時關閉）、DB 來源解析（唯讀候選、狀態分類、依檔案身分分組）、ServiceOwner 狀態機與檔案式操作日誌，以及單一程序內的 `OperationCoordinator`。這些是可測試的契約，尚未接到任何桌面 App。
- **DB 身分策略定案（ADR-36）**：身分由三部分組成：正規化的真實路徑、檔案 ID（dev／ino），以及唯讀取得的血統指紋（`schema_migrations` 最小版本那一列 `version|name|applied_at` 的 SHA-256）。同一檔案視為同一個資料庫；血統相同但檔案不同視為副本，需要使用者選擇；嵌入 UUID 延後到日後經授權的 migration 再補上。
- **啟動前的唯讀 preflight**：`apps/server/src/database-preflight.ts` 在建立任何可能 migration 的 store 之前，以唯讀方式檢查檔案身分、血統、schema 相容性與 sidecar 狀態；提交前會重驗路徑、檔案與血統是否已被替換。`startApi({ database })` 的已驗證入口以重驗後的實際路徑開庫，並使用新的 `WorkIntelligenceStore` 選項 `requireExistingDatabase`（檔案不存在時回 `DATABASE_FILE_MISSING`，不會建立空庫），開啟後再比對一次檔案身分。CLI 行為不變。
- **舊寫入端實驗（DT-04）**：以 schema 33（LATEST）與合成的 migration 34 測試。MCP stdio 寫入回 `MCP_RESTART_REQUIRED`；HTTP API 寫入回 503 `server_restart_required`，讀取仍是 200；長駐 Store 程序在提交時回 `DATABASE_SCHEMA_CHANGED`；migration 之後才啟動的舊程序回 `DATABASE_SCHEMA_VERSION_TOO_NEW`。被拒絕的寫入沒有留下任何資料列，所有情境的 `integrity_check` 都回 ok。
- **唯讀不等於 0 寫入（本機觀察）**：在 Node 22.23.4 與 SQLite 3.53.4 上，以唯讀方式開啟已正常關閉的 WAL 資料庫，會在同一資料夾建立 `-wal` 與 `-shm`，關閉後仍保留；主檔的位元組、mtime 與資料列都不變。預覽不會刪除任何 sidecar。
- **測試隔離（DT-36）**：`tests/helpers/isolated-environment.ts` 由所有 Vitest 設定載入。每個測試檔使用自己的暫存家目錄與設定目錄；監聽或連線 3210 會直接失敗。原本會佔用 3210、或探測 3210 的測試已改為隔離環境。
- **備份與匯出 worker 冷啟**：改用精簡入口 `@work-intelligence/storage/backup-export`，不再在冷啟時載入 `zod` 與 schema 套件。首次匯出的中位數由 188.5 ms 降為 64–80 ms，匯出輸出的位元組不變。

## 不變的部分

沒有 schema 變更（33），沒有 migration。支援的 Node 版本範圍不變（22.16 以上的 22.x，或 24 以上）。CLI 行為不變，匯出輸出的位元組不變。`desktop-core` 不打包進 plugin 或 standalone 套件，因此這兩者的內容不因本版而改變。

## 升級

1. 取得 1.6.42 原始碼後執行 `pnpm install`（新增了 workspace 套件 `packages/desktop-core`，並更新了 lockfile），重新建置並重新啟動。已安裝登入自動啟動服務者可執行 `pnpm service:restart`。
2. 不需要 migration，也不需要重新匯入資料。
3. 執行 `pnpm check`，確認 SQLite 一行沒有警告。

## 未驗證與已知限制

- **實機尚未驗證，不得視為通過**：Windows 11 上的檔案 ID、sidecar、檔案鎖與 WAL 行為；macOS 上的對應項目；Codex plugin、Claude Code plugin、MCPB 與手動 stdio 設定的程序組合（DT-04 的組合 4）。
- **DT-04 的結論有範圍**：方案 1（每次交易邊界檢查 schema）已確認為 MCP、HTTP 與長駐 Store 寫入端的主要屏障。方案 2 仍須實作，才能阻止舊 launcher 啟動舊的 MCP；方案 3 保留為備援。未使用本程式碼的外部 MCP 或 CLI 用戶端，schema 閘無法約束。repo checkout 的 MCP 會先回 `MCP_RESTART_REQUIRED`（build identity 檢查），因此 MCP 的結果包含這道前置檢查。
- **`desktop-core` 只有契約與測試**：本版沒有桌面 App、Electron、安裝程式、服務管理、更新或修復視窗。不要把它當成可用的桌面版。
- **SQLite 版本以發行產物為準**：實驗與 CI 使用的是開發機或 CI 的 Node.js 內建 SQLite。發行產物內 bundled SQLite 的版本，仍以 `pnpm check` 與 release 流程的列印為準。
- **匯出欄位清單仍重複**：匯出的欄位清單在 `packages/storage/src/project-data-export-columns.ts` 重複維護，由 drift test（`tests/storage/project-data-export-columns.test.ts`）保護一致性。改為單一來源（`packages/core`）是後續工作。
- **效能數字為單機量測**：`test:performance` 連續 3 次通過，門檻未調整。冷啟數字來自 `packages/storage/bench/worker-cold-start.bench.mjs` 的 15 次執行，不是 CI 門檻。
- 桌面版的實機驗收項目見[發行實機驗收清單](../release-checklist.md)。
