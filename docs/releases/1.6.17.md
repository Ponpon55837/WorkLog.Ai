# Work Intelligence 1.6.17 更新說明

日期：2026-11-12。應用程式與 plugin 版本為 1.6.17；資料庫 schema 維持 32，不需要 migration。

## 修改檔案前，一次查完它的歷史

Agent 修改一個檔案前，最需要知道的是這個檔案以前發生過什麼：被多少 Session 改過、哪些驗證失敗或沒跑、做過哪些決策、還有哪些未結項。以實際資料（328 筆 Session）量測，最常修改的檔案被 22–69 筆 Session 改過，但 `work_get_context(paths)` 不論歷史多長都只給 1 筆相關 Session、1 條決策與最多 1 個未結項；熱點提示只算最近 30 天，五個檔案中有兩個完全沒有提示。要拼出完整樣貌需要約 7 次呼叫、27,000–60,000 字，而且仍只涵蓋 5 筆 Session。

新增唯讀 operation `work_get_file_history`（經由 `work_read`，`tools/list` 不變）。給定 tracked 專案與 1–3 個 repository 相對路徑，每個路徑回傳：

- `totals`：整段歷史的統計——記錄過該路徑的 Session 數、首次與最後日期、各驗證狀態（passed、failed、not_run、in_progress…）的數量、有 decisions 的 Session 數、這些 Session 產生且仍 pending 的未結項數，以及 changed files 超過 20 個的大範圍修改數。
- `recent`：最新的 Session 摘要（預設 5 筆，最多 10 筆），新到舊：id、完成時間、標題、驗證狀態、前兩條 decisions 與 pending 未結項（id 與縮短的文字），其餘以數量表示。
- `attention`：比 `recent` 更早、驗證失敗或未執行的 Session，最多 3 筆；這些是修改前最需要知道的紀錄。
- `omitted` 與 `nextCursor`：說明還有多少更早的 Session 與失敗紀錄沒列出，把 `nextCursor` 以同一個路徑帶回 `cursor` 即可往前翻頁。

回應頂層另列 `appliesTo` 涵蓋這些路徑的 active Knowledge（id 與標題，最多 5 筆），比對規則與 `work_recall` 相同（glob、完全相同、路徑尾段、目錄）。

只採用已記錄的關聯：Session 的 `changedFiles` 含有該路徑才算，不推論「一起修改」或相似檔名。路徑正規化與 changed files 索引相同（分隔符號、大小寫、`./`、Windows 專案根目錄），查詢走既有的檔名索引，不掃描 Session JSON。已作廢的 Session 不列入；非「記錄中」的專案安靜略過；絕對路徑、`~`、磁碟代號與 `..` 會被拒絕；只讀資料庫中的記錄，不讀 worktree。單一路徑回應上限 4,000 字，每多一個路徑再加 3,000 字；超過時依序縮短文字、只保留 id 與數量，最後才捨棄最舊的摘要，統計與 `nextCursor` 仍然完整。這個 operation 與其他讀取一樣記入讀取稽核。

## work_get_context 會指向完整歷史

帶 `paths` 的 `work_get_context` 原本只在路徑最近 30 天被 3 筆以上 Session 修改時顯示熱點提示。現在前 3 個指定路徑只要有歷史就會顯示，並附上整段歷史的 `totalSessions`；當某個路徑的 Session 多於 context 能顯示的數量時，`relevant.fileHistoryReadWith` 指向 `work_get_file_history`。Web 的熱點畫面不受影響。

## 實測結果

同一份實際資料（328 筆 Session），五個最常修改的檔案：

| 檔案 | Session 數（直接計數／回傳） | 有 decisions | pending 未結項 | 回應大小 | 時間（中位數） |
| --- | --- | --- | --- | --- | --- |
| `packages/storage/src/store.ts` | 69／69 | 68 | 13 | 2,197 字 | 2.2 ms |
| `apps/mcp/src/server.ts` | 52／52 | 52 | 0 | 2,185 字 | 1.8 ms |
| e2e spec | 62／62 | 61 | 0 | 1,685 字 | 1.8 ms |
| `packages/storage/src/context-recall-service.ts` | 22／22 | 22 | 4 | 2,640 字 | 2.1 ms |
| `packages/schema/src/index.ts` | 48／48 | 48 | 3 | 2,249 字 | 2.3 ms |

各驗證狀態的數量也與直接計數一致。原本約 7 次呼叫、27,000–60,000 字的拼湊，改為一次 1,685–2,640 字的回應。5,000 筆合成 Session 的效能測試中，三個路徑（各 28–125 筆 Session）的 p90 約 3 ms，門檻 50 ms。

## 未納入

- 沒有使用 related work 的檔案索引：它只收錄 changed files 不超過 20 個的 Session，實際資料中約一半的歷史會因此漏掉；檔名索引已涵蓋全部 Session，不需要新的 migration。
- 只比對完全相同的路徑，不把目錄或相似檔名當成同一個檔案；需要目錄層級時請改用 Web 的熱點畫面。
- 沒有新增 REST route 或 Web 畫面；這是給 Agent 修改前使用的讀取。

## 升級

1. 取得 1.6.17 原始碼後執行 pnpm bootstrap（或 pnpm install --frozen-lockfile、pnpm build 與 pnpm check）。
2. 若已安裝登入自動啟動服務，執行 pnpm service:restart，確認輸出「服務已在執行 1.6.17」。
3. 透過 launcher 連線的 Agent 會自動切換到新版並收到工具清單更新通知，不需要重新連線；只有 Agent 回報 `restartRequired` 時才重新連線一次。

完整流程見發行與升級指南（docs/release.md）。
