# Work Intelligence 1.6.20 更新說明

日期：2026-11-12。應用程式與 plugin 版本為 1.6.20；資料庫 schema 維持 32，不需要 migration。

## finalize 更快

每個 Agent Session 都以 `work_finalize_session` 收尾。以實際資料（328 筆 Session、43 筆待處理未結項）量測，finalize 中位數約 12–16 ms，其中真正寫入只占約 0.5 ms，大部分時間花在找「相關未結項」提醒：SQL 把每筆來源 Session 的每個變更檔案和每個查詢路徑兩兩比對，每一對都重新把路徑轉成小寫、統一斜線。

現在一次讀出符合條件的 pending 候選，在 JavaScript 評分，每個路徑只正規化一次。評分規則與排序完全沿用舊版：大小寫只折疊 ASCII 字母（與 SQLite `lower()` 相同），目錄依路徑段比對，同分時依來源 Session 完成時間、Session id、項目位置排序。改寫前先以舊 SQL 寫下特性測試固定排序（含同分、大小寫與反斜線、改名、目錄前綴與後綴）；在實際資料上以最近 100 筆 Session 產生 300 組焦點，新舊版本回傳的結果完全相同（共 7,211 筆命中，順序一致）。

| 量測 | 前 | 後 |
| --- | --- | --- |
| 相關未結項查詢（實際資料，中位數） | 5.9 ms | 0.9 ms |
| finalize（實際資料，經 MCP，21 次中位數） | 16.3 ms | 6.0 ms |
| 帶焦點的 `work_get_context`（實際資料） | 約 54 ms | 約 35 ms |
| finalize，20 個變更路徑（5,000 筆合成 Session，三個行程中位數） | 35.4 ms | 15.8 ms |
| finalize 寫入交易（5,000 筆合成 Session，中位數） | 3.8 ms | 1.0 ms |

知識頁維護提示改在交易提交後、和其他唯讀提醒一起計算，不再占住寫入鎖；提示內容不變，查詢失敗時只省略提示，不會讓 finalize 失敗。效能測試新增 `finalizeSession (changed files, Knowledge review)`：變更路徑與待辦來源 Session 及 Knowledge 的 `appliesTo` 重疊，操作 p90 上限 250 ms、交易 p90 上限 50 ms。

## finalize 回條：不再回顯剛送出的內容

實際的 finalize 請求約 3,000 字，回應卻有 5,249 字文字再加 5,453 字 `structuredContent`；其中 64% 是 `session`，把 Agent 剛送出的標題、摘要、workSummary 與 changedFiles 原樣送回。MCP 回應現在是一張回條：

- `session` 只有 `id`、`executionStatus`、`completedAt`、`updatedAt`、`verificationStatus`、`changedFilesCount`，以及伺服器自己決定或補上的事實：推得或與請求不同的 `startedAt`、與請求不同時的已保存 `changedFiles`、請求沒帶 `git` 時伺服器讀到的 commit 與分支、作廢狀態。
- `redactions` 只在有遮蔽時出現；請求帶了完成／取代的未結項 id，或重試從稽核還原出結果時，才回傳這兩個清單。
- follow-up、警告、知識頁提示照常回傳；`relatedOutstandingItems` 改為與 context 相同的指標形狀（id、來源 Session id、文字），來源標題與時間用 `work_get_session` 讀取。

實際資料上同一個請求的回應變成 1,500 字文字與 1,638 字 `structuredContent`；合成的真實大小請求在 `tests/mcp/response-size.test.ts` 鎖定在 2,000 字以內。REST `POST /api/work/finalize` 與 storage 結果維持完整 Session。

文字與 `structuredContent` 兩份都保留：MCP 規範要求回傳結構化內容的工具同時提供文字版本，給只讀文字的用戶端；Codex 的 finalize hook 則先讀 `structuredContent`。這個專案的工具沒有宣告 output schema，所以 SDK 不會驗證結構化內容，也沒有證據顯示 Claude Code、Codex 或 Claude Desktop 擴充只讀其中一份。

## 收尾時提示要檢查的 Knowledge

以前結束工作的 Agent 不知道自己改到的檔案涉及哪些 Knowledge；Knowledge 只有在之後讀取時才會帶 `possiblyStale`。finalize 回條現在可帶 `knowledgeToReview`：最多 3 筆同專案、active 的 Knowledge，而且必須是這次 Session 才第一次讓它可能過時的：

- `appliesTo` 直接點名一個變更檔案：與路徑完全相同，或是比對得到的 glob。只涵蓋上層目錄或只是路徑後綴的不算。
- 從 Knowledge 記錄或最後確認以來，沒有其他 Session 改過它涵蓋的檔案；也就是 `possiblyStale` 因這次才開始。已經是 `possiblyStale` 的 Knowledge 每次讀取都會標示，不在這裡重複。完成時間早於確認時間的補登 Session 不會觸發。
- 這次 Session 自己記錄的、或已在 `appliedKnowledgeIds`／`contradictedKnowledgeIds` 回報過的 Knowledge 不列入。
- 完全相同的排在 glob 前，同類再依更新時間由新到舊；與其他 `appliesTo` 掃描一樣最多讀最新的 2,000 筆 Knowledge。每筆附 `id`、`title`、命中的 `path`，以及與路徑不同時命中的 `appliesTo`。

只是提示，不會改動任何 Knowledge。記錄契約與 work-intelligence skill 說明 Agent 該怎麼做：仍成立就以 `work_update_knowledge` 帶 `confirm: true` 確認，被這次變更推翻就告訴使用者並在確認後更新，不確定就保留。

以實際資料最近 50 筆 Session 重播（唯讀，Knowledge 狀態取各 Session 當時）：最初「任何 `appliesTo` 命中」的寫法會在 32 筆出現提示，這 32 筆的 38 個項目全是完全相同的路徑命中，其中 32 個早已被先前的 Session 標為可能過時；改用上述規則後只有 5 筆 Session 出現提示（6 個項目），每個都點名這次改到的檔案。檢查時由新到舊讀之後的 Session，先在 SQL 以每個涵蓋路徑都含有的片段縮小範圍，遇到第一筆改過它的 Session 就停止；實際資料每次約 0.3 ms，5,000 筆合成 Session 中從未被改過的 Knowledge（需要走完所有後續 Session）約多 3 ms。

## 修正

- `work_get_knowledge_page_context` 的 Session 預覽在 100 字截短時，不會再把 emoji 或其他輔助平面字元切成半個；改用未結項清單原本就在使用、現在共用的截短 helper。
- 兩個「無法確認 lease 目錄」測試（系統狀態 API 與 doctor）改為把 registry 目錄換成同名空檔案，不再依賴移除寫入權限；以 root 執行或在 Windows 上也會真的跑到這個情境。

## 未納入

- 其他會回傳完整 Session 的寫入工具尚未改成回條：`work_update_session_work_summary` 約 5,900 字、`work_update_session_summary` 約 3,900 字、`work_update_session_title` 約 3,700 字、`work_update_session_metadata` 約 3,500 字（實際資料，文字版本；`structuredContent` 各多約 150–200 字）。它們的結果來自不同的 storage 回傳，留待之後一起處理。
- 知識頁維護提示本身的計算（依頁面讀取之後的 Session 完成時間）沒有改動，只移到交易之外。

## 升級

1. 取得 1.6.20 原始碼後執行 pnpm bootstrap（或 pnpm install --frozen-lockfile、pnpm build 與 pnpm check）。
2. 若已安裝登入自動啟動服務，執行 pnpm service:restart，確認輸出「服務已在執行 1.6.20」。
3. 透過 launcher 連線的 Agent 會自動切換到新版並收到工具清單更新通知，不需要重新連線；只有 Agent 回報 `restartRequired` 時才重新連線一次。

完整流程見發行與升級指南（docs/release.md）。
