# Work Intelligence 1.6.54 更新說明

日期：2026-11-18。應用程式與 plugin 版本為 1.6.54。資料庫 schema 仍為 33，沒有 schema 變更，不需要 migration。

## 摘要

本版改善桌面 App 的三個部分：

- 診斷匯出（DT-19）改為先預覽再儲存。預覽顯示將寫入的確切文字與遮蔽摘要；只有按下「儲存檔案…」才會寫檔。不上傳，沒有遙測。
- 舊 runtime 的延後清理（DT-24，ADR-16）。App 只在舊版退役滿 7 天、沒有任何 lease 持有它，且 Windows 可以把資料夾改名移開時才刪除。更新不再因檔案鎖失敗。
- Windows 上 SQLite 停滯的量測（僅測試）。`WI_SQLITE_TIMING=1` 只在 Windows CI 的測試工作中開啟，不改變任何門檻、逾時或斷言。

Windows 11 與 macOS 的實機驗收尚未進行，仍為**待實機驗收**。CI 結果：「CI：待補」。

## 診斷匯出預覽（DT-19）

在修復視窗中，「匯出診斷資訊」先開啟預覽對話框，不再直接寫檔。

- **預覽內容**：將寫入的確切文字，以及遮蔽摘要（依類別列出數量：路徑、授權碼、權杖、電子郵件等），還有因不是 App 自身日誌而捨去的輸出行數。摘要不顯示被遮蔽的值。
- **儲存**：「儲存檔案…」開啟儲存對話框，寫入的是預覽中的同一份文字（POSIX 上權限為 0600）。「取消」或 Esc 關閉對話框。
- **只手動匯出**：只有使用者主動匯出時才寫檔。不上傳，沒有遙測。
- **內容**：固定的欄位，包括版本、平台、服務擁有者與後端狀態、資料庫狀態、最近一次備份、最近的錯誤代碼、階段與時間，以及最近的輸出。輸出行只保留以 App 自己的日誌前綴開頭的行（例如 `[shell]`、`[desktop-child]`、`[work-intelligence]`）。其他行可能含工作內容或其他工具的設定，會被捨去並計數。
- **遮蔽範圍**：
  - 各平台的使用者主目錄（Windows `C:\Users\…`、macOS `/Users/…`、Linux `/home/…`，包含含空白的名稱與 JSON 跳脫形式）、UNC 路徑，以及資料庫與備份路徑；
  - 電子郵件、儀表板的一次性交接代碼、URL 參數與 fragment 中的秘密、URL 內的帳號密碼；
  - 權杖形狀：JWT、PEM 私鑰、AWS、Slack、GitHub 與 OpenAI 形式的金鑰。
- **第二道掃描**：獨立的掃描檢查已遮蔽的文字，並遮蔽仍殘留的內容。若最後的檢查仍找到內容，匯出會被拒絕，錯誤代碼為 `DIAGNOSTICS_SCAN_FAILED`。
- **大小上限**：檔案上限 1 MiB。超過時先捨去最舊的輸出行，再捨去最舊的錯誤，檔案中記錄捨去的數量。
- **預覽有效期**：預覽 10 分鐘內有效，只能儲存一次，而且只能從要求預覽的視窗儲存。否則 App 會顯示新的預覽。
- **線性時間**：所有遮蔽模式以線性時間執行。測試以約 75 種對抗性輸入形狀（各 200,000 字元）驗證，每一種都低於 200 毫秒。舊的遮蔽程式有一個在這類輸入下可能耗時數分鐘的模式，已改寫。
- **測試**：桌面 smoke 檢查儲存的檔案與預覽相同，且不含植入的合成標記。

DT-19 狀態：已實作（CI 可驗證部分）；實機驗收待做。

## 舊 runtime 延後清理（DT-24）

App 永遠保留目前與前一版 runtime。其他舊版 runtime 只在下列條件全部成立時刪除：

1. 已退役滿 7 天（退役時間記錄於 `<launcher root>/leases/gc-state.json`）；
2. 沒有程序在使用它。判斷依據是 lease 檔，不是 process ID；
3. Windows 允許把資料夾改名移開。

- **lease**：每個 launcher action（MCP、serve、hook）在 `<launcher root>/leases/<runtime id>/` 下建立一個 `<隨機>.lease`，內容只有 action 名稱與建立時間（不含路徑、參數或專案資料），程序結束時移除。MCP 與 serve 每 60 秒更新一次。
- **失效的 lease**：以 App 自己的單調時鐘計，超過兩次心跳未更新的 lease 視為已不存在（例如當機後遺留的 lease）。
- **刪除流程**：App 先把資料夾改名移開。Windows 上若有程序執行中或檔案開啟，改名會失敗，App 會稍後再試：10 分鐘、30 分鐘，之後每小時（App 執行中），以及下次啟動時。改名後若出現新的 lease，資料夾會改名回來。
- **更新**：更新不刪除 runtime，也不等待鎖。
- **無法寫入 lease 時**（例如 Agent sandbox 的唯讀 HOME）：action 照常執行。hook 保持靜默；MCP 寫一行不含路徑的 stderr。
- **殘餘風險**：兩種情況無法完全排除。第一，無法寫入 lease 的程序，在兩個以上版本前的 runtime 上執行超過 7 天。第二，被除錯器或 SIGSTOP 凍結超過兩次心跳的程序，會被視為已不存在。
- **成本**：Linux 上建立與移除一次 lease 的中位數為 0.12 至 0.15 毫秒，首次呼叫為 0.4 至 1.0 毫秒（預算 5 毫秒，與 hook 預算相同）。Windows 與 macOS 的數字由 CI 量測（`[lease cost]`）：「CI：待補」。
- **Windows 測試**：一項僅在 Windows 執行的測試，在舊 runtime 中持有真實的檔案鎖，確認更新成功、清理等待，鎖釋放後資料夾被移除。

DT-24 狀態：已實作（CI 可驗證部分）；Windows 檔案鎖的實機行為待實機驗收。R08 在 CI 可驗證部分已緩解。

## Windows SQLite 停滯量測（僅測試）

背景：一次 Windows 儲存測試曾花了 27.9 秒（平常為 1.8 至 4.2 秒）；在 PR #375 的 CI 中，一個壓力寫入程序在單次寫入中等待約 5 秒。本版加入量測工具，用來找出停滯發生的位置。

- **開關**：`WI_SQLITE_TIMING=1`，只在 Windows CI 的單元測試與 SQLite 壓力測試工作中設定。
- **記錄內容**（`tests/helpers/sqlite-timing.ts`）：超過 1 秒的每一次 SQLite 呼叫；`BEGIN IMMEDIATE` 等待的直方圖；資料庫開啟時間；每一次 `wal_checkpoint` 呼叫；超過 10 秒的測試。不記錄繫結值。
- **輸出**：以 CI artifact 上傳，`sqlite-timing-windows-latest`，以及 `sqlite-stress-windows-latest` 之內。
- **額外成本**：每次呼叫約 0.1 µs。
- **不變更**：沒有改變任何門檻、逾時或斷言。生產版建置檢查若發現此 helper 進入 bundle，會失敗。
- **量測結果**：「Windows 量測結果：待補」。
