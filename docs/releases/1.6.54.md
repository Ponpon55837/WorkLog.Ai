# Work Intelligence 1.6.54 更新說明

日期：2026-11-18。應用程式與 plugin 版本為 1.6.54。資料庫 schema 仍為 33，沒有 schema 變更，不需要 migration。

## 摘要

本版改善下列項目：

- 診斷匯出（DT-19）改為先預覽再儲存。預覽顯示將寫入的確切文字與遮蔽摘要；只有按下「儲存檔案…」才會寫檔。不上傳，沒有遙測。
- 舊 runtime 的延後清理（DT-24，ADR-16）。App 只在舊版退役滿 7 天、沒有任何 lease 持有它，且 Windows 可以把資料夾改名移開時才刪除。更新不再因檔案鎖失敗。
- Windows 上 SQLite 停滯的量測（僅測試）。`WI_SQLITE_TIMING=1` 只在 Windows CI 的測試工作中開啟，不改變任何門檻、逾時或斷言。
- 閒置的匯入預覽不再擋住連接埠變更。只有變更真的捨棄了預覽，才顯示提示。
- Hook 與 MCP 狀態辨識 launcher 形式的安裝。Web 狀態頁與桌面 Agent 頁使用同一個辨識器。

Windows 11 與 macOS 的實機驗收尚未進行，仍為待實機驗收。CI：PR #382 的 23 項必要檢查全部通過（commit c4e67ea）。

## 診斷匯出預覽（DT-19）

在修復視窗中，「匯出診斷資訊」先開啟預覽對話框，不再直接寫檔。

- 預覽內容：將寫入的確切文字，以及遮蔽摘要（依類別列出數量：路徑、授權碼、權杖、電子郵件等），還有因不是 App 自身日誌而捨去的輸出行數。摘要不顯示被遮蔽的值。
- 儲存：「儲存檔案…」開啟儲存對話框，寫入的是預覽中的同一份文字（POSIX 上權限為 0600）。「取消」或 Esc 關閉對話框。
- 只手動匯出：只有使用者主動匯出時才寫檔。不上傳，沒有遙測。
- 內容：固定的欄位，包括版本、平台、服務擁有者與後端狀態、資料庫狀態、最近一次備份、最近的錯誤代碼、階段與時間，以及最近的輸出。輸出行只保留以 App 自己的日誌前綴開頭的行（例如 `[shell]`、`[desktop-child]`、`[work-intelligence]`）。其他行可能含工作內容或其他工具的設定，會被捨去並計數。
- 遮蔽範圍：
  - 各平台的使用者主目錄（Windows `C:\Users\…`、macOS `/Users/…`、Linux `/home/…`，包含含空白的名稱與 JSON 跳脫形式）、UNC 路徑，以及資料庫與備份路徑；
  - 電子郵件、儀表板的一次性交接代碼、URL 參數與 fragment 中的秘密、URL 內的帳號密碼；
  - 權杖形狀：JWT、PEM 私鑰、AWS、Slack、GitHub 與 OpenAI 形式的金鑰。
- 第二道掃描：獨立的掃描檢查已遮蔽的文字，並遮蔽仍殘留的內容。若最後的檢查仍找到內容，匯出會被拒絕，錯誤代碼為 `DIAGNOSTICS_SCAN_FAILED`。
- 大小上限：檔案上限 1 MiB。超過時先捨去最舊的輸出行，再捨去最舊的錯誤，檔案中記錄捨去的數量。
- 預覽有效期：預覽 10 分鐘內有效，只能儲存一次，而且只能從要求預覽的視窗儲存。否則 App 會顯示新的預覽。
- 線性時間：所有遮蔽模式以線性時間執行。測試以約 75 種對抗性輸入形狀（各 200,000 字元）驗證，每一種都低於 200 毫秒。舊的遮蔽程式有一個在這類輸入下可能耗時數分鐘的模式，已改寫。
- 測試：桌面 smoke 檢查儲存的檔案與預覽相同，且不含植入的合成標記。

DT-19 狀態：已實作（CI 可驗證部分）；實機驗收待做。

## 舊 runtime 延後清理（DT-24）

App 永遠保留目前與前一版 runtime。其他舊版 runtime 只在下列條件全部成立時刪除：

1. 已退役滿 7 天（退役時間記錄於 `<launcher root>/leases/gc-state.json`）；
2. 沒有程序在使用它。判斷依據是 lease 檔，不是 process ID；
3. Windows 允許把資料夾改名移開。

- lease：每個 launcher action（MCP、serve、hook）在 `<launcher root>/leases/<runtime id>/` 下建立一個 `<隨機>.lease`，內容只有 action 名稱與建立時間（不含路徑、參數或專案資料），程序結束時移除。MCP 與 serve 每 60 秒更新一次。
- 失效的 lease：以 App 自己的單調時鐘計，超過兩次心跳未更新的 lease 視為已不存在（例如當機後遺留的 lease）。
- 刪除流程：App 先把資料夾改名移開。Windows 上若有程序執行中或檔案開啟，改名會失敗，App 會稍後再試：10 分鐘、30 分鐘，之後每小時（App 執行中），以及下次啟動時。改名後若出現新的 lease，資料夾會改名回來。
- 更新：更新不刪除 runtime，也不等待鎖。
- 無法寫入 lease 時（例如 Agent sandbox 的唯讀 HOME）：action 照常執行。hook 保持靜默；MCP 寫一行不含路徑的 stderr。
- 殘餘風險：兩種情況無法完全排除。第一，無法寫入 lease 的程序，在兩個以上版本前的 runtime 上執行超過 7 天。第二，被除錯器或 SIGSTOP 凍結超過兩次心跳的程序，會被視為已不存在。
- 成本：Linux 上建立與移除一次 lease 的中位數為 0.12 至 0.15 毫秒，首次呼叫為 0.4 至 1.0 毫秒（預算 5 毫秒，與 hook 預算相同）。Windows 與 macOS 由 CI 量測（`[lease cost]`）：Windows 首次 1.26 毫秒、中位數 0.75 毫秒；macOS 首次 0.59 毫秒、中位數 0.43 毫秒（CI 於 c1335bc 量測），都在預算內。
- Windows 測試：一項僅在 Windows 執行的測試，在舊 runtime 中持有真實的檔案鎖，確認更新成功、清理等待，鎖釋放後資料夾被移除。

DT-24 狀態：已實作（CI 可驗證部分）；Windows 檔案鎖的實機行為待實機驗收。R08 在 CI 可驗證部分已緩解。

## Windows SQLite 停滯量測（僅測試）

背景：一次 Windows 儲存測試曾花了 27.9 秒（平常為 1.8 至 4.2 秒）；在 PR #375 的 CI 中，一個壓力寫入程序在單次寫入中等待約 5 秒。本版加入量測工具，用來找出停滯發生的位置。

- 開關：`WI_SQLITE_TIMING=1`，只在 Windows CI 的單元測試與 SQLite 壓力測試工作中設定。
- 記錄內容（`tests/helpers/sqlite-timing.ts`）：超過 1 秒的每一次 SQLite 呼叫；`BEGIN IMMEDIATE` 等待的直方圖；資料庫開啟時間；每一次 `wal_checkpoint` 呼叫；超過 10 秒的測試。不記錄繫結值。
- 輸出：以 CI artifact 上傳，`sqlite-timing-windows-latest`，以及 `sqlite-stress-windows-latest` 之內。
- 工作日誌中的報告：Windows 的兩個工作在測試後執行 `tests/helpers/sqlite-timing-report.mjs`，把最慢的 10 次呼叫（操作、時間、SQL 前 120 字元、測試檔、測試名稱、角色）印在日誌中。每一次超過 1 秒的 `BEGIN IMMEDIATE` 等待也會列出，並附上同一個資料庫檔案上時間重疊的交易，作為可能的鎖持有者。不需要下載 artifact 就能讀到。
- 額外成本：每次呼叫約 0.1 µs。
- 不變更：沒有改變任何門檻、逾時或斷言。生產版建置檢查若發現此 helper 進入 bundle，會失敗。
- 量測結果：CI 於 c1335bc 在 Windows 單元測試中記錄了 108 個測試程序。103 個沒有超過 1 秒的呼叫。另外 5 個各有 1 至 9 次超過 1 秒的呼叫，最長 5.5 秒。其中最長的一次是 `BEGIN IMMEDIATE` 等待寫入鎖 5.5 秒；其他程序的 `BEGIN IMMEDIATE` 最長 1.1 秒，其餘的慢呼叫是一般陳述式，最長 3.9 秒。資料庫開啟最長 23 毫秒，`wal_checkpoint` 只有 2 次，沒有一次忙碌。壓力測試沒有超過 1 秒的呼叫。結論：停滯發生在等待鎖與個別陳述式執行期間，不在開啟資料庫或 checkpoint。個別陳述式的明細在 artifact `sqlite-timing-windows-latest` 中；本版不做修正，下一步依明細找出鎖的持有者。

## 閒置的匯入預覽不擋連接埠變更

修復視窗的連接埠變更，過去會因為匯入預覽而被拒絕。使用者在專案頁的「匯入」選了匯出檔並保留預覽，App 最多會拒絕變更 30 分鐘，理由是有工作進行中。

本版起，閒置的暫存預覽（沒有任何操作正在讀取它）不再阻擋連接埠變更。正在執行的匯入、備份、匯出與還原仍會阻擋。

- 變更成功後，連接埠區段只在這次變更真的捨棄了預覽時，顯示「未完成的匯入預覽已捨棄，請在專案頁重新選擇檔案。」
- App 重新啟動時會移除暫存檔。
- 伺服器回給桌面 App 的活動狀態新增獨立的 `pendingImport` 旗標。忙碌清單只保留匯入、備份、匯出與還原。
- Web UI 在使用者離開頁面（route leave）與 `pagehide` 時移除暫存檔。切換語言不會移除。上傳中途取消時，伺服器也不保留檔案。`pagehide` 送出 `keepalive` 的 DELETE，使用同一個 API 路徑、相同的標頭，以及相同的 Origin 與 Host 檢查，伺服器不需要例外。
- 沒有人移除的暫存檔，仍會在 30 分鐘後過期。
- 修復頁沒有新的「捨棄」按鈕。
- 已知限制：在最後一次檢查與重新啟動之間的幾毫秒內暫存的預覽，會被捨棄，但不顯示訊息。

## Hook 與 MCP 狀態辨識 launcher 形式

Web 狀態頁（doctor）過去只認得 checkout 形式的 hook（node 加上 checkout 內的腳本）。桌面 App 安裝的 hook 使用 launcher 形式（`"<shim>" claude-finalize-reminder`），狀態頁因此顯示「未安裝」。桌面 Agent 頁也不檢查事件與 matcher。MCP 的 work-intelligence 項目只要名稱存在，就顯示「已登錄」，即使指令不是 Work Intelligence。

本版在 `packages/agent-setup` 加入共用的辨識器，把每一條 hook 指令分為 launcher、checkout 或其他。狀態頁與桌面 Agent 頁都使用它。

每個必要的事件與 matcher 會得到下列狀態之一：已安裝、需要更新（stale）、未設定、已停用（Claude 的 `disableAllHooks`），或無法判斷（設定檔無法讀取）。

- checkout 形式：指令指向的腳本存在，且事件與 matcher 為最新時，視為已安裝。只有腳本遺失，或 matcher 過舊（例如舊版 Codex 的 PostToolUse matcher）時，才標為需要更新。
- 啟用中的 Claude plugin 視為已安裝。
- 介面顯示由誰管理：「已安裝（由 App 管理）」、「已安裝（由 checkout 管理）」或「已安裝（由 plugin 管理）」。
- checkout 管理的 hook 下方，介面會加上：「checkout 的 hook 設定仍然有效。「改由桌面 App 管理…」是選用的；改用後，移動 checkout、更換 Node 或更新 App 都不必重新設定。」
- MCP：launcher 或既有的 checkout 視為已登錄。其他指令顯示「已登錄，但指令不是 Work Intelligence」。狀態頁給的是提示，不是錯誤。
- 過去能辨識的寫法仍然能辨識：node 的選項（例如 `--no-warnings`）、環境變數前綴、`cd <目錄> &&`、相對於 `cwd` 的路徑、`pnpm --dir=` 與 `-C`，以及 `cmd /c`。Windows 上不加引號的反斜線路徑也能辨識。
- launcher、checkout 腳本與舊的 direct 腳本都會確認檔案存在。不存在時，hook 為「需要更新」，MCP 為「已登錄，但指令不是 Work Intelligence」。
- 桌面 App 把目前的 launcher 路徑交給後端，Web 狀態頁與 Agent 頁因此判定一致。指向其他 launcher 的 hook 為「需要更新」。
- App 不掃描磁碟，只檢查指令中的路徑。
- API 向下相容：既有的摘要欄位不變。新增的選填欄位含來源與各事件的狀態。

## 變更

- 桌面 App：診斷匯出加入預覽與儲存對話框；舊 runtime 的延後清理與 lease；閒置的匯入預覽不再擋住連接埠變更；Agent 頁依共用辨識器顯示 hook 狀態。
- Web：離開頁面與 `pagehide` 時移除暫存的匯入預覽檔；狀態頁依共用辨識器判定 hook 與 MCP 的狀態。
- 伺服器：活動狀態新增 `pendingImport` 旗標；狀態 API 新增選填欄位（來源與各事件的狀態），既有欄位不變。`pagehide` 的 DELETE 沿用既有的 API 路徑與檢查。
- 測試：診斷、lease 與 runtime 清理的單元測試，以及桌面 smoke；僅在 Windows 執行的檔案鎖測試；Windows SQLite 量測 helper（僅測試）；匯入預覽與連接埠變更的伺服器、schema、desktop-core、Web 單元測試與桌面 smoke；hook 與 MCP 辨識的 agent-setup、doctor、Web 單元測試與桌面 smoke。
- Schema：沒有變更（33）。

## 升級

沒有 schema 變更，不需要 migration。照常更新即可。

## 未驗證與已知限制

- Windows 11 與 macOS 實機尚未驗證：診斷預覽與儲存對話框、POSIX 0600 權限、舊 runtime 的改名與清理，以及 Windows 檔案鎖下的更新行為。
- Windows SQLite 停滯的原因尚未修正。量測只指出停滯發生的位置，見上節。
- DT-24 的殘餘風險見上節。
- 診斷遮蔽的已知缺口：路徑最後一段若含空格且沒有副檔名（例如 `/Users/a/Client Acme`），空格後的文字會留下。這樣規定，是為了讓路徑後面的一般文字能保留。電子郵件的本地部分超過 1024 個字元時，不會被當成一個地址遮蔽。

## 待實機驗收

- Windows 11 與 macOS 實機上的：
  - 「匯出診斷資訊」的預覽、「儲存檔案…」、「取消」與 Esc，以及儲存的檔案與預覽相同；
  - 舊 runtime 的延後清理，以及 Windows 上檔案鎖下的更新不失敗；
  - Windows CI 上傳的 SQLite 量測 artifact；
  - 閒置的匯入預覽下，連接埠變更成功；只在真的捨棄預覽時顯示提示；重新啟動後暫存檔已移除；
  - Agent 頁與狀態 API 對 launcher 形式與 checkout 形式 hook 的判定（Claude Code 與 Codex）。
