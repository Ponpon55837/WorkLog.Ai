# Work Intelligence 1.6.23 更新說明

日期：2026-11-12。應用程式與 plugin 版本為 1.6.23；資料庫 schema 維持 32，不需要 migration。

## 安全性：appliesTo glob 比對的成本有上限

1.6.18 起 glob 比對不再回溯，但一次比對的成本仍是「樣式長度 × 路徑長度」，兩者在 schema 上限都很大。儲存的 glob 對很長的呼叫端路徑，仍可能讓單執行緒的 MCP 與 API 程序每次呼叫停住數秒，所有連線都受影響。這類樣式要先被保存（Agent 寫入後被接受，或經由匯入），之後會一直留在資料庫。現在分三層限制：

- **比對前的精確排除**：路徑比樣式的字面字元與 `?` 總數還短、開頭或結尾的字面片段不符，或中間的字面片段沒有依序出現時，直接判定不符合，不執行比對。這些條件都是精確的，不是估計。
- **星號上限**：一個 glob 最多 16 個星號（`*` 或 `**`，相鄰的同類星號算一個）；實際資料中每個 glob 只有一個星號。超過上限的已儲存或匯入樣式照原樣讀出，但永遠不比對。新增 Knowledge（`work_record_knowledge`、REST 新增）以及提交候選與審核候選時的編輯，超過上限會以驗證錯誤拒絕，訊息說明要拆成較窄的 glob 或列出一般路徑。更新不拒絕這類樣式，所以這種記錄仍可封存或只改其他欄位；只要更新後的 `appliesTo` 仍有超限項目，`work_update_knowledge` 會回傳 `warnings`，指出位置與改法。JSON 匯入、還原與讀取不套用這條規則。
- **固定的步數預算**：每次掃描的比對以步數計（每組樣式與路徑 1 步，模擬比對時每讀一個路徑字元再依樣式長度計步），與時間無關，結果可重現。呼叫端路徑的掃描（寬鬆 Knowledge 搜尋、檔案歷史、finalize 的 `knowledgeToReview`）上限 2,000,000 步，實際資料最重的一次用 4,332 步；讀取 Knowledge 時的 staleness 檢查上限 16,000,000 步，實際資料整份 Knowledge 清單約用 73,000 步。預算用完時停止掃描並在結果中標示：寬鬆 Knowledge 搜尋與檔案歷史帶 `appliesToScanTruncated: true`，finalize 結果帶 `knowledgeToReviewTruncated: true`，無法判定 `possiblyStale` 的 Knowledge 記錄帶 `stalenessUnchecked: true`。

| 情境 | 修正前 | 修正後 |
| --- | --- | --- |
| 30 筆 500 個星號的樣式對 20 個 1,000 字元路徑 | 約 3.6 秒 | 不到 2 ms（600 步） |
| 30 筆同樣式對 1 個 4,096 字元路徑 | 約 0.76 秒 | 不到 1 ms |
| 上限內最貴的 16 星號樣式，直到預算用完 | 約 3.1 秒 | 約 10 ms |

一般樣式的比對結果與之前完全相同：測試以原本的正規表示式為基準，比對固定對照表與新增的 6,000 組產生樣式；實際資料複本中 59,682 組樣式與變更檔案的組合結果完全一致。效能測試新增兩個案例（門檻 20 ms 與 100 ms）。

## 相關未結項：讀取量有上限

finalize 的 `relatedOutstandingItems` 與 `work_get_context` 的 `relevant.outstandingItems` 自 1.6.20 起把範圍內所有 pending 項目讀進來排名，沒有上限。現在每次最多讀 2,000 筆（來源 Session 由新到舊）；實際資料最大的專案有 43 筆。範圍內更多時結果帶 `truncated: true`，`total` 只計入已排名的項目。上限內結果與順序不變：實際資料複本上的 300 個焦點得到相同的命中與順序。也量測過先在 SQL 篩掉不相關項目的做法，但只少了一成多的資料列、呼叫時間卻變成兩倍，所以沒有採用。

## Skill：兩條規則回到核心

1.6.22 拆分 skill 時，「Agent 自主決定的決策會進入 Web 審核佇列；確認、拒絕與升為 Knowledge 只能在 Web 進行」只留在記錄格式文件。這句話回到核心 skill 的 finalize 步驟，並補上一句：被進行中的整理未結項請求涵蓋的項目，不可用 finalize 的 `resolvedOutstandingItemIds`／`supersededOutstandingItemIds` 繞過審核。兩條都列入閱讀預算測試的核心規則清單。

## 其他

- `db:redact` 的註解改為正確描述：重新索引在整理的交易提交後執行；舊的索引列已在同一個交易中刪除，重新索引失敗只會留下待更新標記，下一次讀取時補上。行為不變。

## 未納入

- Web 不顯示新的截斷與 `stalenessUnchecked` 標示，留待之後版本。
- `stalenessUnchecked` 只出現在完整 Knowledge 記錄，recall、context 等摘要不帶這個標示。

## 升級

1. 取得 1.6.23 原始碼後執行 pnpm bootstrap（或 pnpm install --frozen-lockfile、pnpm build 與 pnpm check）。
2. 若已安裝登入自動啟動服務，執行 pnpm service:restart，確認輸出「服務已在執行 1.6.23」。
3. 透過 launcher 連線的 Agent 會自動切換到新版並收到工具清單更新通知，不需要重新連線；只有 Agent 回報 `restartRequired` 時才重新連線一次。

完整流程見發行與升級指南（docs/release.md）。
