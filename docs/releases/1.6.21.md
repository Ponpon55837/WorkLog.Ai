# Work Intelligence 1.6.21 更新說明

日期：2026-11-12。應用程式與 plugin 版本為 1.6.21；資料庫 schema 維持 32，不需要 migration。

這一版只改讀取路徑的效能，所有回應內容與形狀都不變。CPU profile 顯示讀取時間有 79–86% 花在 SQLite 內，所以改善來自少做掃描與重複查詢，而不是 JavaScript 微調。

## 結果完全相同

- 實際資料（以副本量測）：未聚焦與全域 `getContext`、5 個 task context、15 個 recall、41 個寬鬆 Knowledge 搜尋、6 個 Session 列表文字查詢、Dashboard、提醒聚合與 metadata follow-up 計數，修改前後各跑三次，220 個序列化結果的雜湊完全相同。
- 合成資料：5,000 與 20,000 筆 Session 的 benchmark 資料庫上，37 個受影響的讀取路徑修改前後的雜湊完全相同。
- `tests/storage/read-path-equivalence.test.ts` 以修改前的實作作為 oracle，比對 recall／寬鬆 Knowledge 搜尋／focused context 的排序、逐筆與整批重建索引後的 chunks、rowid、paths 與 FTS 分數、文字查詢 Session 列表，以及改寫 join 順序的列表、Dashboard 事件數與熱點期間查詢。`pnpm test:retrieval-quality` 的 25 個案例數字與修改前相同。

## 每次 context 都要的計數改為快取

`work_get_context` 每次都回傳 metadata follow-up 計數，這個計數要掃描範圍內每一筆 Session 的 changed files 與 verification JSON，在 5,000 筆 Session 時約佔未聚焦 context 的一半。現在結果依專案範圍保存在每個連線上，key 是在同一個 statement 讀出的資料庫識別、`data_revision` 與 SQLite `schema_version`：

- 每張 project-data 資料表都有在同一個交易內遞增 `data_revision` 的 trigger，計數器存在資料庫檔案裡，所以 REST server 或任何 MCP 程序的寫入，下一次讀取都會重新計算。
- 替換資料庫檔案會換新的資料庫識別；另一個程序執行 migration 等 schema 變更會改變 `schema_version`。
- key 在計算前讀取；交易進行中既不讀也不寫快取，因為未提交的寫入會移動 revision，rollback 後另一個程序的提交可能得到同一個 revision 數字。
- policy 檢查每次照常執行，只重用計數本身；不同專案與全域範圍各自一個 key。

`tests/storage/data-revision-cache.test.ts` 用第二個 store 與原始連線模擬另一個程序，涵蓋這些情況（包括 rollback 後同一個 revision 數字、移除 trigger 後只剩 DDL 改變）。同一次 `work_get_context` 裡，知識頁摘要、知識頁省略清單與待處理知識頁需求原本各自重建同一個專案的知識頁記錄，現在每次呼叫只建一次，呼叫結束即丟棄。

## recall 只讀排序需要的資料

recall 與寬鬆 Knowledge 搜尋原本對每個查詢詞執行一次 `MATCH`，把所有命中的 rowid 送回 JavaScript 組成集合，只為了算詞頻和判斷每個命中段落含哪些詞。現在詞頻改由 SQLite `COUNT(*)` 計算；只有在需要判斷段落含哪些詞時才讀 rowid：範圍內沒有命中段落、某個詞完全沒有命中，或只有一個詞有命中（OR 查詢回傳的每個段落一定含有它）時都不讀。嚴格搜尋零命中後的寬鬆搜尋若仍找不到結果，原本 7 次完整讀取（5,000 筆 Session 約 14 ms）變成 7 次計數（約 1.5 ms）。

排序本身混合 BM25、欄位權重、詞涵蓋率、路徑、近期度與 Knowledge 證據，SQL 無法依它排序，所以候選集合維持完整，沒有加 LIMIT；全量排序在 profile 中佔比可忽略，也維持不變。`appliesTo` 原本就每列只解析一次。

## 大量變更後的第一次讀取

搜尋索引由 trigger 標記待更新，讀取前同步。一般 finalize 後只有一筆待更新文件，仍由下一次讀取同步，剛寫入的 Session 立即可搜尋。大量待更新文件時：

- 同步改為在同一個寫入交易內，以一個 statement 移除所有待更新文件的舊 chunk 與 path 列，讀取與寫入 statement 每次同步只準備一次，專案路徑脈絡也只讀一次。刪除與寫入的列及順序不變，新 chunk 的 rowid 也與逐筆處理相同。5,000 筆 Session 重建由 839 ms 降到 572 ms。
- 線上專案資料匯入在提交後立即同步索引；`db:restore` 與 `db:redact --apply`（資料庫已是目前 schema 時）在結束前同步。之後的讀取不再承接這些大量變更。同步失敗時待更新標記保留，由下一次讀取處理，與以前相同。

`pnpm bench:recall-scale` 在 5,000 筆干擾 Session 時，recall p95（含評估快照第一次讀取時的整批重建）由 595 ms 降到 345 ms，排名與信心度數字不變。剩下的時間是必要的寫入（35,500 個 chunk、FTS 與 path 列）、斷詞與提交，沒有背景執行緒或計時器。100 ms 的目標沒有達成：一般 finalize 留下的大量待更新文件（例如連續寫入數千筆而中間沒有讀取）仍由第一次讀取在請求內同步。

## 其他查詢

- Session 列表的文字查詢原本先 `COUNT` 掃描一次、再以 LIMIT/OFFSET 掃描一次；現在一次讀出所有符合的 id（已排序），由數量得到總數，再依主鍵讀出該頁。頁碼超出最後一頁或 `pageSize: 0` 的行為不變。
- 最新優先的 Session 清單（Dashboard、context 的最近 Session 與最近決策）改以 `CROSS JOIN` 讓 SQLite 沿 completed 索引讀到上限就停，不再排序所有 tracked Session 的完整列；Dashboard 的 6 筆在 20,000 筆 Session 時由 9 ms 變成 0.02 ms。
- 報告與指定期間的熱點改從該期間的 Session 開始 join；提醒的未結項計數改從 pending 項目開始；Dashboard 事件數一次讀出符合的 Session。這些改寫在 20,000 筆 Session 時隨資料量成長得比資料快，原因是每個事件或路徑都要隨機讀一次 Session 列，資料庫超過 page cache 後成本急升。

## 未納入

- 沒有 schema migration。之後若要再加速 Dashboard，可新增部分索引 `CREATE INDEX idx_sessions_live_project ON sessions(project_id) WHERE voided_at IS NULL`：20,000 筆 Session 時 Session 計數由 4.8 ms 降到 1.4 ms；事件數仍取決於事件數量，沒有改善。`sessions(project_id, updated_at)` 不會被「本期更新的較早 Session」查詢採用，不建議。
- 報告的「本期更新的較早 Session」需要讀該專案所有較早的 Session（20,000 筆時約 2.8 ms × 3）；年報與全部期間熱點在 20,000 筆時仍約 250 ms 與 170 ms，主要是讀取量，沒有明確的計畫問題。
- 帶多個命中詞的 recall 與寬鬆 Knowledge 搜尋仍需讀取每個詞的 rowid；FTS5 不提供每列各詞是否命中的輔助函式，node:sqlite 也無法註冊 FTS5 輔助函式。

## 升級

1. 取得 1.6.21 原始碼後執行 pnpm bootstrap（或 pnpm install --frozen-lockfile、pnpm build 與 pnpm check）。
2. 若已安裝登入自動啟動服務，執行 pnpm service:restart，確認輸出「服務已在執行 1.6.21」。
3. 透過 launcher 連線的 Agent 會自動切換到新版並收到工具清單更新通知，不需要重新連線；只有 Agent 回報 `restartRequired` 時才重新連線一次。

完整流程見發行與升級指南（docs/release.md）。
