# Work Intelligence 1.6.60 更新說明

日期：2026-11-19。應用程式與 plugin 版本為 1.6.60。資料庫 schema 仍為 33，沒有 schema 變更，不需要 migration。

## 摘要

本版修正 Windows 上 MCP 連線數仍是 0 的問題，並處理 1.6.59 桌面版審查留下的小問題。

## 修復項目

- **MCP 連線數仍是 0（Windows）。** 找到原因：Agent 把「已連線」的觀察寫在設定目錄，但 MCP 的 lease 放在作業系統暫存目錄，而暫存目錄依程序看到的 `TEMP`／`TMP` 而定（受限的 Agent 環境、8.3 短檔名、大小寫不同都會不同），後端因此在另一個目錄計數。現在 lease 放在設定目錄、與觀察同一處，兩邊不會再對不上；舊的暫存位置在過渡期仍會讀取（1.8.0 移除）。範圍雜湊改用真實路徑，Windows 上不分大小寫與分隔符。
- **App 內的 MCP 根本不記錄 lease。** App 的 runtime 是獨立套件（standalone bundle），而獨立套件一律略過 lease 註冊，所以不論目錄在哪，連線數都不可能大於 0。現在在 App 內執行的套件（設有範圍變數，或位於 `<App 根>/runtimes/<id>/`）會註冊；一般獨立安裝仍不註冊。
- **lease 失敗不再無聲。** MCP 把自己的 lease 範圍、目錄是否可寫與失敗原因記在 `agent-observations.json` 的選用欄位（檔案版本仍為 1，舊版 App 讀取不受影響）。Web 系統狀態會說明為什麼是 0（範圍不同、目錄不可寫、Agent 已斷線，或舊版 MCP 未回報）；診斷摘要多了 MCP lease 區段，只含範圍 id（8 個字元）、數量與布林值，沒有路徑。
- **啟動失敗在服務停止前就標為需修復。** 準備 runtime 失敗時，若服務仍在執行，不再把 App 標為已停止或需修復。
- **資料庫檢查沒有期限。** 唯讀的完整性檢查現在在既有的 5 分鐘上限到時明確失敗；沒有調大任何逾時。整理步驟根本沒執行時，不再回報「資料不完整」。
- **同一資料庫的第二個伺服器。** 設定的連接埠被同一個資料庫的另一個 Work Intelligence 伺服器占用時，不再另外啟動備援伺服器（換資料庫與接管也一樣），改回報原本的錯誤。
- **備份位置。** 資料夾在判斷風險前不再被建立，被拒絕的資料夾不會留下東西。重啟失敗後改回舊資料夾也失敗時，結果會明確告知（`not-restored`）並進入修復流程，不再只寫入日誌。
- **還原。** 暫存副本建立期間若有 Agent 開啟了資料庫，不會清空資料庫的 WAL 與 SHM；還原會以「資料庫使用中」停止，現有資料庫完全不動。
- **換新電腦時還原。** 兩個缺少的專案與所選資料夾同名時，或會落在同一個資料夾的專案，不再對應。

## 說明

- 沒有更動、附原因：後端無回應時（`reportUnresponsive`）與其他停止走同一條單一停止路徑，該路徑會把關不掉的子行程記在結果裡而不是丟例外。
- 限制：觀察每個 MCP 程序只寫一次，第一次列出工具之後的心跳失敗不會反映在其中；Agent 看得到、後端看不到的 `WORK_INTELLIGENCE_CONFIG_DIR` 仍會讓兩者分開。Codex 是否把 `TEMP`／`TMP` 傳給 MCP，沒有 Windows 機器無法驗證。
