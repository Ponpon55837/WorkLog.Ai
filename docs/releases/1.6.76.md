# Work Intelligence 1.6.76 更新說明

應用程式與 Agent plugin 版本為 1.6.76。資料庫升級到 schema 38，升級時會先備份再自動遷移。

## Agent 審查請求也涵蓋有疑慮的 Knowledge

除了待確認的決策與 Knowledge 候選，Agent 審查請求現在也會納入需要重新確認的 active Knowledge：

- **可能過時**：建立或上次確認之後，有後續工作改了它 `appliesTo` 涵蓋的檔案。只是一次改了很多檔案的大範圍工作（`broadChangesSince`）不算。
- **被後續工作指出有矛盾**：有 Session 回報這筆 Knowledge 和實際情況不符。

判斷規則與注意事項佇列相同。很久沒確認、但沒有上面兩種訊號的 Knowledge 不會納入。Knowledge 和決策、候選共用一次 500 筆的上限，請求上另外顯示 Knowledge 的筆數。

Agent 讀到的每筆 Knowledge 包含內容、`appliesTo`、為什麼有疑慮、建立與上次確認時間，以及最多 5 筆之後改到相關路徑的 Session（標題、完成時間與相關路徑）。項目本身維持原本的欄位長度，後續 Session 與既有 Knowledge 清單只用一頁剩下的字數。

### 三種處理方式

每一種都要附理由，處理結果立即生效：

- **仍成立**：Agent 核對後確認內容仍正確。和你在 Web 按「確認」相同，會更新上次確認時間並清除疑慮。
- **封存**：內容已不適用，走原本的封存流程。
- **改寫後取代**：Agent 寫一筆新的 Knowledge 取代舊的。新的這筆走原本的寫入流程，舊的會被封存；沒有改寫的欄位沿用舊的。

Agent 必須實際讀過目前的程式碼或後續工作記錄才能判斷。證據不足時不送出，項目保持待處理。不能只因為相關檔案有變動就封存。Agent 也只會在你建立請求後才處理，不會自己發起。

新 Knowledge 寫入被拒絕時（例如內容含敏感資訊），回應會帶 `knowledge_rejected` 與原因。項目不會被標成已處理或過期，修正後可以用新的 `idempotencyKey` 重新送出。

## 在 Web 檢查與推翻

「知識」分頁的 Knowledge、候選與待確認決策三個清單旁邊，右側欄都有「Agent 審查請求」，可以建立請求並查看進度與結果；清單本身留在畫面最上方。Knowledge 清單的標題列可以切換「全部 Knowledge」與「由 Agent 處理」，後者列出每筆的處理方式、理由與時間。覺得不對時按「推翻」：

- 仍成立：撤回 Agent 的確認，上次確認時間與疑慮標記回到確認前的狀態。
- 封存：Knowledge 恢復為使用中。
- 改寫後取代：Agent 建立的新 Knowledge 封存，原本的 Knowledge 恢復為使用中。

Agent 處理之後你又改過的 Knowledge，推翻時會維持你改過的樣子。

REST：`GET /api/agent-review-knowledge`（可帶 `projectRoot`）列出結果，`POST /api/knowledge/:knowledgeId/overturn` 推翻。

「請 Agent 處理」按鈕不再因為沒有待確認的決策與候選而停用，因為 Web 無法事先知道有沒有需要審查的 Knowledge。沒有任何可處理的項目時，會顯示目前沒有待審查項目的訊息。

## 修正

- 較早完成的工作記錄事後補報「有套用」某筆 Knowledge 時，不會再清掉較晚的工作記錄留下的「被指出矛盾」標記。回報本身仍會記錄，但這筆 Knowledge 會繼續留在需要複查的清單與 Agent 審查請求中。
- 反方向也一樣：較早完成的工作記錄事後補報「被指出矛盾」時，不會把之後已確認過的 Knowledge 重新標成需要複查，也不會蓋掉較新的矛盾標記。判斷依證據發生的時間，和搜尋排序用的規則相同；時間相同時以確認為準。
- 推翻 Agent 的「仍成立」只撤回 Agent 那一次確認。之後你或其他工作記錄又確認過的，維持不變（結果為 `unchanged`），同一毫秒內的確認也一樣；Agent 確認之後才回報的矛盾也會保留。
- 審查請求建立後，如果有其他工作記錄改到這筆 Knowledge 適用的檔案，Agent 對它的處理會以 `skipped_stale` 略過，因為 Agent 還沒看過這份新證據。和它無關的工作記錄不影響處理。
- Agent 審查的提示文字改為正確的提交操作名稱 `work_submit_agent_review_verdicts`。

## 要注意的限制

- 還來不及檢查是否過時的 Knowledge（後續工作太多，檢查在額度內沒做完）這次不會納入。
- 略過的判斷只看 Work Intelligence 記錄到的工作記錄；沒有存成工作記錄的程式碼修改無法偵測。
- 推翻過的 Knowledge 不會再進入之後的審查請求，和決策、候選相同。

## 資料庫

schema 38 只放寬 `agent_review_request_items` 的檢查條件，讓它能記錄 Knowledge 項目與「封存」「取代」兩種處理方式，沒有新增資料表或欄位。匯出、匯入、永久刪除與搜尋都不受影響。因為 SQLite 無法直接修改檢查條件，遷移時會在同一個交易中複製資料、重建這張表與它的索引和 trigger。

## 升級

桌面 App 可在「設定」分頁的「更新」卡片檢查新版。依使用的安裝方式參考[更新 Work Intelligence](../user-guide.md#更新-work-intelligence)。資料庫會從 schema 37 遷移到 38，遷移前自動備份；schema 31 到 37 的匯出檔仍可匯入。

這一版改了 MCP contract 文字，MCP 相容性 ID 因此改變：升級後已連線的 Agent 會收到 `restartRequired`，請重新連線 Work Intelligence MCP；更新 Agent plugin 後也一樣。Agent 開始工作前固定要讀的文字量由 42,249 降為 42,244（上限 42,250）。
