# 知識品質與檢索效率發展計畫

規劃日期：2026-10-22（Asia/Taipei）。狀態：使用者已同意以本文件作為正式計畫；Phase 0 完成；Phase 2 第一輪（PR #261～#263）與 P0 PR #268～#271 完成；Phase 1 依 Phase 0 第 4 步結果暫不開 PR；Phase 3 第一輪（C1–C4 盤點與量測）完成，結果見「Phase 3 進度」；Phase 4 第一輪（D1–D3 盤點與量測）完成；D1 第二輪最小方案已交付 PR #275，結果見「Phase 4 進度」；D2 不做，D3 經使用者決定不做；其餘階段尚未執行。檢視基準：WorkLog.Ai v1.6.4（main `f8653ed`）、SQLite schema 30。核心方向：Save What Matters · Retrieve What Matters · Learn What Works。

## 1. 目標

WorkLog.Ai 的目標不是累積最多工作紀錄，而是把開發者與 Agent 的工作成果整理成可維護、可驗證、可檢索、可重用的工作知識，讓後續 Agent：

1. 更快理解專案現況。
2. 更準確找到相關的歷史工作與技術決策。
3. 減少重複探索與已知錯誤。
4. 辨識過時、矛盾或缺乏驗證的資訊。
5. 完成任務後只保存值得保留的成果。
6. 在有限的 context 與 token 預算內取得足夠資訊。

**核心目標：資料持續增長，但 Agent 取得正確資訊的成本不應隨資料量等比例增長。**

## 2. 設計原則

- **品質優先於數量**：不以 Session、Evidence 或 Knowledge 的數量衡量成功。工作紀錄說明實際發生的事，Knowledge 幫助未來的工作，兩者不混用。
- **保留事實，不製造推論**：區分有證據的事實、Agent 尚未驗證的宣稱、確認未完成的事項、資料不足以判斷的狀態。缺少證據不等於失敗，單一操作成功不等於整個任務完成。
- **分層檢索**：任務開始時只給高相關、精簡的 context，需要時再讀完整 Session 與 Evidence。
- **知識可以演進，但不悄悄改寫歷史**：Knowledge 可確認、修正、取代或封存，保留來源與版本。
- **本機優先與使用者控制**：沿用 Project Recording Policy，只有 tracked 專案進入記錄與檢索；不因自動化而擴大預設收集範圍，也不自動替使用者建立 Agent 工作或鎖定工作流程。
- **不增加沒有證據支持的複雜度**：優先使用既有 SQLite、FTS、MCP 與 Knowledge 架構。是否導入 embedding、向量索引或新模型，由檢索品質實測決定。
- **先測量，再改善；先證明問題，再增加複雜度。**

## 3. 三層資訊架構

| 層 | 用途 | 要求 |
| --- | --- | --- |
| Evidence：事實與來源 | 讓工作紀錄可以被核對 | 可回到來源；區分已觀察與未觀察；標示來源不完整；避免重複；有大小限制與保留政策，不要求永久保留所有原始操作內容 |
| Work Session：結構化工作歷史 | 準確描述每次有意義的工作 | 沿用五段 workSummary（成果、範圍、決策、驗證、狀態／未結項）；一個 Session 可以沒有值得提升為 Knowledge 的內容 |
| Knowledge：可重用的專案經驗 | 協助未來的決策 | 保存重要決策、可重用流程、已確認的除錯方法、專案限制與常見陷阱；必須有適用範圍、來源與生命週期 |

## 4. 現況與缺口

以下現況是 2026-10-22 讀取程式與文件確認的結果，不是待新增功能。計畫中的改動應在這些能力上延伸，不建立平行的評估或檢索架構。

| 能力 | 現況 | 缺口 |
| --- | --- | --- |
| 合成檢索品質門檻 | `tests/storage/retrieval-quality.test.ts`：20 題虛構查詢分 K／S／R／N／P 五類，整體 hit@5 ≥ 0.95、MRR ≥ 0.90，另有詞彙擴展、證據強度、日期範圍、重複規劃片段等定向案例 | 只在小型合成資料上量測 |
| 個人資料檢索評估 | `pnpm eval:recall`：以唯讀快照評估 `work_recall` 與 `work_get_context`，輸出 hit@1、hit@5、MRR、no-hit 誤判、回應大小與延遲；2026-10-22 起有使用者私有題庫與真實資料基線（見 Phase 0） | 無答案題目的判斷（見 Phase 0 發現） |
| 效能門檻 | `pnpm test:performance`：5,000 筆合成 Session 的各讀取路徑 p90 門檻 | 合成資料單薄（Session 沒有未結項、Knowledge 只有少量、沒有 Evidence）；沒有更大規模 |
| 資料規模下的排序 | 無 | 沒有量測「加入大量不相關資料後，正確答案是否仍排在前面」 |
| Context 預算 | `work_get_context` 有焦點 10,000、無焦點 16,000 字元上限，跨區去重，省略項目附 `omitted` 與 `readWith` | 尚未依查詢類型區分預算 |
| MCP 回應大小 | `pnpm test:response-size` 檢查各工具序列化大小 | — |
| Knowledge 可信度 | 確認／推翻回饋影響排序；知識頁在來源 Session 變更、作廢或還原後標示 `needsReview` | 相似 Knowledge 的累積與合併建議尚未處理 |
| 儲存品質 | context 回報缺漏回填、缺少檔案清單、驗證未執行等計數；finalize 以 idempotency key 防重複 | 沒有 Session 重複率、驗證宣稱與 Evidence 一致性的量測 |
| Agent 讀取稽核 | Agent Read Audit 記錄 Agent 讀過哪些資料 | 讀取次數不代表有幫助，尚未與後續確認或推翻關聯 |

## 5. 工作主軸

### A. 儲存品質

- **A1 Session Quality Contract**：以五段 workSummary 為基礎，定義每段應保存與應拒絕的內容。重點：不把「實作」寫成「已驗證」；決策只寫有依據的理由；驗證區分通過、失敗、未執行與未知；未結項只寫確實存在的事；不在各段重複同一件事；沒有內容時允許留空。先強化 Agent 指引與驗收測試，不立即修改 schema。
- **A2 保存完整性**：針對忘記保存、重複建立 Session、缺少驗證資訊、Agent 中斷後狀態不明等情況改善既有 finalize 與保存提醒。只提醒或排入待處理請求，不自動建立 Session，也不因偵測到檔案修改就宣告完成。
- **A3 Knowledge 候選門檻**：以可重用性、具體性、證據強度、新穎性、有效範圍評估候選，先以明確條件與理由呈現，不必一開始就變成單一分數。允許直接拒絕重複、模糊、缺乏來源或價值不足的候選。

驗收：finalize 不強制產生 Knowledge；重複 finalize 不增加 Session；已知未驗證的結果不被標成通過；每筆接受的 Knowledge 都有可追溯來源；品質測試可以重跑。

### B. 精準檢索

- **B1 依問題類型檢索**：專案現況、歷史錯誤、技術決策、期間報告各有不同的優先資料。是否需要明確的查詢意圖分類，要由 Phase 0 的失敗案例證明。
- **B2 分階段檢索**：確認專案範圍 → 結構化欄位與 FTS 找候選 → 合併 Session、Knowledge、未結項 → 依相關性、證據、有效性與重複程度排序 → 在預算內回應 → 需要時再讀細節。錯誤代碼、檔名、API 名稱等精確查找不能被語意相似度蓋過；中文、英文與中英混合都要有測試。
- **B3 控制重複與低價值結果**：避免同一件工作的重複 Session 或相似交接佔滿結果，但保留「第一次修復失敗、第二次成功、後續測試推翻假設」這類重要差異。
- **B4 Context Budget**：結果優先包含標題與摘要、相關原因、有效性或驗證狀態、來源識別碼與取得細節的方式；來源不足、結果截斷或超出預算時明確回報。

驗收：不同資料規模下重要答案仍排在前面；大量不相關資料不明顯降低原本正確答案的排名；Agent 用少量 MCP 呼叫取得必要 context；回應大小不隨資料量無限制增長。

### C. 知識生命週期

- **C1 狀態管理**：已提出未審核、已接受有效、來源變更待核對、與新證據矛盾、已被取代、已封存。先檢查既有狀態與衍生規則是否足夠，再決定是否新增欄位。
- **C2 衝突處理**：新 Session 與既有 Knowledge 衝突時，保留原 Knowledge、記錄矛盾來源、標示需審查、附上證據，經確認後才修正、取代或保留。不能只因日期較新就判定較正確。
- **C3 控制膨脹**：對候選做相似知識檢查，可以建議合併、補充或取代，不自動刪除歷史依據。Knowledge Pages 呈現目前適用的知識，不無限制拼接所有 Session。
- **C4 實際使用價值**：可用既有 Agent Read Audit 與 Session 的確認／推翻引用關聯，不新增事件收集，也不因讀取次數多就宣稱知識正確。

驗收：過時或矛盾的知識能被辨識；歷史決策不被悄悄覆寫；更新有版本與來源；相同知識不無限累積。

### D. 幫助下一次工作

- **D1 Task-aware context**：深化既有 `work_get_context` 與 `work_recall`，依任務內容提供相關決策、近期工作、相關未結項與需要重新核對的 Knowledge。
- **D2 Project Brief**：由既有 Knowledge Pages 與 Session 衍生的精簡簡報，不是另一套獨立的永久事實來源；第一階段只透過 MCP 組合，不新增 UI 頁面。
- **D3 報告價值**：統計從原始結構化 Session 計算，不用前一份 AI 摘要生成下一份；沒有足夠來源時不補造結論。

驗收：報告的主要結論可回到來源 Session；能區分完成、進行中與未驗證；Project Brief 不與 Knowledge Pages 形成兩套矛盾的知識。

### E. 長期品質評估

- **E1 真實問題題庫**：涵蓋精確錯誤搜尋、模糊技術問題、已知修復方式、架構決策、跨 Session 延續、過時或矛盾知識、期間查詢、路徑查詢、沒有答案的問題、相似干擾。每題標記預期命中的 Session／Knowledge，或預期沒有結果。題庫依第 7 節的規則只留在本機。
- **E2 資料規模**：1,000、5,000、10,000、50,000、100,000 筆 Session，並含合理比例的 Evidence、Knowledge 與未結項。CI 維持 5,000 筆，更大的規模在本機手動執行。
- **E3 指標**：準確性（hit@1、hit@5、MRR、no-hit 判斷、過時 Knowledge 誤用、相似資料干擾）、效率（P50／P95 延遲、MCP 回應大小、token 估算、候選數量）、儲存品質（Session 重複率、紀錄遺漏、證據覆蓋、候選接受／拒絕原因、來源引用完整性）。不以單一指標代表整體品質。
- **E4 回歸門檻**：先測量基線，之後每次修改檢索邏輯都與固定題庫比較。品質不能在沒有理由下退步；效能變差需要明確的品質收益；回應大小不無限制增加；安全與資料政策不退化；正確的無結果判斷不被假陽性取代。具體數字依基線訂定。

## 6. 分階段實施

採小範圍、可驗收、可回退的增量開發。每個 PR 只處理一個問題，說明問題與重現方式、受影響的資料流程、範圍與不處理的事項、對既有契約與資料的影響、品質或效能結果、已知限制與回退方式。能用現有 schema 與衍生資料完成的功能先不新增資料表；需要 migration 時保證既有資料可讀，並測試升級與失敗情境。

### Phase 0：基線與缺口盤點（完成）

1. 在獨立 worktree 跑既有合成檢索品質、效能與回應大小測試，記錄基線。
2. 建立使用者私有的真實題庫（第 7 節），用 `pnpm eval:recall` 在真實資料的唯讀快照上產生基線。
3. 加入資料規模下的排序量測：把合成題目放進大量干擾資料中重測，並讓合成資料包含未結項、Knowledge 與 Evidence。
4. 把每個失敗歸類為保存、候選召回、排序、知識有效性或 context 輸出問題，依影響程度決定 Phase 1 與 Phase 2 的 PR。

完成條件：能重複量測資料品質、檢索準確度、延遲與回應成本。

#### Phase 0 進度與發現（2026-10-22）

- 第 1 步：合成檢索品質 25/25、回應大小 12/12 通過，數字與 `docs/testing.md` 記錄的基線一致。`pnpm test:performance` 在本機 Windows 有多項超過預算（例如有相關未結項的 `getContext` p90 約 700 ms，預算 500 ms），程式碼與 `main` 相同；CI 只在 Ubuntu 執行這組門檻，Windows 的實際速度另行追蹤。
- 第 2 步：建立 71 題私有題庫（51 題有答案、20 題無答案，涵蓋第 5 節 E1 的類別），由 Agent 擬題、另一個 Agent 複核。真實資料基線：recall hit@1 0.86、hit@5 0.98、MRR 0.91；context hit@5 1.00、MRR 0.94；recall 延遲中位數約 40 ms。較弱的類別是描述症狀的自然語句、過時或被推翻的知識、跨多個 Session 延續的工作。
- 第 3 步：新增 `pnpm bench:recall-scale`（量測方式見 `docs/testing.md`「資料規模下的排序量測」），在 1,000、5,000、10,000 筆合成干擾 Session 下重測 12 題正例、2 題未結項與 4 題無答案題。結果：
  - Knowledge、結構化 Session、自然語句問句（中英文）在每一級都排第 1，即使 10,000 筆時每題約有 70 筆標題只差一個詞的近似項；路徑題排第 1～2，輸的那一次是另一筆碰過同一個檔案的 Session。
  - 未結項題在約 3,000 個未結項中仍排第 1（其中約 500 個也被列為相關）。context 回應最大約 9,860 字元，在 10,000 字元上限內。
  - 答案只寫在 raw handoff 的題目在 1,000 筆時已掉到第 21 名或前 30 名以外，之後都找不到；搶到第一名的都是標題、tags、內文含部分查詢詞的 Knowledge。這是 raw 欄位權重（0.3，標題為 3）的直接結果，答案只存在 raw 時，規模一大就無法被找到。
  - 4 題無答案題有 1 題在 1,000 筆以上回傳 `high`，與真實資料的發現一致。
  - 這類多詞查詢的 recall 延遲中位數隨規模上升，10,000 筆時超過 1 秒（單次量測，誤差大）；寫入一筆 Session 的時間也隨資料量增加，10,000 筆時單筆超過 100 ms。原因見第 4 步。
  - 第一版干擾資料有兩個偏差，會讓結構化 Session 與路徑題看起來在 5,000 筆後失敗：Knowledge 全部用建立當下的時間，拿到完整新近加分；近似項會從其他欄位補回被拿掉的詞。修正後這些失敗消失，上面的數字都是修正後的結果。
- 第 4 步：逐題查看真實資料基線中沒有排第一的 7 題（recall 6 題、context 1 題），以及第 3 步的合成失敗與兩項變慢的原因。真實資料只在本機唯讀快照上查看，這裡只寫類別與題數。
  - **保存、候選召回：沒有失敗。** 7 題的預期答案都在前 8 名內；合成資料的 raw 答案也有被計分，只是排在後面。檢索會對所有命中的紀錄計分，沒有候選數量上限。
  - **排序：延續或被取代的紀錄壓過最終版（4 題，最大宗）。** 舊的準則排在後來推翻它的紀錄前面；中間版本排在最終版前面，即使中間版的標題已寫明後來改回；規劃紀錄排在實作與驗證紀錄前面；同一系列的主 Session 排在後續修正前面。這些紀錄彼此用詞相近，字面分數接近，排序看不出哪一筆是目前有效的版本。對應 B3 與 C1。
  - **排序：多欄位加總壓過精準答案（2 題，加上合成的 raw 失敗）。** 分數是各欄位命中的加總，所以內容很多的紀錄佔優勢：大型匯入 handoff 或主題相近的 Session，靠標題、摘要、raw 多處各命中幾個詞，壓過只在標題與內文精準命中的決策 Knowledge。合成資料是同一機制的反面：答案只在 raw（權重 0.3）時，輸給結構化欄位命中部分詞的紀錄。對應 B2。
  - **查詢解讀，不屬於檢索問題（1 題）。** 問句寫了日期，但評估沒有傳 `from`／`to`。工具契約已要求 Agent 自己把日期轉成 `from`／`to`，所以不改檢索；之後擴充題庫時，期間題要同時量測有傳與沒傳日期的情況。
  - **confidence 無法判斷有沒有答案。** 已在上面記錄並決定不改計算。
  - **context 輸出：沒有失敗。** 回應都在字元上限內，未結項題在大量資料中仍排第 1。
  - **效能：寫入變慢。** CPU profile 顯示寫入時約六成的時間花在找相關未結項：每次 finalize 都對所有待處理的未結項，逐一用 `instr` 比對每個查詢詞，所以耗時跟待處理未結項的數量成正比。合成資料讓 30% 的 Session 留下未結項且從不結案，放大了這個成本；真實資料庫目前的待處理未結項很少。`work_get_context` 也走同一段查詢。
  - **效能：recall 變慢。** 計分本身很快。主要成本是 recall 回傳前，替每一筆 Knowledge 命中各呼叫一次信任狀態查詢，每次都載入該 Knowledge 之後的全部 Session 來判斷是否過時；一次 recall 最多 30 筆命中，就重複掃描 30 次。已有可以一次處理多筆 Knowledge 的版本，recall 這條路徑沒有用到。另外，第一次查詢會補建所有尚未同步的搜尋索引，p95 的單次長延遲來自這裡。

  依影響程度排定的 PR（每個 PR 先用私有題庫與 `pnpm bench:recall-scale` 證明效益，再決定是否合併）：
  1. **recall 的 Knowledge 信任狀態改為一次批次查詢**（Phase 2 效能）：只改查詢方式，不改排序與回應內容。風險最低，直接降低 recall 延遲。
  2. **相關未結項的比對先縮小範圍**（Phase 2 效能）：避免每次 finalize 和 context 都全表逐字比對。要先量測真實資料的待處理未結項數量，確認值得做。
  3. **延續與取代關係進入排序**（Phase 2 B3，對應 4 題）：利用既有的 Session 延續連結，或在結果中把同一系列放在一起，讓最終版排在前面。要先量測真實資料中這些紀錄有沒有連結；沒有連結時，屬於 Phase 1 的保存品質問題（A2）。
  4. **欄位加總的正規化**（Phase 2 B2，對應 2 題與合成 raw 失敗）：限制單筆紀錄靠多欄位累加的分數，或依內容長度調整。影響範圍最大，最後做，並必須維持現有合成檢索品質門檻。

  Phase 1 的 A1～A3 目前沒有對應的失敗案例；依第 6 節「先證明再做」的原則，Phase 1 等第 3 個 PR 量測完連結覆蓋率後再決定範圍。

**confidence 只代表字面相符，不代表有答案。** 現行規則下，`high` 有 14／17 題第一名就是正確答案，但 20 題無答案題中有 3 題也是 `high`；`low` 同時包含正確答案、排名較後的答案與無答案題，沒有一題無答案題回傳 `none`。原因：

1. 中文查詢以兩字切詞，問句會產生跨詞片段。這些片段在整個資料庫都不存在，依 IDF 公式反而拿到最高權重，在各題平均佔查詢權重約一半，把所有紀錄的覆蓋率一起壓低，讓正確答案也落在 `high` 門檻以下。
2. 計算覆蓋率時排除這些片段，正確答案會升為 `high`，但無答案題也一起升為 `high`。
3. 再加上「至少命中幾個查詢詞」的條件也無法區分：難的無答案題，最接近的紀錄在結構化欄位可命中 5～14 個查詢詞。模擬中這個規則讓 `high` 涵蓋的正確答案從 14 題增為 32 題，無答案題誤判為 `high` 也從 3 題增為 6 題。

只靠字面比對無法判斷問題是否有答案。決定：不改計算，在工具契約、Agent skill 與 `docs/mcp-tools.md` 說明 `high` 與 `low` 都只是字面相符的訊號，引用前必須讀完整紀錄。之後若要改善，需要能理解語意的判斷，依第 2 節原則，先以題庫證明效益再評估。

## 7. 真實資料的使用規則

- 真實工作紀錄只能在本機用於執行測試與評估，不得 commit 或推送到 git，也不得寫入任何文件。題庫、評估結果與中間檔案都放在 repository 以外。
- 文件與 PR 只記載機制層面的發現與彙總數字，不包含查詢文字、Session／Knowledge 內容、id、檔名或專案名稱。
- 使用真實資料的評估在獨立的 git worktree 執行，不在使用者日常使用的 checkout 建置或測試，避免影響正在執行的服務與 MCP。
- `pnpm eval:recall` 以唯讀連線建立暫存快照，檢索與索引同步只作用在副本；評估時以 `--db` 指定資料庫，不複製資料到 worktree。
- repository 內的測試只使用虛構的合成資料。

## 8. 不納入的範圍

- 完整的 Agent telemetry 或監控平台；蒐集所有 prompt、tool call 與執行事件作為永久資料。
- 以 Session 或 Knowledge 數量作為成長指標。
- 全面導入 embedding 或向量資料庫。
- 讓 AI 未經審核自動改寫重要 Knowledge。
- 新的獨立資料中心或管理介面。
- 自動推論工作時間、驗證結果或完成狀態。
- 在沒有實測瓶頸前進行大規模重構。

新需求必須能證明提升了資訊品質、檢索能力、知識有效性或實際工作效率。

## 9. 最終成功標準

- **儲存**：每次完成任務後保留可靠的工作事實與必要證據，只有值得重用的內容提升為 Knowledge。
- **檢索**：Agent 能快速找到最相關、目前仍適用的資訊，不需要遍歷大量歷史。
- **效率**：資料量增加時，延遲、MCP 呼叫與 token 消耗保持可控。
- **可信度**：重要結論有來源，驗證狀態不被猜測，過時或矛盾的知識不被當成無條件有效。
- **長期價值**：歷史紀錄實際幫助後續 Agent 減少重複工作與重複犯錯。長期可用相同的真實任務對照有無 WorkLog context 的結果，但這不是任何階段的完成條件。

**WorkLog.Ai 不追求記住所有事情，而是持續保存值得相信、值得查找、值得重用的開發知識。**
