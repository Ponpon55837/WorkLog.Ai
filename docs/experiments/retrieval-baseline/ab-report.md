## 方法

- **兩臂**：A 是 main（3458302）的 `work-intelligence` skill。B1 在 `references/knowledge.md` 加 K-a、K-b、K-c、K-d，在 `references/reading-records.md` 加 R-a、R-b。兩臂的 MCP server 用同一份 build，只有 skill 文字不同；指引在要求時從各自的 skill 資料夾讀出。
- **資料**：每個 run 都用 `runner.mjs --prepare` 另建一個暫存資料庫，內容是 `fixture.mjs` 的虛構專案。沒有使用任何真實資料。
- **Agent**：每個 run 開一個 subagent 扮演使用者的 Agent。它只能透過一個小型 MCP stdio 用戶端（`tools`、`resources`、`read`、`call`）連到該 run 的 server。兩臂的 prompt 逐字相同，不提到實驗，也不要求固定格式或依據標籤。回答寫進 `answer.md`。
- **情境**：K1–K5，以及檢索題 A1、A6、B1、B4、B8、C1、C3、C6、D2、D4、D6、E1、E4，每格 A、B1 各 2 次，同一情境內 A、B1 交錯執行。
- **記錄**：每次 MCP 工具呼叫與 resource 讀取的字元數、MCP 呼叫次數、Agent 的 Bash 回合數、subagent 回報的 token 與耗時。token 包含讀指引的部分，指引字元另列為 `resourceChars`。
- **評分**：
  - 知識頁依 `knowledge-page-e2e.md` 的機械檢查，直接查資料庫。
  - 檢索題先機械比對 id（是否在資料庫中、是否命中 `mustCite`），再交給盲評。盲評看不到臂別，id 換成 fixture key，順序打亂。盲評逐點給答案要點分數，並檢查三件事：是否把 `mustNotCite` 當成現況、D4 是否提醒 `needsReview`、是否分開標示依據。
  - 通過條件：要點覆蓋至少 2/3，沒有把不可引用的紀錄當成現況，指定的信任標記有提醒。
- **事先定好的規則**：
  - 品質下降：B 兩次都失敗且 A 兩次都通過，再加跑 3 次確認。
  - 成本變差：13 題中 B 較差至少 10 題，且中位數差至少 20%。
  - 停止條件依任務說明，見「結論先講」。

## 限制

- **每格只有 2 次**，只能篩出明顯差異；7/10 對 10/10 的差距不能當成穩定的效果大小。
- **模型與輪次重疊**：subagent 原本要求的模型第 1 輪不能使用，改跑 Opus 5；第 2 輪跑 Sonnet 5.5。兩臂在同一輪使用同一模型，所以每輪是一個 block，但結論不能套用到其他模型。
- **檢索題有天花板效應**：A 已經全過，這批題目分不出 R-a、R-b 的品質差異。
- **盲評只有一位評分者**（Haiku），沒有做評分一致性檢查。
- **K 指引是綁在一起測的**：每條指引各自的效果是從失敗行為推論出來的，沒有做逐條移除的消融。
- **只有一份 fixture**；兩輪之間 token 的變動約 ±3%。
- **K4 的語意判定是事後決定的**，嚴格判定的結果同時列出。
- token 是 subagent 回報的總量，包含讀指引與 harness 的固定開銷，不是只算任務本身。
