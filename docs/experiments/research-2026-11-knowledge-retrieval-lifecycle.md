# 研究 R2：Knowledge 檢索與生命週期（2026-11）

> 這是調查階段的文件，結論放在最前面。本輪只產出結論與可重複執行的量測設計，不改 `packages/`、`apps/` 下的產品程式碼。
>
> 文中數字都是彙總值，即計數、比例與分位數，不含任何記錄文字。數字有兩個來源：
>
> - 檢索：單一專案上的時間序重播，共 285 個任務，其中 221 組是「任務 × 當時適用且有 appliesTo 的 Knowledge」。
> - 生命週期：6 個專案的私有副本，共 639 個 Session、1,298 條決策、146 筆 Knowledge。
>
> 所有腳本都由上層 session 在私有副本上執行，只回傳彙總 JSON。量測腳本：`docs/experiments/knowledge-task-recall-gap.mjs`、`docs/experiments/knowledge-lifecycle-probe.mjs`。

## 0. 結論摘要

| 主題       | 一句話結論                                                                                                                                                                                                                                                                                                                                                                                  |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A 檢索     | P5 之後還剩的缺口主要是**任務標題和 Knowledge 幾乎沒有共同用詞**：漏掉的配對，共同詞中位數只有 1 個。文字層的補救（document expansion、症狀詞彙表）在這份資料上精確率只有約 18%，不划算。有效的槓桿仍是**路徑**：P5 已經把嚴格命中從 11 拉到 60，事後知道變更檔時上限是 146。另一個問題在流程：沒有 appliesTo 的流程或約定類 Knowledge 只能靠「最近 12 筆」清單被看見，這是越用越差的結構。 |
| B 生命週期 | 二元的 possiblyStale 在路徑命中子集上標了 69%，失去鑑別力。只用現有資料做三級分級，strong 剩 15%（67/439），值得做，但要先用小規模人工標註驗證 strong 的精確率。「applied 宣稱會粉飾過時」在資料上不成立：三種確認規則下過時比例只差 0–2 個百分點。決策之間真正的取代極少，重複也只佔約 2%，**決策演進和去重都不值得做**。                                                                  |

**最值得先做的三件事**（依對「越用越好用」的貢獻排序）：

1. **為沒有 appliesTo 的流程類 Knowledge 建一條「專案常設規則」管道**，取代它們目前依賴的「最近 12 筆」。
   - 現況：Agent 回報 applied、但 appliesTo 沒涵蓋的 56 組中，46 組根本沒有 appliesTo，其中 73% 只靠最近清單被看到。
   - 問題：Knowledge 一多，這些就會被擠出清單，是唯一會隨使用量「越用越差」的缺口。
2. **把過時訊號改成分級**（strong／moderate／weak，只用現有資料），先做 30–50 筆的人工標註小實驗，確認 strong 的精確率後再產品化。
   - 現況：路徑命中子集 69% 被標成可能過時；69% 的過時配對是因為檔案在確認後被 4 個以上 Session 改過，也就是熱門檔案。
   - 分級後，strong 只剩 22% 的過時配對。
3. **P5 的兩個後續小實驗**：
   - (a) 只給 task 時為 Knowledge 保留名額。模擬排在前 5、但產品沒顯示的有 20 組。
   - (b) 檔案共變擴展，加上「至少 2 筆支持」的投票。沒有投票時精確率 46%，另外救回 19 組，代價是負面題多 16 筆。
   - 兩者都在 P5 的同一個路徑框架內，可以沿用 P5 的重播量測。

**不建議做**：

- Document expansion：精確率 18%，負面題多 55 筆。
- 由歷史累積的症狀詞彙表：精確率 18–19%。
- 改用 FTS5 原生多欄 `bm25()`：現行的 chunk 權重已經等效。
- 決策取代欄位與決策演進時間線：30 對候選中只有 1 對是真正的取代。
- 決策去重：只佔 2%。
- 「applied 必須帶路徑證據才推進確認基準」：對過時比例沒有影響。
- 向量資料庫、額外 LLM：使用者明定的邊界。

## 主題 A：只有任務描述時怎麼找對 Knowledge

### A.1 問題大小

重播資料來自 `knowledge-task-recall-gap.mjs` 在單一專案上的輸出，build 用的是 1.6.33 候選分支的 storage：

| 指標                                                         | 數字                                                                       |
| ------------------------------------------------------------ | -------------------------------------------------------------------------- |
| 任務（有變更檔的 Session）                                   | 285；其中有適用 Knowledge 的 98 個，負面題（沒有任何適用 Knowledge）175 個 |
| scoped 配對（有 appliesTo 且涵蓋該任務的變更檔）             | 221                                                                        |
| 只給標題、依任務找到                                         | 11（5.0%）                                                                 |
| 只出現在最近 12 筆清單                                       | 95（43%）                                                                  |
| 完全不在 context 裡                                          | 115（52%）                                                                 |
| applied_only 配對（Agent 回報 applied，但 appliesTo 沒涵蓋） | 56；找到 6，只靠最近清單 41（73%）                                         |
| 其中根本沒有 appliesTo                                       | 46/56                                                                      |
| P5 實測（上層提供，產品實跑）：嚴格命中                      | 11 → **60**（+49）                                                         |
| P5 實測：推測指標的品質                                      | 69 筆中 49 筆是目標（71%），負面題多 8 筆                                  |
| 事後已知變更檔時能找到的上限                                 | 146                                                                        |

基準可信：腳本量到的 221／11／95，和上層與 P5 實測各自量到的 221／11／98 一致。腳本模擬 P5（`d_p5Like`）的結果是救回 57、負面題多 8，和實測的 +49、+8 接近，所以腳本可以當作這類路徑擴展的估計器。

### A.2 缺口來自哪裡

只給標題時沒找到的 scoped 配對共 210 組，原因互斥、依序判定：

| 原因                                 | 組數 | 說明                                                                                       |
| ------------------------------------ | ---- | ------------------------------------------------------------------------------------------ |
| 詞彙落差，擴展也救不了               | 94   | 任務詞和 Knowledge 文字、來源或 applied Session 標題都沒有交集                             |
| 有交集，但排在預算外                 | 107  | 其中 86 組連最低覆蓋門檻 0.1 都沒過；模擬排在前 5、但產品沒顯示的 20 組；排名 6–12 的 1 組 |
| 詞彙落差，但 document expansion 可救 | 9    | 7 組靠來源 Session 標題，2 組靠 applied Session 標題                                       |
| 沒有 appliesTo，或 appliesTo 不匹配  | 0    | 依定義不在 scoped 內；applied_only 中分別是 46 與 4                                        |

Knowledge 寫的是解法與規則，任務標題寫的是要做什麼或症狀。漏掉的配對，共同詞中位數是 1 個（p90 是 2），任務詞中位數卻有 12 個。所以缺口主要不在排序或預算，而是**兩邊根本沒用同一套詞**。在不用向量和 LLM 的前提下，文字層能補的很有限。這也解釋了 P5 為什麼有效：它繞過文字，改用相似任務實際改過的檔案去比對 appliesTo。

P5 之後還剩約 161 組（221 − 60）。其中：

- 有 86 組（146 − 60）只要提早知道正確路徑就能找到。這是 R3「由伺服器觀察路徑」的範圍，本文只交叉引用，不重疊。
- 其餘大多是純詞彙落差，或 appliesTo 太窄、太錯。

### A.3 各做法的量測結果

估計來自重播模擬器。模擬器只在 Knowledge 之間排名，比產品寬鬆：在負面題上，模擬顯示 54 筆，產品顯示 33 筆。所以下表的絕對值偏樂觀，但各做法之間的相對比較可以採信。

加入項的精確率 = 救回 ÷（救回 + 負面題多出 + 正面題上多出的非目標）。

| 做法                                | 救回（scoped／applied_only） | 負面題多出（受影響任務數） | 正面題上多出的非目標 | 加入項精確率 | 判定                     |
| ----------------------------------- | ---------------------------- | -------------------------- | -------------------- | ------------ | ------------------------ |
| P5 實測                             | +49                          | +8                         | —                    | 71%          | 已上線                   |
| P5 模擬（`d_p5Like`）               | 57／0                        | 8（4）                     | 18                   | 69%          | 與實測一致               |
| (a) document expansion              | 8／19（合計 27）             | 55（42）                   | 69                   | 18%          | **不做**                 |
| (c) 症狀詞彙表，支持數 ≥1           | 1／20                        | 39（26）                   | 56                   | 18%          | **不做**                 |
| (c) 症狀詞彙表，支持數 ≥2           | 0／8                         | 11（9）                    | 23                   | 19%          | **不做**                 |

其他觀察：

- 三種做法的聯集最多救回 97–102 組，但主要是 P5 的貢獻。文字擴展帶來的雜訊大約是它救回的 4 倍。
- 若要保留 (a)，只在一個條件下值得重測：Knowledge 數量大很多，且來源或 applied Session 標題的用詞明顯比現在一致。在目前資料上不成立。

### A.5 建議

| 項目                                | 建議                 | 理由                                                                         |
| ----------------------------------- | -------------------- | ---------------------------------------------------------------------------- |
| **A1. 專案常設規則管道**            | **先做小實驗，再做** | 沒有 appliesTo 的流程類 Knowledge（46/56）依賴最近清單，Knowledge 增加就消失 |
| A2. 只給 task 時保留 Knowledge 名額 | 先做小實驗           | 模擬排在前 5、產品沒顯示的有 20 組；要量負面題代價                           |
| A3. 共變擴展加上 ≥2 支持投票        | 先做小實驗           | 沒有投票時精確率 46%，低於 P5 的 71%                                         |
| (a) document expansion              | 不做                 | 精確率 18%，負面題多 55 筆，在 42 個任務上出現                               |
| (c) 症狀詞彙表                      | 不做                 | 精確率 18–19%                                                                |
| (b) FTS5 原生多欄 bm25              | 不做                 | 現行 `FIELD_WEIGHTS` 的 chunk 權重已經等效；改成多欄要遷移並重建 FTS 表      |
| 最近 12 筆在帶 task 時的定位        | 併入 A1              | 帶 task 時，最近清單應讓位給常設規則與命中結果，不要單純刪除                 |

**A1 的設計方向**：

- 對象：active、沒有 appliesTo、kind 是 pattern、decision 或 gotcha 的 Knowledge。
- 排序：依證據（applied 次數、最近一次 applied、沒被 contradicted），不依 `updated_at`。
- 上限：固定筆數（例如 5–8 筆），帶 task 時排在 relevant 之後、最近清單之前。
- 與決策的關係：從決策辨識出的常設要求，提升成 Knowledge 後也走這條管道。但真實資料只有 3 組跨 3 個以上 Session 的常設要求（見 B.2-3），所以這條管道的主要來源是現有的無 appliesTo Knowledge，不是決策。
- 風險：applied 宣稱和實際路徑的一致性很低（R1 量測：專案累積 200 筆以上時只有 2%），單純依 applied 次數排序可能把錯的規則頂上去。排序要加上 contradicted 降權，並在實驗中和「依 `updated_at` 排序」對照。

## 主題 B：Knowledge 的生命週期

### B.1 問題大小

資料來自 6 個專案的私有副本，`knowledge-lifecycle-probe.mjs` 輸出：

| 指標                                                         | 數字                                                          |
| ------------------------------------------------------------ | ------------------------------------------------------------- |
| active 且有 appliesTo 的 Knowledge                           | 76 筆；以現況判定可能過時的 37 筆（49%）                      |
| 路徑命中子集重播（Knowledge × 即將改到它涵蓋檔案的 Session） | 439 對；可能過時 303 對（**69%**）                            |
| 上述過時配對中，確認後被 4 個以上 Session 改過               | 210/303（69%）                                                |
| 從確認到第一次後續變更的天數                                 | 中位數 2.2 天，p90 6.0 天                                     |
| audit 共 330 筆，其中更新 145 筆                             | 只有確認的 104 筆（72%）：來自 applied 75 筆，手動確認 29 筆  |
| audit 中有修改內文的                                         | 39 筆；改 appliesTo 的只有 2 筆                               |
| 用過 supersedes 的                                           | 3 次，都同時封存了舊條目                                      |
| 決策                                                         | 1,298 條；含「改為／不再／instead」等修訂語彙的 158 條（12%） |

上層先前看到的 138/142 是 context 輸出中帶 paths 的指標子集，和本表的 439 對重播口徑不同，但結論一致：**越接近「即將改這個檔」的情境，二元訊號越飽和**。熱門檔案在確認後兩天內就會被改，所以「確認後檔案有改過」幾乎恆真。

### B.2 回答三個問題

**(1) 如何讓過時訊號恢復鑑別力。**

只用現有資料可以算的分級（探針中的 `gradeStale`）：

| 等級     | 條件                                                                                                                                    | 現有資料可算？ | 路徑命中子集                 | 全量（76 筆） |
| -------- | --------------------------------------------------------------------------------------------------------------------------------------- | -------------- | ---------------------------- | ------------- |
| strong   | 涵蓋的檔案被刪除或改名（`changed_file_changes_json` 的 status），或 Knowledge 文字中的識別字出現在後續變更 Session 的標題、摘要或決策裡 | 可以           | 67（佔過時 22%，佔全部 15%） | 9             |
| moderate | 其餘                                                                                                                                    | 可以           | 119                          | 16            |
| weak     | 後續變更全是大範圍掃改（21 個檔以上），或只來自同一輪工作（session_links，或來源 Session 後 24 小時內）                                 | 可以           | 117                          | 12            |

| 訊號                         | 現有資料可算？                                                         |
| ---------------------------- | ---------------------------------------------------------------------- |
| 變更的行數或幅度             | 不行，Session 只記路徑與 added／modified／deleted／renamed，需新增記錄 |
| 變更是否真的碰到被引用的符號 | 不行，需要 diff 或符號層級的資料，需新增記錄                           |

其他事實：

- 全量 76 筆中，識別字有出現在後續變更的佔有識別字且已過時者的 28%；有刪除或改名的只有 1 筆。
- 識別字命中是粗略的代理，會誤報也會漏報。

**建議**：

- 產品端不再用一個布林值，改成分級：只有 strong 主動提示；moderate 保留；weak 收進細節。
- 順序要求：上線前先用 `--reveal` 抽 30–50 對 strong 與 weak 配對，請資料擁有者人工判定「Knowledge 內容是否真的已不成立」。只有 strong 的精確率明顯高於 weak（建議門檻：差距在 2 倍以上）才產品化。
- 借鑑：Swimm 以「被引用的符號是否還在」觸發；Stack Overflow for Teams 把過時當作排序與佇列，不當旗標。

**(2) 確認、修訂、取代、淘汰的成本，以及 Evidence-first。**

現有介面與成本（`apps/mcp/src/server.ts`、`packages/schema/src/index.ts`、`knowledge-service.ts`）：

| 操作 | 介面                                                                         | Agent 的成本                                      | 備註                                                            |
| ---- | ---------------------------------------------------------------------------- | ------------------------------------------------- | --------------------------------------------------------------- |
| 確認 | finalize 的 `appliedKnowledgeIds`，或 `work_update_knowledge {confirm:true}` | finalize 的 id 陣列不用額外呼叫；手動確認一次呼叫 | applied 會推進 lastConfirmedAt，這是只有確認的 audit 的主要來源 |
| 修訂 | `work_update_knowledge` 帶欄位                                               | 一次呼叫                                          | audit 存修改前後的完整快照                                      |
| 取代 | `work_record_knowledge {supersedesId}`                                       | 一次呼叫，但要先知道舊條目的 id                   | 同一個交易內封存舊條目                                          |
| 淘汰 | `work_update_knowledge {status:"archived"}`                                  | 一次呼叫                                          | 可以還原                                                        |
| 提示 | finalize 回傳的 `knowledgeToReview`                                          | 不用額外呼叫                                      | 只提示，不改任何資料                                            |

「以 applied 宣稱延後過時判斷，是否讓訊號失真」，用反事實回答：

| 確認規則                             | 全量過時比例   | 路徑命中子集過時比例 | 子集中 strong |
| ------------------------------------ | -------------- | -------------------- | ------------- |
| 現行（applied 與手動確認都推進基準） | 37/76（48.7%） | 303/439（69.0%）     | 67            |
| applied 必須自己改到命中的路徑才推進 | 37/76（48.7%） | 303/439（69.0%）     | 67            |
| 只有手動確認推進                     | 38/76（50.0%） | 313/439（71.3%）     | 81            |

**結論：在這份資料上，applied 並沒有粉飾過時**，三種規則只差 0–2 個百分點。原因是 applied 很少落在過時的 Knowledge 上：過時的 37 筆中，有 31 筆從來沒有被 applied。所以「applied 必須帶路徑證據」這條規則目前沒有實際效果，**不建議為了過時訊號去改它**。只有確認的 audit 佔 72%，是低資訊量的雜訊，但不影響過時判斷。

Evidence-first 的落點：

- 維持現行原則：已確認的 Knowledge 不自動改寫，`knowledgeToReview` 只提示。
- 降低成本的方向：讓 `knowledgeToReview` 依上面的分級只列 strong，並附上觸發的證據（檔案被刪或改名、命中的識別字）。Agent 看證據決定確認、修訂或封存，成本仍是一次呼叫。
- 現況缺口：程式層沒有任何機制阻擋已確認的 Knowledge 被直接改寫，保護只靠 skill 規範與不可變的 audit。這屬於 R4 的範圍，本文只記錄。

**(3) 決策之間的取代關係。**

| 量測                                                             | 數字                                                                                               |
| ---------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| 同專案、不同 Session、IDF Jaccard ≥ 0.3 的候選對                 | 53 對                                                                                              |
| 人工標註 30 對（資料擁有者在本機用 `--reveal` 看過，只回傳計數） | 後者確實修改前者 6 對，其中**真正改變做法 1 對**，其餘 5 對是加條件或擴大範圍；24 對是幾乎原文重述 |
| 修訂語彙在候選對中的比率                                         | 7–10%，比非候選的 12% 還低，不能當取代訊號                                                         |
| 正規化後逐字相同的重複群                                         | 9 群、22 條                                                                                        |
| 加上近重複（≥ 0.8）的重複群                                      | 11 群、27 條（佔 1,298 條的 2.1%）                                                                 |
| 跨 3 個以上 Session 的常設要求候選                               | 3 群、11 條                                                                                        |

**結論**：

- 真正的取代非常少。粗估 53 個候選中大約 1–2 個，佔全部決策不到 0.2%。
- 重複也只佔 2%。
- 所以以下都**不做**：決策取代欄位（要動 `session_decisions`、匯出入、永久刪除、MCP 契約，約 10 個檔案）、決策演進時間線、決策去重呈現。
- 對 Agent 來說，「改檔前知道哪些決策仍有效」的需求，比較適合由 Knowledge（`kind=decision` 加 appliesTo）滿足，而不是從決策文字推導。
- 若要保留低成本的選項，可以參考 adr-tools 的 `adr new -s`：只在 Agent 主動把決策提升成 `kind=decision` 的 Knowledge 時，用既有的 `supersedesId` 標出取代對象。這不需要任何新欄位。

## 量測腳本

兩支腳本都位於 `docs/experiments/`，共同性質：

- 唯讀開啟資料庫，在單一 read transaction 內讀完。
- 預設只輸出彙總數字。
- 都有 `--self-check`：用合成資料驗證邏輯，並斷言輸出中不含任何合成字串。
- 都通過 `pnpm lint` 與 `pnpm format:check`。

| 腳本                            | 用途                                                                                                  | 執行方式                                                                  |
| ------------------------------- | ----------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| `knowledge-task-recall-gap.mjs` | 時間序重播：缺口原因分類，以及 (a)(c)(d) 的救回與誤報估計，並附模擬與產品實際結果的對照               | 真實執行需要先 build `packages/storage`；`--self-check` 不需要            |
| `knowledge-lifecycle-probe.mjs` | 過時分級、路徑命中子集重播（`--path-hit-replay`）、確認規則反事實、audit 型態、決策取代與重複的啟發式 | `--sample N --seed S --reveal` 只供資料擁有者在本機人工標註，輸出不得回傳 |

另外，`task-path-replay.mjs` 補上了 `node:process`、`node:console` 的 import，讓全 repo 的 `pnpm lint` 能通過。這支檔案原本在 base 上就無法通過 lint。

## 未能查證的事項

- 多個借鑑來源的官方頁面在本 session 的網路無法直接讀取，表中標註「只讀到摘要」：sqlite.org、arxiv.org、Swimm、Guru、Stack Overflow 官方頁、adr.github.io、rfc-editor.org、peps.python.org、martinfowler.com。FTS5 `bm25()` 的欄位權重說明也沒有讀到原文。不過這項判定為不做，不影響結論。
- Michael Nygard 原文中「ADR 應不可變」的原句沒有查證。
- 檢索估計來自模擬排名器，比產品寬鬆（負面題上模擬 54 筆、產品 33 筆）。絕對數字偏樂觀，各做法的相對比較可以採信。
- 生命週期重播使用 Knowledge 目前的 appliesTo 與 kind，沒有用 audit 重建歷史版本；不過改過 appliesTo 的 audit 只有 2 筆，影響應該很小。
- 「識別字命中」是否真的代表內容已失效，以及 strong 等級的精確率，都還沒有人工標註，是 B1 實驗要回答的問題。
- 決策取代的比例只來自 30 對標註；「大約 1–2 個真取代」是外推值。
- P5 的實測數字（11 → 60、71%、負面題 +8）由上層提供，本分支沒有 P5 的程式碼。
